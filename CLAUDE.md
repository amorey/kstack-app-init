# kstack-app

A Kubernetes desktop app (Kubetail). Three parts that talk to each other:

- **`src/`** — React webview (this file's focus).
- **`src-tauri/`** — Tauri/Rust native host (windows, tray, sidecar lifecycle). See `src-tauri/CLAUDE.md`.
- **`sidecar/`** — Go sidecar (GraphQL API, Kubernetes + cloud logic). See `sidecar/CLAUDE.md`.
- **`proto/`** — shared gRPC contract (host↔sidecar). Single source of truth, compiled to Go (committed, via `protoc`) and Rust (via `src-tauri/build.rs`). Run `make proto` after editing.

The **`Makefile` is the polyglot entry point** — Go/Rust/JS commands meet there (`make test`, `make lint`, `make vet`, `make proto`). The Go sidecar deliberately lives outside `package.json`.

## Host↔sidecar transport: GraphQL **and** gRPC over one socket (h2c)

The host and sidecar share a single Unix socket / named pipe. **GraphQL** (webview↔sidecar) rides HTTP/1.1 (POST + SSE). **gRPC** (host↔sidecar control channel — today the tray's auth-state watch + login/logout, and the resync poke) rides HTTP/2. Both are multiplexed by **h2c**: the sidecar's composition root (`internal/app`) wraps its handler in `h2c.NewHandler` with a dispatcher (keyed on `grpcserver.IsGRPCRequest`) that routes HTTP/2 `application/grpc` requests to the gRPC server and everything else to GraphQL. No TLS (the socket is user-restricted). The cluster surface is **GraphQL-only** (`clusters`/`clustersWatch` + the parallel `clusterCachesWatch` + cluster mutations), consumed by the webview; there is no gRPC kube/cluster channel. `clustersWatch`/`clusterCachesWatch` are **Kubernetes-style delta watches** (an `Added` snapshot then per-object `Added`/`Modified`/`Deleted`), streaming the Cluster and ClusterCache kinds independently — the webview keys each into a map and joins caches onto clusters by `clusterID`. (The webview's kube-context picker derives its context list from `clustersWatch` — see `src/lib/kube-config.tsx`.)

## Frontend (`src/`)

React 19 + TanStack Router + [urql] (GraphQL) + Vite + Tailwind v4. UI primitives come from `@kubetail/ui`. Package manager is **pnpm**.

- Entry: `src/main.tsx` → `RouterProvider`. Routes in `src/routes/` (code-based, wired in `src/routeTree.ts`): `__root.tsx` mounts the provider stack only and renders an `Outlet`; `_app.tsx` is a **pathless layout route** whose component is `AppLayout` (the sidebar shell), and the pages — `chat.tsx` (`/chat`) and `dashboard.tsx` (`/dashboard`) — nest under it so they share that shell. Chat and Dashboard are **peer named routes**; `index.tsx` (`/`) owns no view — it redirects to `DEFAULT_ROUTE` (the one place the default lives), so New Window / secondary windows can open at `/`. The Chat/Dashboard switch is the sidebar's `ModeNav` (router `Link`s, not local state), so each mode is a real, deep-linkable route.
- **Active kube-context** is one window-wide choice shared by both modes, held in the `kubeContext` **search param** on `_app` (not a provider or the host file). `_app` declares it via `validateSearch` and keeps it across the chat↔dashboard navigation with `retainSearchParams(['kubeContext'])`, so it's per-window and deep-linkable. `src/lib/active-kube-context.tsx` (`useActiveKubeContext`) is the one accessor: it resolves the param against the context list (`useKubeConfig`), falling back to the kubeconfig's current context when the param is absent or names a gone context, and `setContext` just writes the param. The picker (`components/widgets/kube-context-picker.tsx`) is a thin control over it and lives in the **context bar** (`components/widgets/kube-context-bar.tsx`) — a slim strip across the top of the main content area, mounted in `AppLayout`'s `main` above the `Outlet` so it's shared by chat and dashboard (it's window-wide, exactly like when it sat in the sidebar, but with horizontal room the narrow sidebar lacked). The bar shows the full (untruncated) context name plus the context's **cluster** and **user** metadata — read from the resolved context via `useActiveKubeContext`'s `active` record, sourced from the Cluster's `status.source.kubeconfig` (namespace isn't exposed by the sidecar yet). Selection is a **frontend view-scope only** — it never rewrites the kubeconfig's current-context, and it isn't threaded into requests yet (chat's `ChatInput`/dashboard queries consume it per-feature, some needing a sidecar schema change).
- **Layouts** live in `src/layouts/` — presentational shells (each renders an `Outlet`) that layout routes mount. `AppLayout` is the main window (floating sidebar + inset). Secondary windows (log tail, container exec) will get their own sidebar-less layout here, nested under a separate pathless layout route; a Tauri window just opens at that route's path (see `src-tauri/window_manager.rs`).
- Path alias: **`@/*` → `src/*`**.
- App-wide concerns live in `src/lib/` (auth, error bus/boundary, sync-status, kube-config, ready-gate, `platform.ts` for sync `isMacOS()`/`isLinux()` UA detection, `host-file.ts` for host-persisted settings, `theme.tsx` for the color scheme); reusable UI in `src/components/widgets/`.
- **Theming**: `src/lib/theme.tsx` distinguishes two axes so a future skin feature slots in cleanly. (1) **Color scheme** — the user picks a `ColorSchemePreference` (`system`/`light`/`dark`, *when* the app is dark) that resolves to a concrete `ColorScheme` (`light`/`dark`; System follows `prefers-color-scheme`). It's class-based: the resolved scheme toggles a `.dark` class on `<html>` that Tailwind's `dark:` variant keys on (see `@custom-variant dark` in `index.css`; `@kubetail/ui` ships the `.dark` token overrides, and `index.css` paints the document `background` from the scheme's token so a new window's first frame is themed). The preference's **source of truth is the host's `host.json`** (`src-tauri/src/host_file.rs`) — the webview uses no localStorage for theming. It's just one field of that file, and **`src/lib/host-file.ts` owns the whole protocol** (`readInjectedHostFile` / `updateHostFile` / `subscribeHostFile`), so `theme.tsx` only picks its field out and the next host-persisted setting adds a field rather than re-implementing the plumbing. It flows three ways. *Boot*: the host injects the file into every window as `window.__KSTACK_HOST__` before any page script runs, so the **inline script in `index.html`** (hand-mirroring `resolveColorScheme`) applies `.dark` on first paint and `ThemeProvider` (in `__root.tsx`) initializes from the same global (`readInjectedPreference`) — no async reconcile. That the *window* doesn't flash white is a separate, purely host-side mechanism: the host paints each window's native background with the resolved scheme at creation, so its first frame is themed before the webview draws. The webview plays no part — there is no reveal step to add one to — see `src-tauri/CLAUDE.md`. *Change*: `setPreference` applies optimistically and writes through the host's general `update_host_file` command. *Sync*: after every write the host broadcasts the merged file to all windows (`host-file-updated`, hand-mirroring `host_file::UPDATED_EVENT`); each provider updates from it, so open windows stay in step. Components read it through `useColorScheme()` (`{ preference, setPreference }`); `applyPreference` mirrors the resolved scheme onto the root. (2) **Theme (skin)** — the named palette within a resolved scheme (e.g. "github-light"): **not built yet**, but the word "theme" is reserved for it (`resolveColorScheme` is the seam, the resolved `ColorScheme` indexing `themes[scheme]`, applied later as a `data-theme` attribute; persistence would be new `Option` fields on `HostFile`). The picker lives in the Settings dialog (`components/widgets/settings-dialog.tsx`, opened from the account menu via `openDialog('settings')`).
- **Window frame**: the three platforms draw their window frame three ways. **macOS** keeps native decorations (opaque; OS draws corners + shadow). **Windows** is frameless (`decorations(false)`) but **opaque** — DWM still draws a borderless window's own shadow (and rounds the corners on Win11), so the app must not paint a second one. **Linux** is frameless *and* **transparent** (`src-tauri`), so the OS draws no border or drop shadow and the webview supplies its own. `components/widgets/window-frame.tsx` (`WindowFrame`, wrapping the whole app at the root — see `routes/__root.tsx`, so loading/error states get it too) is that supplier **for Linux only**: it insets the app a few px from the window edge, clips to rounded corners, and paints a thin border + soft outer shadow into the transparent gutter. It uses `contain: paint` so the app's `position: fixed` chrome (title bar, sidebar) re-anchors to the inset frame instead of the window edge. On **macOS and Windows it's a passthrough** (both full-bleed; the OS draws corners + shadow). `main.tsx` tags `<html class="frameless">` **on Linux only** so the document background goes transparent (revealing the gutter); macOS and Windows stay opaque. Because the frame insets the app, a full-height screen must fill the *frame*, not the window: use **`min-h-[var(--app-min-h)]`** (defined in `index.css`) instead of `min-h-svh` — the variable is `100svh` when full-bleed (macOS/Windows, no frame box) and `100%` of the frame when frameless (Linux), so content isn't clipped at the bottom by the frame's `overflow-hidden` (and it tracks the frame's collapse to `inset-0` while maximized). The library's `SidebarProvider` hardcodes `min-h-svh`, so `app-sidebar.tsx` passes the same class to override it via `cn`/tailwind-merge. When the Linux window is **maximized** there's no off-window space for the gutter, so `WindowFrame` collapses to a full-bleed `inset-0` surface (no inset/corners/border/shadow) and the resize grips hide — matching native apps like Firefox; this is driven by `lib/window-maximized.ts` (`useWindowMaximized`), which re-queries Tauri's `isMaximized()` on every `onResized`. Dropping OS decorations also drops the native resize borders on **both Linux and Windows**, so `components/widgets/window-resize-handles.tsx` (`WindowResizeHandles`) renders invisible fixed edge/corner grips along the window edges (over Linux's gutter, or over the outermost px of the app on Windows) — each starts a native resize drag via Tauri's `startResizeDragging` (gated by `core:window:allow-start-resize-dragging` in `src-tauri/capabilities/default.json`). It's a **sibling** of `WindowFrame`, not a child: the frame's `contain: paint` would otherwise re-anchor its `position: fixed` grips to the inset box and clip them. Renders nothing on macOS (or while maximized).
- **Title bar / menu**: macOS keeps its native traffic lights and native global menu bar (`src-tauri/app_menu.rs`); the sidebar header doubles as the title bar. On Linux/Windows the window is frameless with a full-width custom title bar across the top (`app-sidebar.tsx`): a hamburger **app menu** (`components/widgets/app-menu.tsx`, `AppMenu`) at the left, a draggable strip in the middle, and custom **window controls** (`components/widgets/window-controls.tsx`, `WindowControls` — minimize/maximize/close, styled to read as native since there are no OS caption buttons) at the right; the floating sidebar starts just below the bar. Off macOS there's no native menu bar, so `AppMenu` stands in for it as the single hamburger holding the app-wide actions (New Window and Quit); it renders only off-macOS and owns the `Ctrl/Cmd+N` / `Ctrl/Cmd+Q` shortcuts, invoking the `new_window` / `quit` Tauri commands.

### GraphQL — never talks HTTP directly

The webview has **no network access**. urql is configured (`src/lib/graphql/`) to route every operation through Tauri IPC:

- Queries/mutations → `invoke('graphql_query')` (`invoke-fetch.ts`).
- Subscriptions → `invoke('graphql_subscribe' / 'graphql_unsubscribe')` over a Tauri `Channel` (`subscribe-exchange.ts`, with its own capped-backoff reconnect).

The Rust host forwards these to the sidecar over a Unix socket — queries as plain HTTP POSTs, and each subscription as its own SSE (`text/event-stream`) stream that the host parses into the `Channel` frames. When touching transport/retry logic, read `src/lib/graphql/client.ts` and its tests first.

### Codegen — generated types, don't hand-write

`pnpm codegen` (`codegen.ts`) reads the **sidecar's** schema (`sidecar/graph/schema.graphqls` — single source of truth) and emits `src/gql/`.

- Write operations with the **`graphql()` tagged template from `@/gql`**; the typed document drives urql.
- **`src/gql/` is generated — never edit it.** After changing a query or the sidecar schema, run `pnpm codegen` (or `pnpm codegen:watch`).

### Tests

Vitest + `@testing-library/react` (jsdom). Tests are co-located (`*.test.ts[x]`). Mock the Tauri bridge with **`mockTauriCore()` from `@/test-utils`** (and `vi.mock('@tauri-apps/api/core', …)` + dynamic import of the module under test). For GraphQL-driven components, push frames via `liveChannel().onmessage!(...)` — see `src/components/widgets/sync-health-badge.test.tsx`.

- **No magic sleeps.** Don't wait on wall-clock delays to let async work settle — use `vi.useFakeTimers()` + `advanceTimersByTimeAsync`, `await waitFor(...)`, or a `flush()`/`act` helper that drains microtasks. Real `setTimeout` waits are flaky and slow.
- Run: `pnpm test --run` (or `make test-js`). Watch: `pnpm test`.

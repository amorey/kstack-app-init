# sidecar — Go backend

A standalone Go binary started by the Tauri host. It exposes the app's GraphQL API (and a gRPC control channel) and owns all Kubernetes logic. **No TCP** — it listens on a Unix domain socket (named pipe on Windows), prints `READY unix:<path>` to stdout so the host can dial it, and shuts down on `SIGINT`/`SIGTERM` or **stdin EOF** (the host closing its end = "parent gone").

## Layout

The codebase mirrors the **kubetail layout**: `main.go` is lifecycle only, `internal/app` is the composition root + routing, and the GraphQL server lives in `graph` (alongside the resolvers). There is **no `server` package**; "the server" is the thin listener in `main.go`.

- `main.go` — **lifecycle only**. Parses flags, binds the socket, builds the `*app.App`, mounts it on an `http.Server`, registers `app.NotifyShutdown` via `srv.RegisterOnShutdown`, serves, and drives graceful shutdown (`srv.Shutdown` → `app.DrainWithContext` → `app.Close`). No composition logic.
- `internal/app/` — **composition root + routing + lifecycle owner**. `app.go` (`app.New(Config{...})`) builds the shared pieces (the `*poke.Service`, then `cluster.New(...)` → `*cluster.Service` — which owns its own kubeconfig watcher and beehive store/instance — plus `auth.Service` and `cloud.Service`), constructs the `graph.Resolver` (holding the `ClusterService` + `auth.Service`), wires the GraphQL server (`graph.NewServer`) and gRPC server (`grpcserver.NewServer`), mounts them on a mux, and multiplexes onto one h2c handler: an `h2c.NewHandler` whose dispatcher sends `grpcserver.IsGRPCRequest` traffic to the gRPC server and everything else to the mux. It owns this *composition* — that these two surfaces share a socket and the h2c wiring itself — while `grpc/` owns the gRPC-request predicate. `App` is a thin `http.Handler`: it holds the two sub-servers and the services, delegating `Start`/`Close` to them and fanning `NotifyShutdown`/`DrainWithContext`/`Close` out to the sub-servers. `App.Start(ctx)` returns a drain-func (matching `cluster.Service.Start`) — it starts the services (`pokeSvc.Start` → `clusterSvc.Start`, which starts beehive + watcher internally, → `cloudSvc.Start`, each returning its own stop func) and returns one `stop` that fans out to `clusterSvcStop(ctx)` → `cloudSvcStop(ctx)` → `pokeSvcStop(ctx)` (poke last, so its hub — the controllers' resync subscription — is closed only after cluster has drained; the left-to-right arg evaluation in the `errors.Join` enforces this). `App.Close` then only stops the gRPC transports and calls `clusterSvc.Close` (the poke broadcaster and cloud engine are already drained by `stop`); `clusterSvc.Close` owns the full watcher + beehive + cache teardown order internally.
- `graph/` — GraphQL: `schema.graphqls`, generated code, resolvers, and **`server.go`** — `graph.Server` (`NewServer(*Resolver)`), the gqlgen handler with the bearer-token plumbing, SSE shutdown lifecycle, and `NotifyShutdown`/`DrainWithContext` (see Shutdown below). The `Resolver`'s dependencies must be non-nil — tests wire fakes (e.g. a fake `auth.Service`); degraded behavior lives inside the services, not behind resolver nil-guards.
- `grpc/` — gRPC surface. `grpc/server.go`: `grpcserver.NewServer(authSvc, pokeSvc)` wraps a `*grpc.Server` (registering `AuthService` and `PokeService`; `AuthService.AuthStateWatch` is the lone server-streaming RPC and joins the `streams` WaitGroup so it drains at shutdown — `PokeService` is unary-only so it doesn't) with the `NotifyShutdown`/`DrainWithContext`/`Stop` lifecycle surface. `grpc/auth_server.go` implements `AuthService` over `auth.Service`: `StartLogin`/`Logout` (unary, nil-service → `Unavailable`) and `AuthStateWatch` (server-streaming, latest-value from `auth.Subscribe()`, nil-service → end immediately). `grpc/poke_server.go` implements `PokeService` over `*poke.Service`: one unary `Poke` (nil-service → `Unavailable`) that broadcasts `Poke(SourceHost)` — the host calls it on OS resume / network-on to resync long-lived connections. `grpc/authpb/` holds the committed protoc output for `proto/auth.proto`; `grpc/pokepb/` for `proto/poke.proto`. Regenerate all with `make proto` (or `go generate ./grpc/...`); never hand-edit `*.pb.go`. (Kube/cluster data is **not** a gRPC service — it lives only on the GraphQL surface: `clusters`/`cluster` queries, `clustersWatch` + `clusterCachesWatch` subscriptions, cluster mutations.) The predicate `IsGRPCRequest` lives in `grpc/server.go`; the composition root uses it to route the shared h2c socket.
- `internal/` — building blocks: `app` (composition root, above), `ipc` (binds the per-OS IPC endpoint — AF_UNIX socket / named pipe — with user-only access; `main.go` uses `ipc.Listen`/`DefaultSocketPath`/`Scheme`), `k8shelpers` (the kubeconfig watcher — `KubeConfigWatcher`, consumed by `internal/cluster`), `atomicjson` (crash-safe single-file JSON read/write), `logging`, `sqlitemigrate` (shared forward-only SQLite migration runner), `appdb` (owns the app-level `app.db` — its connection pool and single migration sequence — and hands the `*sql.DB` to consumers), **`poke`** (cross-subsystem resync broadcaster — see below), plus the **cluster** package under `internal/cluster/` (the Kubernetes/cluster subsystem behind `ClusterService` — see *Cluster subsystem* below), the **auth** packages under `internal/auth/` (the mostly-flat root `auth` package — `auth.Service`, the local-first identity layer — with the OAuth2/OIDC protocol layer carved into the `auth/oauth` sub-package), and the **cloud** packages under `internal/cloud/` (the root `cloud` package — `cloud.Service`, the cloud-synced settings feature that *depends on* `auth` — and its settings sub-packages; see *Auth / identity* and *Cloud settings sync* below).

## Cluster subsystem (`internal/cluster`)

The cluster subsystem is one flat package, `internal/cluster` (`package cluster`), fronted by **`ClusterService`** — the single boundary between the frontend and the cluster backend. Beehive (`github.com/amorey/beehive`) is the control plane: a SQLite-backed, level-triggered controller framework (a small operator runtime). The service owns its beehive store (at `<dataDir>/beehive.db`) and instance outright — beehive is cluster-only, so there's no reason for the composition root to hold it; if a non-cluster kind ever needs beehive, hoist the store/instance back up to `internal/app` and pass `*beehive.Beehive` into `cluster.New`. Beehive (**v0.22.0**) hosts four resource kinds in an **owner chain** — `Cluster → ClusterCache → ClusterCacheGVRDiscovery → ClusterCacheGVRSync` — so deleting a cluster cascades (beehive GC) down the whole subtree. Each `ClusterCache` carries a **`kstack.io/cache-files` finalizer** so its deletion (a UID-switch prune or a cluster cascade) blocks until the cache's sync children have drained and the controller has removed the on-disk `.db` file — the file can't be orphaned. A `Cluster` owns **zero or one** `ClusterCache` at steady state (none until its first successful probe; the cache for its current physical identity thereafter) — a physical-cluster migration to a new kube-system UID creates the new identity's cache and **deletes the superseded one** (so the two coexist only briefly during the hand-over). The children are enumerated via the owner edge (`Client.ListOwnedObjects`, the typed kind-scoped form), not by re-deriving a name. (There is no separate per-context intake kind: the kubeconfig importer reconciles contexts directly into `Cluster` objects, 1:1.)

The package holds (flat, by file): the **domain types** (`types.go`, `helpers.go` — the spec/status split, `ClusterID`, names, condition helpers, `ConnectionEligible`), the **beehive controllers** (`core_controller.go` = `ClusterCoreController`, with its liveness watch in `connection_sentinel.go`; `cache_controller.go` = `ClusterCacheController`; and the cache's sync subtree — `cache_gvr_discovery_controller.go` = `ClusterCacheGVRDiscoveryController`, `cache_gvr_sync_controller.go` = `ClusterCacheGVRSyncController`, and `cache_sync_workers.go`, which holds the worker registry and report-folding that controller runs on), the **kubeconfig importer** (`kubeconfig_importer.go` — the sole creator of `Cluster` objects), the **service boundary** (`service.go`), and the **cache's client policy** (`cache_client_config.go` + `cache_idle_timeout.go`). That last one is the per-cache budget every client built on a cache's behalf shares — a `flowcontrol` rate limiter (set as `RateLimiter`, **not** QPS/Burst: client-go builds a fresh token bucket per REST client when the field is nil, so a cache's ~300 clients would each get a private ceiling and bound nothing), the `kubesync.ListLimiter` its workers contend for, and an idle-read timeout that cancels a non-watch request making no progress for 2 minutes (so a wedged LIST can't hold a limiter slot forever). It is keyed per cache and handed to BOTH the per-kind sync workers and the discovery pass through `controllerRuntime.policies()`, which is the only reason it bounds anything; it lives in the root package because it composes the `ConnectionManager`'s config, which is a root concern. Two genuine deep modules are carved out as leaf sub-packages (the `auth/oauth` precedent), neither importing the root, grouped under `internal/cluster/cache/`: `internal/cluster/cache/store` (`package store` — the per-cluster SQLite cache `Manager`, which owns the cache's **reads** and lifecycle), `internal/cluster/cache/kubesync` (`package kubesync` — the list/watch sync machine, which owns neither end: the caller supplies where to pull from and where rows land), and its two specializations `internal/cluster/cache/eventsync` and `internal/cluster/cache/objectsync`, which own the **writes** to the events table and the objects table respectively. The `cache/` parent is a namespace directory only (no Go files); the controllers that drive these stay in the root `cluster` package (it's glue — coupled to the root's beehive kind types + condition/eligibility helpers, and registered by `service.go` — so moving it under `cache/` would cycle). All cluster tests are **white-box** (`package cluster`), matching the tree's white-box-by-default rule; shared fixtures (kubeconfig sources, a memory-backed beehive with the kinds registered, a no-op controller) live in `testutil_test.go`. They're an in-package `_test.go` file rather than a separate `testutil` package on purpose: a `package cluster` test importing a `testutil` that itself imports `cluster` would be an import cycle, and the `_test.go` suffix keeps the `testing`/`testify`/`sqlite` deps out of the production build.

**`ClusterService` (`service.go`) is the boundary.** `cluster.New(dataDir, kubeconfigPath, pokeSvc) (*Service, error)` builds the kubeconfig watcher (over `kubeconfigPath`), opens the beehive store + instance (at `<dataDir>/beehive.db`), builds the beehive clients (one per kind), constructs and **registers the four controllers** with beehive, and builds the importer and the per-cluster cache `store.Manager` (rooted at `<dataDir>/clusters/<ClusterID>/`, keyed by beehive ObjectIDs — see Per-cluster cache below); the returned `*Service` implements the `ClusterService` interface — the GraphQL-facing domain surface: `List`/`Get` (a Cluster alone — no cache join), `Watch`/`WatchCaches` (two **independent Kubernetes-style delta watches** — the Cluster kind and the ClusterCache kind, each folded out of beehive's per-kind `WatchList` — which hands back a snapshot plus the change stream strictly above it — into one delta stream: the snapshot replayed as `Added`, then per-object `Added`/`Modified`/`Deleted` (the shared `watchListChan` pump, which also collapses a deletion-pending object to `Deleted` and ends the stream on beehive's terminal `Failed` change); the ClusterCache stream is standalone and joined onto clusters **client-side**, so cache churn never re-emits a cluster), `WatchCacheSyncHealth` (each cache's folded sync verdict — see below), `CacheStats`, `SetEnabled`/`SetSyncEnabled`/`RetryConnection`/`ClearCache`/`Delete`. Every beehive detail (the store itself, names, the owner chain, the spec/status split, the delta-watch mapping) and the cache files live behind it; callers deal only in the domain `Cluster`/`ClusterCache`. `*Service` additionally owns the full control-plane lifecycle off the interface: `Start(ctx)` starts beehive, then the importer; the resync poke bus is **not** wired by the Service — the core and per-kind-sync controllers subscribe to it directly in their own beehive `Start` (see below). `Close(ctx)` tears down in dependency order — close the watcher + stop the importer, stop beehive (every controller — which unsubscribes from the poke bus) and then the sync workers, shut down the cache (safe only now the workers are gone), then close the beehive store. The composition root (`internal/app`) holds the concrete `*Service` (for `Start`/`Close`), hands it to `graph.Resolver` typed as the interface, and owns only the shared poke bus — the cluster-shutdown ordering invariant lives entirely inside `Service.Close`.

Adding a future cluster-creator (manual creation, kstack-cloud sync) means a new `ClusterSpecSource` *variant* (the discriminated union on `ClusterSpec.Source`) + a new importer peer writing `Cluster` objects with that variant + a sibling block in `ClusterStatusSource`, plus a per-variant credential-resolution case in `ClusterCoreController` (today it hard-codes the kubeconfig variant). All creators share the one `Cluster` kind; reintroduce a separate intake kind only if two sources must ever *dedup* into one `Cluster` (e.g. a kubeconfig context and a cloud record naming the same physical cluster) — until then the 1:1 importer→`Cluster` mapping is the simpler shape.

- **Kubeconfig watcher** (`internal/k8shelpers`, `k8shelpers.KubeConfigWatcher` — a self-contained, reusable building block in its own package, but the cluster service owns the *instance*: `cluster.New` constructs it from `kubeconfigPath` and `Service.Start`/`Close` drive its `Start`/`Close`) — fsnotify + 100ms debounce over the kubeconfig precedence paths, publishing full `*api.Config` snapshots on a latest-value hub (current-on-subscribe). The importer and `ClusterCoreController` consume it through the package-local `KubeConfigSource` interface (`Get`/`Subscribe`; tests substitute a static fake): the importer consumes the snapshot stream, the controller only reads `Get()` for credential resolution.
- **Domain types** (`types.go`, `helpers.go`) — `Cluster{ID, Generation, CreatedAt, DeletionRequestedAt, Spec, Status}` (a Cluster alone — its ClusterCache children are **not** joined in; they stream standalone via `WatchCaches` and are joined client-side. `DeletionRequestedAt` carries beehive's soft-delete tombstone under its own name, surfaced as-is — no rename at the domain boundary), keyed by a `ClusterID` that IS the beehive **ObjectID** (`type ClusterID = ObjectID`, an alias of the generic `cluster.ObjectID int64` identity type) — opaque, source-agnostic, and stable for the record's life (a departed kube-context is orphaned not deleted, so its id survives a return; the id changes only on an explicit Delete). The id is deliberately *not* the remote cluster's UID; cross-source dedup, if ever needed, is a read-side grouping on the probed `Server.UID`. The source's natural key (e.g. a kube-context name) lives only on the beehive **name** — an importer-internal reconcile/uniqueness key, never the identity: a kubeconfig Cluster is *created* with the name `kubeconfig/{context}` (so beehive's per-kind name-uniqueness rules out a duplicate for a context), but nothing reads it back by that name — lookups go through `Get(ctx, beehive.ObjectID(id))`. On the wire every object id is **one shared GraphQL scalar** (`scalar ObjectID`, bound to `cluster.ObjectID` in gqlgen.yml) carrying a decimal string (`"42"`) via `MarshalGQL`/`UnmarshalGQL` — so gqlgen hands the cluster resolvers an already-typed `cluster.ObjectID` (= `ClusterID`) argument, no per-resolver parsing. The single scalar + marshalling path is reused by every kind (`ClusterCacheID` is the second such alias, naming a ClusterCache's own ObjectID), instead of a per-kind scalar. The frontend codegen maps the scalar to `string` (`codegen.ts`), so the webview still sees an opaque string. (The on-disk cache is keyed by the same beehive ObjectIDs — see Per-cluster cache.) The GraphQL types bind **1:1 by name** to these (see gqlgen.yml), and the schema mirrors beehive's `Cluster → ClusterCache` owner chain: there is **no merge/projection type**. `ClusterSpec` is user/API-owned (`Name`, `Enabled`, `SyncEnabled` — declarative names, no `is` prefix; `Source` — the source *reference*, a discriminated union `ClusterSpecSource{Kubeconfig *ClusterSpecSourceKubeconfig{Context}}`, Manual/Cloud later). The matching *observation* (cluster/user names, presence, isDefault) is **not** in spec: the `ClusterCoreController` observes it live from the kubeconfig each reconcile and writes it to `ClusterStatus.Source` (the importer is creation-only — see below). The spec/status split of the source is named for the path: `ClusterSpecSource`/`ClusterSpecSourceKubeconfig` (the reference) vs `ClusterStatusSource`/`ClusterStatusSourceKubeconfig` (the observation). `Enabled` is the master "use this cluster in the app" switch — it gates `ConnectionEligible` and the webview's context picker / cluster lists; `SyncEnabled` is the sub-toggle gating the cache's syncs (`syncEligible = Enabled && SyncEnabled`). The spec carries **no trigger/counter fields**: a targeted retry (`RetryConnection`) forces an immediate out-of-band re-probe via the core controller's retry bus (`Reprobe`) — backoff-neutral, so a failed "check once more" retry neither resets the ladder to the fast 1s ramp nor advances the schedule; the automatic cadence is undisturbed by manual clicks (only a successful probe clears backoff) — and resync pokes drive an out-of-band reconcile — never through a spec write. The beehive **stored** types are `ClusterStatus` (Cluster kind: `Source`/`Server`/`Principal`/`LastConnectedAt` + `Connected`/`Healthy` conditions — both stored *and* served, no copy) and `ClusterCacheStatus` (ClusterCache kind: **empty** — the cache reports through its `Synced` condition alone, since it measures nothing itself; see the status-is-propagation rule below). Two live-but-unstored facts are **not** `Cluster` fields at all — a scheduling change and a recorded probe both fire no object `WatchList`, so folding them onto the list would force a re-emit on every backoff cycle. Instead each is its own per-cluster gauge/log watch: the **next-attempt countdown** streams via `clusterScheduleWatch` (beehive's `WatchSchedule`) and the **probe-outcome history** via the events surface (`clusterEvents`/`clusterEventsWatch`); see below.

**Connection-attempt history rides beehive's event log, exposed through a generic events surface — not a `Cluster` field.** The `ClusterCoreController` records each probe outcome via `ControllerClient.AddEvent` under the `ConnectionEventCategory` (`"connection"`) category — Normal/`Connected` on success, Warning/`ProbeFailed`|`ResolveFailed` on failure. beehive coalesces consecutive same-`(category, type, reason)` outcomes into one aggregated **run** (`Event{ID, Count, FirstAt, LastAt}`, message/detail sampled latest-wins), so a flapping cluster reads as a compact transition timeline and a stuck-down one as a single high-count run. Retention is beehive's: `beehive.New(..., WithEventRetention(maxEventRuns, 0))` bounds each `(object, category)` timeline to the newest `maxEventRuns` (20) runs, GC-swept.

**`WithStartupFullPass(true)` is declared per kind at `Register`** — on `Cluster` and `ClusterCache`, the two that own process-scoped state, plus `ClusterCacheGVRSync` (each object owns a running worker) and `ClusterCacheGVRDiscovery` — whose periodic re-discovery is a `RequeueAfter`, and those are in-memory, so without the startup pass a settled discovery object would never look at its cluster again after a restart. beehive's owed pass drains only work the *store* records as outstanding (an unconverged spec, an owed dependency wake), while these kinds own process-scoped state a restart invalidates but never wrote down — the core controller's live connections and liveness sentinels, the per-kind syncs' running workers. Without the startup pass a settled `Cluster` would come back unreconciled and therefore unconnected until something else woke it. There is deliberately **no periodic** full pass (`WithFullPassInterval` stays off): once running, each controller re-arms itself with `Result.RequeueAfter`, and the out-of-band triggers (kubeconfig change, resync poke, retry bus) cover the rest — a periodic pass over every object would buy nothing and cost the store a scan.

**Generic events surface (`clusterEvents` / `clusterEventsWatch`).** Rather than a bespoke per-timeline type, the event log is exposed generically, keyed by object id: `service.events(ctx, client, id, category, limit)` reads a run timeline (newest first) and `service.watchEvents(...)` streams it as bare runs (snapshot then live, conflated per run id — the consumer **upserts by `Event.ID`**), both kind-agnostic (any beehive kind client satisfies the small `eventClient` interface; `ListEvents` is object-id-only, so a single reader serves every kind). The Cluster-kind entrypoints `ClusterEvents`/`ClusterEventsWatch` sit on `ClusterService`, backing the GraphQL `clusterEvents(id, category, limit): [Event!]!` query and `clusterEventsWatch(id, category): Event!` subscription. The **ClusterCache kind** has the exact parallel — `ClusterCacheEvents`/`ClusterCacheEventsWatch` (same generic `events`/`watchEvents` over `s.cacheClient`, keyed by the cache's own `ClusterCacheID`), backing `clusterCacheEvents(id, category, limit)` / `clusterCacheEventsWatch(id, category)` — carrying the cache-sync history the cache controller records under category `"sync"`. The domain `Event{ID ObjectID, Category, Type beehive.EventType, Reason, Message, Count, FirstAt, LastAt}` binds 1:1 to the GraphQL `Event` (its run `id` rides the shared `ObjectID` scalar — no dedicated event-id scalar; `type` binds straight to `beehive.EventType`, the same external-enum pattern as `ConditionStatus`). The subscription streams **bare** `Event`s (mirroring beehive's `WatchEvents`), not an ADDED/MODIFIED delta — the client's upsert-by-id makes the distinction redundant. This is what keeps per-probe chatter **off** the status watch: a repeated identical failure records an event (bumping a run's count) without rewriting `ClusterStatus` (the core controller skips the status write when `ClusterStatusEqual`), so a failing cluster does not churn its status/conditions every probe, and the probe history is fetched/streamed **per cluster** by whatever view wants it (the panel subscribes only while a row's diagnostics are open) rather than riding the whole-list `clustersWatch`. The frontend derives the `ok` boolean as `type === 'Normal'`.

**The next-attempt countdown rides a schedule gauge, not the list.** `Service.Watch` forwards the Cluster kind's `WatchList` as a delta stream (`Added`/`Modified`/`Deleted` per cluster) — it holds no per-cluster event or schedule watchers, and cache changes are on the **separate** `WatchCaches` stream, not folded in. The "Next check" countdown is a beehive **schedule gauge**: `beehive.Client.WatchSchedule(id)` streams `Schedule{NextRequeueAt}` as a latest-value gauge (current-on-subscribe, then on every (re)schedule — backoff step, `RequeueAfter`, poke, out-of-band `Requeue`), none of which fire the object `WatchList`. The service maps it (`scheduleWatch` → domain `Schedule{NextRequeueAt *time.Time}`, zero → nil) behind `ClusterScheduleWatch(id)`, exposed as the GraphQL `clusterScheduleWatch(id): Schedule!` subscription. Like `Event`, the wire `Schedule` type is **generic** (kind-agnostic) even though the entrypoint is kind-scoped. This is the only correct source for the countdown: only the scheduler knows authoritatively when the next reconcile moves, and it moves for reasons (poke, spec edit, out-of-band requeue) that no status/event proxy fully captures. **The gauge also carries an in-flight probe flag (`Schedule.Probing`, GraphQL `probing: Boolean!`)** so the webview can show a definite "checking now" during a probe rather than inferring it from a momentarily-absent `NextRequeueAt`. `Probing` is *not* a scheduler fact — it is owned by the `ClusterCoreController`, which `setProbing(id, true)` at the top of the eligible branch of `converge` and clears it via `defer` when converge returns (success, failure, or resolve error alike; it already holds `writeMu` across the whole probe). The controller fans each transition out over a `gochan/broadcast` hub (`WatchProbe(ctx, id) <-chan bool`, current-on-subscribe: a subscriber opening mid-probe sees `true`); `ClusterScheduleWatch` **merges** that stream with the beehive schedule gauge (`mergeSchedule` — re-emits the combined latest as either side moves, drops a closed sub-source without ending the stream). Because both sub-sources are current-on-subscribe, the merged subscription drives *both* the "Next check" countdown and the "checking now" state from one channel. (`coreController` — the service's seam over `*ClusterCoreController` — gained `WatchProbe`; the service holds the concrete controller so the merge reaches it directly.) The frontend's detail row subscribes to it (and `clusterEventsWatch`) only while open, so an idle cluster costs nothing. The ClusterCache kind's **spec** carries `ServerUID` — the kube-system namespace UID of the physical cluster that cache mirrors (the identity a migration turns over; named to match the `ClusterStatus.Server.UID` it is compared against). The domain `ClusterCache{ID ClusterCacheID, ClusterID, ServerUID, Status}` is a standalone record on the `WatchCaches` stream — `ID`+`ClusterID` locate the on-disk file and let the client join the cache onto its cluster (`ClusterID` is resolved from beehive's owner edge — `GetOwner` — in `buildClusterCache`), `ServerUID` marks which physical identity it mirrors. **Active-ness is deliberately *not* a field**: the active cache is the one whose `ServerUID` matches the cluster's last-probed `Status.Server.UID`, but that parent UID changes with *no* cache event (a migration flips it on the Cluster), so a per-cache stream could never keep an `Enabled`/active flag fresh — only the client's live join against the current `clusterStatus.server.uid` is correct, so the derivation is the client's. **Conditions are beehive's, not ours.** `cluster.Condition` is a type alias for `beehive.Condition` (`{Type, Status, Reason, Message, Liveness, Unconfirmed, TransitionedAt, UpdatedAt}`), and conditions live as their own rows on the beehive object rather than inside a status blob — so they sit **beside** status on the domain records and on the wire (`Cluster.conditions`, `ClusterCache.conditions`), not under `status`. The store owns what the package used to hand-roll: the `TransitionedAt` stamp (kept unless `Status` changes), no-op suppression of an unchanged write, and the liveness downgrade. There is no `ObservedGeneration` per condition — beehive's object-level `ObservedGeneration` is the handshake, and every condition on one of our objects is written by one controller in one pass, so a per-condition copy would only duplicate it. gqlgen binds the GraphQL `Condition` straight to the beehive type, the same external-type pattern as `EventType`/`ConditionStatus`.

**Every condition we report is a `Liveness` condition** (`liveCondition` in `types.go` is the only constructor). `Connected`, `Healthy`, and `Synced` all describe process-scoped state — a live connection, a live API-server observation, a running sync worker — none of which survives a restart. Marking them liveness is what makes beehive serve a previous process's write as `Unknown` until this process re-confirms it, instead of a stale `True`; the downgrade is a read-time transform, so nothing is written at startup and `Reason` is preserved (which is why `syncWasRunning` can key on it across a restart). **A downgraded condition is flagged `Unconfirmed`**, and that flag is load-bearing on the wire: because the reason and the stamps survive the downgrade, they describe the *last known* status rather than the `Unknown` being served, so a consumer that reads them uncritically will assert state nobody has observed. The sync panel is the case — it must not render a pre-restart `SyncFailed` reason as a red "Error", nor a pre-restart `transitionedAt` as uptime (nor the absent-True as a definite "0m" outage); both fall back to the pending reading until the first reconcile re-confirms. The controllers themselves ignore the flag: they overwrite unconditionally, and `syncWasRunning` *wants* the pre-restart reason — a cache that was syncing when the process died really did stop. That we have **no** store-truth conditions is a fact about this domain, not an oversight: everything the cluster subsystem reports is an observation of live state.

**A pass writes its conditions once, inside a transaction with its status.** Each controller accumulates into a `conditionSet` (upsert by type) and writes the whole set with `SetConditions` inside `client.Within`, alongside either `UpdateStatus` or — when the status is unchanged — `SetObservedGeneration`. Both halves matter. The single transaction means a watcher never sees `Connected=True` beside a stale `Server`, nor half of a `Connected`/`Healthy` pair. The explicit handshake matters because **a condition write does not settle a generation**: it bumps `resource_version` (so watches and the dependency waker see it) but leaves `generation`/`observed_generation` alone, so a pass whose only output is a condition — the common case for `ClusterCache` and for a paused sync child, whose statuses are empty — would otherwise leave the object unsettled and re-enqueued by the owed pass forever.
- **ClusterCoreController** (`core_controller.go`) — the connection/health controller, and the **owner of the kubeconfig source observation** (it writes `status.Source` live; the importer writes only the spec source reference). Each reconcile: observe the kubeconfig into `status.Source` (a departed context keeps its last-known names, `IsPresent=false`) → eligibility gate (`connectionEligible`: kubeconfig-sourced, freshly-observed present, enabled, not deletion-requested) → resolve credentials → identity probe (ServerVersion, kube-system UID, SelfSubjectReview) → `/readyz` health check, folding observations into the `Connected`/`Healthy` conditions and refreshing `Server`/`Principal`/`LastConnectedAt` on success. A probe failure is **returned as an error** (after the status write lands) so beehive applies its own exponential backoff — base 1s, ×2, capped at 2m via `WithMaxRetryInterval` at registration — and resets it on the next success; a success returns the ~30s health cadence via `RequeueAfter`. Out-of-band reprobes bypass beehive's worker, so their failures don't disturb the scheduled backoff. `probe`/`check` default to the real network implementations; tests inject fakes. After a **successful probe** (so the kube-system UID is known) it ensures a `ClusterCache` child exists for that identity (`ensureClusterCache`, idempotent via the UID-keyed name's UNIQUE — concurrent reconciles can race the create; the child is created with the `kstack.io/cache-files` finalizer), then **prunes superseded caches** (`pruneSupersededCaches`: `ListOwnedObjects` the cluster's caches and request deletion of any whose `ServerUID` differs from the just-probed one). Both steps are **gated on a confirmed UID**, not eager: a never-probed cluster has no cache, and a transient disconnect (`Server.UID == nil`) never prunes — so a physical migration to a new UID creates the new identity's cache and deletes the old, leaving one cache per cluster. A create/prune error is non-fatal (logged; the next reconcile retries) so it doesn't lose the just-observed connection status. **Reconciles of one cluster serialize on that cluster's own lock and re-read the object fresh under it**: beehive status writes carry no resourceVersion guard, so without this an out-of-band reconcile holding a stale snapshot could clobber the status-owned observation. The lock is deliberately **per cluster**, not one shared mutex — two clusters' reconciles write different objects and every other piece of state `converge` touches is separately guarded (`connMgr`'s RWMutex, sentinels under `sentinelMu`, probing under `probeMu`), so distinct clusters reconcile **in parallel**. That matters most at startup, where beehive's startup pass and the kubeconfig watcher's first snapshot both enqueue every cluster at once: under one shared mutex a single unreachable cluster's dial timeout would delay every cluster queued behind it. The fan-out is bounded by `clusterProbeConcurrency` (8) in the two places that spend their time in the same probe — beehive's worker count for the Cluster kind (`WithConcurrency` at `Register`) and `reconcileAll`'s own pool. The per-cluster lock map is never reclaimed (bounded by kube-contexts ever seen, so tens), which avoids freeing a lock another goroutine is about to take. It drives three **out-of-band** triggers from a single background worker (`StartBackground`/`StopBackground`) that `select`s over all sources, each re-running `Reconcile` in-memory (a controller writes status, not spec): (1) the **in-process retry bus** (`Reprobe(id)` → buffered `retryCh`), whose producers are the **connection sentinel** (see below) and **`Service.RetryConnection`** (the user-initiated "retry now"), both re-probing one targeted cluster out-of-band — backoff-neutral, since an off-worker reprobe failure never reaches beehive's scheduled backoff (it neither resets nor advances the ladder); (2) the **resync poke bus**, which on a poke (OS resume / network-on) re-reconciles every cluster; and (3) the **kubeconfig watcher** (subscribed here), which on a kubeconfig change re-reconciles every cluster so presence/isDefault updates promptly and the resulting status write wakes each `ClusterCache` dependent. The core controller folds the poke + watcher buses into this combined worker instead of the shared `pokeSubscription` helper (which the per-kind sync controller uses via `StartPoke`/`StopPoke`); the `Service` sequences `StartBackground`/`StopBackground` around the beehive lifecycle. **Connection sentinel** (`connection_sentinel.go`): after a **successful probe** `converge` opens one long-lived liveness watch on the cluster's `kube-system` namespace (`ensureSentinel`, keyed by the connection-config fingerprint so a credential rotation restarts it; torn down by `stopSentinel` the moment the cluster goes ineligible / fails to probe). The controller reacts only to the **watch stream closing** — the earliest connection-loss signal — by firing one `Reprobe` and exiting; the re-probe re-confirms the connection and, on success, `converge` opens a fresh sentinel. A persistently-down cluster runs **no** sentinel (only beehive's backoff retries), so it never spins; a benign server-side watch timeout just triggers one idempotent re-probe. This makes fast connection-loss detection a property of the connection controller itself — **independent of whether sync is running** — which is why there is no sync → connection hook. The sentinel goroutines anchor to `StartBackground`'s context and are joined in `StopBackground`. **HTTP/2 keepalive:** the composition root calls `cluster.ConfigureKubeHTTP2Keepalive()` once at startup (`internal/app`), tightening client-go's HTTP/2 connection health check (the `HTTP2_READ_IDLE_TIMEOUT_SECONDS` / `HTTP2_PING_TIMEOUT_SECONDS` env vars apimachinery reads, set only when unset so an operator override wins) from the 30s/15s default to 10s/5s — so a silently-dropped API-server connection is torn down in ~15s instead of ~45s, which is what makes the sentinel's watch close (→ re-probe) promptly.
- **ClusterCacheController** (`cache_controller.go`) — decides whether one cache should sync and pushes that decision down; the workers themselves are two levels below it. It finds its parent Cluster via the **owner edge** (`client.GetOwner`), not by parsing the cache name, and declares a `DependsOn` edge on it. That edge matters for spec changes (`SyncEnabled` toggled) **and** for the parent's status writes, since eligibility's presence is read from the `ClusterCoreController`-written `status.Source` — beehive's `wakeDependents` fires on a status `Modified`, so the cache free-rides on the core controller's observation writes. It does **not** re-read the parent after declaring the edge: beehive closes that race on both sides of the call, because creating the edge stamps a durable reconcile-owed atomically with the edge, and once it exists the dependency watermark is taken from the cursor at object *load* rather than at completion, so a target that moved mid-pass stays owed. It syncs only the **active** cache: `syncEligible` (`ConnectionEligible && SyncEnabled`) **AND** this cache being the parent's current identity (`obj.Spec.ServerUID == parent.Status.Server.UID`) — a cache left behind by a migration is *paused* in the brief window before the core controller prunes it, so nothing writes the new cluster's data into a stale identity's file. **The sync anchor exists for the cache's whole life; a pause is a spec write, never a deletion.** This is the one place that evaluates the sync rule; it collapses the result into the anchor's `Spec.Enabled`, and the discovery controller relays it to every per-kind child, which never re-derive it. The anchor is ensured unconditionally (`ensureGVRDiscovery` → `ensureCacheSyncChild`: idempotent `GetOrCreate` + `Update` + `AddDependency`), and the `Update` is a no-op on a matching spec so a steady re-apply writes nothing and wakes nobody. On its **deletion** path (`DeletionRequestedAt != nil`, set by a prune or a cluster cascade) it waits for `ListOwned` to come back empty — requeuing on `childRetryInterval` — then deletes the on-disk cache file via the `store.Manager` and clears the `kstack.io/cache-files` finalizer so GC can collect the row. A file-delete error returns without clearing the finalizer, so the row lingers and the next reconcile retries; the file is never orphaned. That wait is what makes the barrier real: GC's cascade *marks* children for deletion but does not order their teardown, and each per-kind child carries `gvrSyncDrainFinalizer` cleared only once its worker has stopped — so "the children are gone" means "their workers have drained", and the `.db` is never deleted under a live writer. `SyncStopped` is the one sync event this layer records rather than folding up from a child, deliberately: `converge` collapses `syncEligible && active` into a single bit, so a child sees only "off" and could never tell a user-initiated pause from a migration hand-over. The guard is `syncSwitchedOff(clusterObj) && syncWasRunning(prev)` — the two spec switches alone (never eligibility, whose presence half goes false whenever a kubeconfig rewrite makes the context briefly vanish, which is not a pause), and only on a genuine running→stopped transition, read off the `Synced` condition the pass is about to overwrite so it survives a restart and can't re-fire on an already-paused cache. Its own `Synced` condition stays coarse (`Syncing`/`Paused`); the verdict a UI wants is the read-side rollup (`WatchCacheSyncHealth`).
- **ClusterCacheGVRDiscoveryController** (`cache_gvr_discovery_controller.go`) — the cache's sync anchor, one object per `ClusterCache`: it asks the cluster which GVRs it serves and converges the set of `ClusterCacheGVRSync` children onto that answer, one per syncable GVR. It resolves its inputs through the shared `resolveCacheChain` (`helpers.go`) and declares the same `DependsOn` edge on the `Cluster`, so a successful probe wakes a pass that was waiting; it gates the same three ways (`Spec.Enabled` false → `Discovered=False/Paused`, no credentials → `NoConnection`, else discover). **The child set is a projection of the API server's answer, so a pass is a set reconcile, not an append**: it creates what appeared, refreshes what remains (`Update` is a no-op on an unchanged spec), and *deletes* what the cluster no longer serves — deletion is right here where a pause is not, because an uninstalled CRD has no objects to mirror and no history worth keeping, whereas a pause is temporary and so travels as `Spec.Enabled` on children that stay put. Children are matched by their deterministic name (`gvrsync/{discoveryID}/{apiVersion}/{resource}`), so the comparison needs no per-child bookkeeping, and they are read back with the typed `Client.ListOwnedObjects` — one query for the whole set, not a `Get` per child. The spec compare before each `Update` is the controller's own: beehive suppresses the *write* on matching bytes, but a few hundred no-op calls are still a few hundred transactions, and the steady state is that they all match. **A partial answer never prunes**: an unavailable aggregated APIService fails only its own group — a per-group error on the legacy path, a `Stale`-freshness group-version in the aggregated document — and client-go surfaces either as `ErrGroupDiscoveryFailed` *alongside usable results*, so `discovery.IsGroupDiscoveryFailedError` splits "this group is gone" from "this group didn't answer" — a partial pass adds and refreshes only, and reports `Discovered=False/DiscoveryPartial`; a total failure (`DiscoveryFailed`) touches no child at all and hands the retry to beehive's backoff. The filter (`syncableGVRs`) drops subresources, anything not both `list`- and `watch`-able (e.g. `SubjectAccessReview`), and the non-canonical `events.k8s.io` spelling of Events — the same collection the core `v1` one serves, so keeping both would double-write it. `Discovered` is its own condition axis, distinct from `Synced`: a current kind list says nothing about whether the per-kind workers are caught up, and vice versa. It is the controller's *only* object write — the pass's gauges are kept in memory and sampled on read (`Stats`), per the status-is-propagation rule above. Discovery cannot be watched — the `APIGroupDiscoveryList` document carries no resourceVersion (its own godoc: no "replayable ordering among multiple apiservers"), so there is no position to resume from — and currency is therefore a poll: `RequeueAfter: gvrDiscoveryInterval` (5m, the worst-case lag before a new CRD gains a child) — which is why this kind takes `WithStartupFullPass(true)`; see the startup-pass rule above. Registered with `clusterProbeConcurrency` for the same reason the `Cluster` kind is: a pass is mostly one cluster's request, and a single worker would let one unresponsive API server delay every other cache's discovery. The request is bounded by copying the rest config with `gvrDiscoveryTimeout` rather than through the context, since client-go's discovery surface takes none. It writes no cache-store rows: each child registers its own `kind_catalog` entry when its worker starts and drops it when the child is deleted, so the catalog says exactly "what this cache holds" rather than "what the cluster advertised at the last pass". Events are no exception — their store registers `('v1','Event','events')` on start like every other kind's, which is what makes the trigger-maintained Event count reachable (`store.Kinds` is a `kind_catalog` LEFT JOIN, so a count with no catalog row beside it is invisible, and the dashboard's curated Events row shows none). Their row has no removal counterpart in practice: the kind is always served, so only the cache file going away ends it. Children are created **with the `gvrSyncDrainFinalizer`**, so a prune waits for the kind's worker to stop before the row is collected.
- **ClusterCacheGVRSyncController** (`cache_gvr_sync_controller.go`) — owns one `objectsync` worker per `ClusterCacheGVRSync` object, mirroring that kind's objects into the cache. The count is what shapes it: a cache has one of these **per served kind** — a hundred or more, Events among them. Three consequences. The steady state must write nothing, and does (the condition is unchanged so beehive suppresses it, and the status is empty), because a heartbeat that bumped `resource_version` would be a hundred parent wakes every 30s — `TestGVRSyncFoldsWorkerReports` pins it. It registers with `WithConcurrency(gvrSyncConcurrency)`, which unlike the `Cluster` kind's is about volume not latency: a startup pass has hundreds of objects to walk, each opening the cache and starting a worker. And the per-kind isolation is the point — a CRD whose watch is forbidden reports `Synced=False/Stale` on its own object and leaves every other kind syncing. Its owner climb is **one hop longer** than a direct child of the cache would be (this object → its `ClusterCacheGVRDiscovery` anchor → the `ClusterCache` → the `Cluster`), which is why `resolveCacheChain` takes an `ownerReader` rather than a controller client: the extra hop starts the shared climb from a plain kind client. **A worker's identity is its connection fingerprint AND its kind**, so it is rebuilt when either moves. The kind half matters because a child is named for its `(apiVersion, resource)` alone: a CRD deleted and recreated with the same plural but a different Kind or scope keeps the same child, which discovery respecifies in place — comparing only the fingerprint would leave the old worker writing rows under the obsolete Kind (the objects table is keyed by kind) and reporting against a stale generation. The rebuild also `Forget`s the superseded kind, since the child that owned those rows now describes something else and nothing else would ever collect them. Gating is the usual three ways (`Paused` / `NoConnection` / running), and a **pause keeps the kind's rows and catalog entry** so an unpause resumes from the saved position — only a deletion clears them. Deletion drains the worker behind `gvrSyncDrainFinalizer`, then calls `objectsync.Forget`, which is **best effort and deliberately outside the barrier**: the finalizer exists to prove the worker stopped, and blocking on the row cleanup would deadlock the common case where the whole cache file is being deleted anyway (it uses `Manager.Lookup`, never `Open`, for the same reason — re-opening a cache mid-teardown would re-materialize the file the cache controller is about to remove).
- **The worker machinery** (`cache_sync_workers.go`) — split out of `ClusterCacheGVRSyncController` because it is a distinct concern from the reconcile itself, and because the shape generalises to any future worker-owning kind. The `workerSet` registry and its **drain-before-forget** rule (a failed drain keeps the entry, which is what makes the deletion barrier real — a timed-out drain that forgot its worker would let the next reconcile clear the finalizer while the wedged goroutine still writes to a `.db` about to be deleted); the fact that a worker is registered with the set **before** `Start` — which is what decides which of two racing builders wins, the loser dropping the worker it built — and the matching latch in `kubesync.Worker.Stop`, so a stop arriving in that window makes the later `Start` a no-op instead of leaving a goroutine nobody holds a handle to; the **per-object lifecycle lock** held across a whole stop-then-start sequence — the reconcile takes it for its entire pass and the resync poke for each worker it bounces, because the gap between a stop and the start after it is a moment when the object legitimately has no worker, and a pause or deletion landing there would report itself done (a deletion clearing the drain finalizer that holds the cache file open) while the restart puts a worker back for an object that is paused or gone; the `syncSink` that guards an out-of-band report by entry-pointer identity and re-checks under the owner's `writeMu`; `syncedCondition` (report → `Synced`); and `recordSyncTransition`/`syncEvent` (report → the event log's start/complete vocabulary, recorded **only** on a change in the `(State, Cause)` pair). The noun is captured on the entry at worker start, so a Deployment sync's log reads "cached 12 deployments" and the Event sync's reads "cached 12 events" from one set of format strings.

- **Events are an ordinary synced kind.** They are discovered, reconciled and run by exactly the machinery every other kind uses, and diverge only in which `kubesync.Store` their worker writes to (`eventsync.NewStore` vs `objectsync.NewStore`, picked by `newLiveGVRWorker` — the one place that knows a kind can want a different store). That divergence is real and is why the store stays separate: its table has its own columns and FTS index, its retention is server-mirrored by the relist prune, it wakes a dedicated write broker, and the two api spellings normalise into one uid-keyed row. Two consequences fall out. The discovery filter drops the **non-canonical spelling** (`events.k8s.io/v1`) rather than Events themselves, because one collection served twice would get two workers fighting over the same uid-keyed rows. It keys that drop on the api group and plural (`isAltEventsKind`) — the same pair `isEventsKind` routes writes on, and deliberately not the Kind name, since "Event" is not reserved and a CRD named Event in somebody's own group is that user's kind. And the discovery controller **seeds the `v1/events` child before it does anything that can fail or wait** (`ensureEventsChild`, ahead of the pause gate and the credentials check) — events are the highest-value diagnostic data in the cache, and a pass has to reach the API server before it can report a kind, so on a slow or throttled cluster this is the difference between mirroring events and mirroring nothing. It lives there rather than in the cache controller because that controller owns the child set and prunes it; two owners writing one set would fight. The seed does a `GetOrCreate` **and** an `Update`: the first pass for a fresh cache usually runs before its cluster has connected, so it seeds the child disabled, and `GetOrCreate` never mutates — guarded by the same spec compare `syncChildren` uses, since the seed runs on every pass and the steady state is that the spec already matches. Both paths build the spec through one constructor (`eventsSyncSpec`), since a field they disagreed on would have each pass overwrite the other's.
- **The sync surface is granular, not rolled up — except for the one verdict a UI needs.** A cache's per-kind health rides `clusterCacheGVRSyncsWatch` (cache-scoped), but the row badge in the sync panel needs one reading per cache, and no single child's is it: ninety-nine healthy kinds beside one forbidden CRD is not a healthy cache. `WatchCacheSyncHealth` (→ `clusterCacheSyncHealthWatch`, unscoped, one record per cache) folds them read-side in **one process-wide fold** shared by every subscriber — dominated by the worst reason (SyncFailed > Stale > NoConnection > Syncing, with Paused the mildest reading — reached only when nothing ranked and nothing unobserved is left, and true of a PARTLY paused cache too, since a pause reaches a cache's hundred-plus children one at a time and the frames in between must not claim health), **naming the offending kinds as a sorted `unhealthyResources` list rather than a rendered phrase** (truncation is a layout decision, and the client keys its timeline subscription on the first offender — it must not parse that back out of prose), and rolling the freshness stamps up as *newest write* beside *oldest proof* (a cache is only as verified as its least-recently proven watch). A child whose condition a previous process wrote and this one hasn't re-confirmed (and one that hasn't reported at all yet) is counted but **not** treated as healthy: the verdict falls to `Unknown`/`Syncing` until every kind has been observed, ranked below a real failure. Healthy is a claim about every kind, so the absence of an observed fault is not the same as observed health — most visibly right after a restart, when beehive serves every liveness condition downgraded until its worker re-confirms it. **It is a read-side projection, not a stored condition** — the status-is-propagation rule cuts both ways: nothing in the object graph acts on this, so storing it would wake the cache and every watcher each time any of its hundred-plus children changed verdict. A cache whose discovery anchor is gone is **dropped** from the published map rather than recomputed (an anchor exists for a cache's whole life, so its absence means the cache was collected; folding zero records would instead republish a permanent "no kinds yet" `Unknown` for a cache that no longer exists, and a delete/recreate cycle would grow the snapshot without bound). There is no delete *frame* — the stream is a gauge keyed by `cacheID`, and the client drops a verdict when the cache itself leaves `clusterCachesWatch`, the stream that owns that lifecycle. It recomputes on watch frames **and on a 10s tick**, because the freshness stamps it folds live in controller memory and move with no frame behind them — the same trap `ClusterCache.stats` fell into — and only for the caches a frame actually dirtied, since at cold start each of a cache's hundred-plus kinds delivers its own.

  **One fold, many subscribers.** Every window computes the same verdict from the same two watches, so the fold is owned by the `Service` (started lazily on the first subscriber, ended by `stopSyncHealthFold` — which cancels AND joins it, since its two fleet-wide watch leases come back in its defers — before beehive stops) and its output goes to a `gochan/watch` latest-value hub; `WatchCacheSyncHealth` is a thin adapter that diffs the shared snapshot into the per-cache frames the wire speaks. Per subscriber that is a channel and a small map, rather than two more beehive watches, another ticker, another copy of every per-kind record and another `writeMu` acquisition per flush. **The hub carries the whole verdict map, not per-cache deltas**, and that is the load-bearing choice: the fold's input is large (a hundred-plus records per cache) but its output is tiny (one per cache), so publishing all of it is cheap — and it buys two properties a delta broadcast would have to reimplement. A new subscriber's first read returns the current value, which is exactly the "every cache, right now" a window needs on open (a settled cache emits nothing, so a window served only future frames would render "not reported yet" forever). And a slow subscriber coalesces onto the newest map instead of falling behind, which is correct for a gauge — where a dropped delta would be lost state.
- **One type per child kind, and one rollup for the fleet view.** A cache's sync is done by its per-kind children, and each child's health is served as its own record (`WatchGVRSyncs`, cache-scoped) rather than folded onto the cache; the discovery anchor's own axis is a separate record again (`WatchGVRDiscoveries`, unscoped — one per cache). Both map an object to a domain record shaped alike — `{ID, owner, Spec, Conditions}`, where `Spec` is the beehive kind's **own stored type served as-is** (no projection layer) and the owner id comes from the owner edge, so the client joins children onto caches exactly as it joins caches onto clusters. They are separate streams for the same reason the cache stream is separate from the cluster stream: a child rewrites far more often than its cache changes, and folding it in would re-emit the cache that often. They are not merged with **each other** either — they answer different questions (`Synced`: is this kind's mirror current? vs `Discovered`: is the list of kinds to sync current?) on different cadences.

  **Status is a propagation channel, not a place to keep gauges.** A status write bumps `resource_version`, which wakes every dependent and pushes a frame to every watcher — so status is for state a *dependent* must react to. A measurement only a UI reads does not belong there however durable it is: storing it makes every pass wake the parent to propagate a number no controller consumes. **All three cache-side kinds follow it**: `ClusterCacheStatus` is empty too — the cache measures nothing itself, and the rollup a UI wants is served read-side (see below) rather than stored, because no *controller* acts on it either. `ClusterCacheGVRDiscoveryStatus` and `ClusterCacheGVRSyncStatus` are **empty structs**, and their measurements — each worker's `lastUpdateAt`/`lastLiveAt`, the discovery pass's `lastDiscoveryAt`/`resourceCount` — live in their controllers' memory, served on request through `Service.GVRSyncStats` / `GVRDiscoveryStats` and resolved onto each GraphQL record as `stats` (a resolver field, the `ClusterCache.stats` shape — metrics-server to the API server's stored objects). Two things follow. A steady report now writes **nothing at all**: the condition is unchanged so beehive suppresses it, and there is no status left to rewrite, so a settled child stops bumping its version — a worker's ~30s heartbeat and the discovery pass's interval both stop waking the parent cache (`TestGVRSyncFoldsWorkerReports` and `TestGVRDiscoverySteadyPassWritesNothing` pin the resource_version). And the gauges are honestly absent until this process measures them: for a sync child that pairs exactly with its `Synced` condition being liveness-downgraded after a restart (a consumer that must not render a pre-restart `Watching` must not render a pre-restart stamp either); for discovery the kind list it describes is durable, but *when it was confirmed* is an observation nobody here has made. What stays on each object is its **condition**, which is the part a dependent could legitimately act on.

  **A gauge needs a stream, not a field on a record whose write cadence is unrelated.** The corollary of the rule above: a *resolver field* on an object is only as fresh as that object's watch frames, and a settled object emits none. A cache's contents are the case — a live measurement, but served as a `ClusterCache` field a consumer would see whatever the cache held **at subscribe time** (during a cold sync, a small early fraction of what lands seconds later) and never a change. So they ride `clusterCacheStatsWatch(id, cacheID)`, a `cacheGaugeWatch` over the store's write broker: current on subscribe, then a fresh value **only when it changes** (the dedupe is what makes a per-write gauge affordable), and zeroed stats when the cache closes. `cacheGaugeWatch` and `cacheDeltaWatch` share `cacheWatchLoop`, which owns the WatchDB lifecycle rebind + the coalescing debounce; they differ only in what they do on each fire — diff a keyed snapshot, or dedupe a single value. **The rule: if a number is measured rather than stored, it rides a stream keyed to what changes it, never a field on an object whose write cadence is unrelated.** And a consumer subscribes to what it actually reads: the webview's always-mounted registry (`src/lib/clusters.tsx`) joins in only the sync-health rollup, because it drives every row's status column, while `clusterCacheGVRDiscoveriesWatch` and the cache-scoped per-kind watch are subscribed inside the sync dialog's expanded row — their only reader. **The per-GVR children are their own kind on their own cache-scoped surface** — one per synced kind rather than one per cache, carrying their own identity (apiVersion/resource/scope), so they get their own domain + GraphQL type and a **cache-scoped** watch (`WatchGVRSyncs(cacheID)` → `clusterCacheGVRSyncsWatch(cacheID)`), unlike the unscoped streams (an unscoped stream of ~100 records per cache is a firehose the always-mounted cluster provider must not carry; the discovery watch is unscoped precisely because it is one per cache). The scoping is done on the **owner edge**, since beehive's WatchList is per-kind: the cache's discovery anchor has a deterministic name, so its id is one lookup, and each object's owner arrives eager-loaded, making the filter a field read rather than a query per object. A cache whose discovery has never run streams nothing (it owns no records yet) rather than erroring. Their per-kind freshness rides `ClusterCacheGVRSyncStats` on the same `stats` resolver pattern as the other two children. Where two children's served spec/status shapes coincide, point both GraphQL types at one Go model in `gqlgen.yml` — a binding decision, not a reason to merge kinds on the wire. The child's **event timeline** is served the same way: `ClusterCacheGVRSyncEvents`/`ClusterCacheGVRSyncEventsWatch` are the generic events surface keyed by one kind's record id, which is where the sync-transition history actually lives (`recordSyncTransition` writes to the child, not its cache — the cache's timeline carries only what the cache itself records, e.g. `SyncStopped`).
- **Kubeconfig importer** (`kubeconfig_importer.go`) — the kubeconfig-sourced creator and **sole creator of `Cluster` objects**, **creation-only**: it consumes watcher snapshots and, for every context not already referenced by a (non-deleting) `Cluster`, creates one with the deterministic name `kubeconfig/{context}` (the context's natural key), writing only the `Source` reference. The deterministic name means beehive's per-kind name-uniqueness rules out a duplicate even under a concurrent create. It never updates, orphans, or deletes — a departed context is orphaned by the `ClusterCoreController` flipping `status.Source.Kubeconfig.IsPresent=false`, and a returning context reuses its never-deleted `Cluster` (the importer finds it by context and skips re-creation). An already-tracked snapshot writes nothing. A pure beehive writer — it doesn't know `ClusterCoreController` exists; its `Start`/`Stop` are owned by `Service`. (Today it enumerates via `List()` + a context match; a future `cloud/` source would scope by name prefix — deferred until a second source exists.)
- **Per-cluster cache** (`internal/cluster/cache/store`) — one SQLite file per cache incarnation at `<dataDir>/clusters/<ClusterID>/<ClusterCacheObjID>.db`, addressed by a `store.CacheRef{ClusterID, CacheID int64}` of the parent `Cluster` and `ClusterCache` **beehive ObjectIDs** (the ids are `AUTOINCREMENT`, so a delete+recreate yields a fresh, never-reused file with no finalize-vs-recreate race). Pure-Go modernc driver, WAL; single-conn writer pool + 4-conn reader pool, owned by a `Manager` (`Open(ctx, CacheRef)`/`Lookup(cacheID)`/`WatchDB(cacheID)` (a latest-value stream of a CacheID's open handle across its lifecycle — current-on-subscribe (nil when not open), then a fresh value on open/close/replace; long-lived readers like `ClusterDataKindsWatch` use it to bind to a cache that opens *after* they subscribe or rebind when it's swapped, instead of binding once to `Lookup`)/`CacheBytes(CacheRef)` (stat-only, works closed)/`ResourceStats`/`Kinds` (the discovered `kind_catalog` rows, backing `ClusterDataKinds`)/`Events(ctx, limit)` (the newest cached events, ordered by `last_seen DESC`, flattening the involved-object identity — backs `ClusterDataEventsWatch`)/`Objects(ctx, apiVersion, resource)` (one kind's cached objects — the universal-identity `ObjectRow` projection, `resource`→`kind` translated via a `kind_catalog` subquery, ordered by `(namespace, name)`; backs `ClusterDataObjectsWatch`)/`DeleteCacheFiles(ctx, CacheRef)` (also reaps the now-empty per-cluster dir)/`Shutdown`). It also owns the two write helpers its own tables define, shared by both sync stores rather than reimplemented per specialization: `ResumeCookie` (one collection's list/watch position — the `cluster_meta` `<apiVersion>/<Kind>.last_list_rv`/`.last_list_at` pair, with `Get`/`Persist`/`Advance`/`Delete` over an `Execer` so a cookie write rides either the writer directly or a relist's transaction) and `EnsureKindCatalog` (the `kind_catalog` upsert every worker runs at start). Each `ClusterDB` carries **two independent coalescing write-notify brokers** (one `notifyBroker` type, reused): `ObjectsSubscribe`/`ObjectsNotify` for object writes (drives the kind-catalog and objects watches — kinds are a read projection of object writes) and `EventsSubscribe`/`EventsNotify` for event writes (drives the events watch) — kept separate so an event burst never wakes the object-write re-reads. The object-write broker is additionally **resource-routed**: subscribers can register keyless (`ObjectsSubscribe`, wakes on any write — the kind-catalog watch) or keyed to one `(apiVersion, resource)` (`ObjectsSubscribeResource` — a per-kind objects watch), and writers ping either keyless (`ObjectsNotify`, a broadcast — a catalog registration, which announces a kind before any object of it exists) or keyed (`ObjectsNotifyResource(apiVersion, resource)`, every `objectsync` write, from the worker's own kind). A keyed notify wakes the matching-key subscribers **plus** every keyless subscriber (so the catalog watch still wakes on a new kind's first object), leaving other-resource objects watches untouched — so an unrelated resource's write costs a per-kind objects watch no re-read (the SQL + diff that a flat broadcast wasted). The routing key is the **plural resource, not the Kind**, deliberately: that's the identity a `ClusterDataObjectsWatch` is opened on, and it's stable across a CRD remap — a CRD deleted and recreated with the same `(apiVersion, resource)` but a different Kind keeps the key, so the subscription tracks the replacement driver's writes instead of going stale against the dead Kind. The events broker uses only the keyless forms (one consumer, no routing). The service resolves the **active** cache's `CacheRef` from a domain `ClusterID` (`cacheRef` helper): the `ClusterID` *is* the parent Cluster's ObjectID (the directory), and the file id is the `ClusterCache` for the cluster's currently-connected identity — found by reading the parent's `Status.Server.UID` and looking up the name `{ClusterID}/{serverUID}` (no `caches/` prefix: ClusterCache is its own beehive kind, so its names already sit in a disjoint namespace). `newCacheRef(clusterObjID, cacheObjID)` is the one `beehive.ObjectID→int64` conversion point (keeps the leaf `store` beehive-free). The live-stats resolver instead builds the `CacheRef` straight from the domain `ClusterCache{ClusterID, ID}` it already holds, so per-cache stats need no name lookup. Open runs an integrity check (corrupt → quarantined as `.corrupt-<stamp>`), migrations (its own embedded sequence — agent-optimized schema: universal `objects` + `owner_refs`/`labels`/`status_history`/`events`(+FTS)/`kind_catalog`/`kind_counts` (per-kind object counts kept exact by triggers on `objects`, so the dashboard nav's counts read O(kinds) instead of a grouped scan)/`cluster_meta`; `raw_json` zlib-compressed, Secrets redacted before persist), and a per-cluster janitor (status-history TTL sweeps + incremental vacuum — events are **not** janitor-managed; their retention is server-mirrored by the Event sync's relist prune). The cache never owns syncing — the workers that write into it belong to the cache's sync children.
- **The sync machine** (`internal/cluster/cache/kubesync`) — mirrors one Kubernetes collection into one local table for as long as it runs, and is deliberately ignorant of *which* collection. The caller supplies a `Source` (list/watch **plus a metadata-only list and a single-object get**, already scoped to its GVR — built by `kubesync.NewDynamicSource(cfg, gvr)` over the dynamic + metadata clients) and a `Store` (`ResumeRV`/`Count`/`ApplyChange`/`PersistRV`/`BeginReplace`/`EnsureCatalog`, plus the **optional `MetadataDiffStore`** — `SnapshotRVs`/`DeleteByUIDs`/`ApplyDiff`/`ClearRV` (the last two exist so the diff pass keeps the full LIST's invariant that *a cookie means a completed pass*: its objects arrive by GET in arbitrary order carrying their own resourceVersions, so a per-object cookie advance could leave the position ahead of changes the pass never applied) — which a store implements to opt into the diff resync below; `objectsync` does, `eventsync` deliberately doesn't, having no per-object resourceVersion), and this package owns everything between them: the resume/full-list state machine (`driver.go`), the **resync strategy choice** (`resync`: where the store can report what it holds and the cache is warm, it lists identities only (**paginated**, one page resident at a time like the full LIST), fetches bodies for just the objects whose resourceVersion moved, and deletes the vanished in **one batched `DeleteByUIDs`** (they land on the writer connection the whole cache shares, so per-object commits would queue every other kind's worker behind them) — on a quiet cluster the 30m re-list then costs one small response and no body fetches, instead of re-downloading the whole collection; it falls back to the paginated full LIST for a cold cache, a non-participating store, a server serving no metadata endpoint, or a delta past `defaultDiffThreshold`, where N round trips lose to one LIST), the error budget, the graded liveness proofs, the **LIST-phase concurrency bound** (`WithListLimiter` — a counting semaphore held across the list-heavy work and released before the indefinite watch, so one cache's hundred-plus workers don't all decode a page at once; the caller shares one limiter across the set that should compete — here, one cache's kinds — which is why it's the package's one production Option), and the `Status` reports a controller folds into conditions. Its `Status` counts items, not events or objects — each controller names the unit in the message it renders. **`Store.ApplyChange` advances the resume cookie itself**, in the same transaction as the row: the driver deliberately does not follow it with a `PersistRV`, because that doubles the writer-lock acquisitions on the hottest path in the system and opens a window where the row is durable behind a cookie that still points before it. `PersistRV` remains for the bookmark path, where the server proves currency with nothing to write. **Two packages specialize it**, differing only in their Source and Store, because the sync itself is one problem: `eventsync` and `objectsync` below.
- **Events write path** (`internal/cluster/cache/eventsync`) — a `kubesync.Store` and nothing more: `NewStore(cdb)`, composed with a source into a worker by `newLiveGVRWorker` like every other kind's. Events are synced by the same controller, the same worker and the same state machine; what differs is only where the rows land, and that difference is real — the events table has its own columns (involved-object identity, first/last seen, count) and an FTS index, its retention is server-mirrored by the relist prune rather than the janitor, it wakes a dedicated write broker so an event burst can't drive the object watches, and the two api spellings the server serves events under normalise into one uid-keyed row (which is also why the discovery filter keeps only the canonical `v1` one — mirroring both would double-count every event).

  The design is **watch-for-latency, poll-for-correctness**: the watch path makes the steady state cheap and is allowed to be lossy, while pull-based backstops guarantee correctness, so known edge cases (a dropped delta, a stale resume cookie) self-heal within one interval instead of being closed by exact, stateful edge-handling. A run **resumes** from the persisted resourceVersion cookie (`cluster_meta`, keys `v1/Event.last_list_rv` + `.last_list_at`) via a RetryWatcher — unlike a client-go Reflector, which can't be seeded and so re-lists every body on every wake. With no cookie (or after a 410) it falls back to a **paginated full LIST that prunes**: each page lands in its own transaction (bounding memory to one page) stamping `updated_at`, `Commit` reconciles the table by **mark and sweep** (one `DELETE` of the rows still below the session's mark — the same shape `objectsync` uses, since a keep-set of every uid would defeat the point of paginating and a per-stale-row delete would hold the cache's single writer across thousands of statements; the mark is one millisecond *past* the session start so a row written in the same tick can't masquerade as one this pass wrote), and a continue-token expiry restarts the pass from the top (bounded by `maxListRestarts`, then `errListRestartBudget` rather than one unpaginated LIST that could OOM). Pruning is what makes retention **server-mirrored**: an event the api server has already GC'd is dropped, so the cache reflects whatever `--event-ttl` the cluster enforces, and the janitor manages events not at all. **The cookie means "a full LIST completed on disk":** the first `WritePage` durably deletes it in the same transaction as the first rows and only `Commit` rewrites it, so partial rows and a cookie that would resume past them can never coexist; clearing on the first *write* rather than at `BeginReplace` means a pass that fails before writing anything leaves the previous snapshot's cookie intact and still resumes cheaply. A **periodic jittered re-list** (`defaultResyncPeriod`, 30m, jittered off the cache id so many clusters don't re-list in lockstep) is the backstop under all of it: a watch alive that long ends itself so the run re-lists.

  **Liveness and the error budget** decide what the user is told. **Proofs are graded, not collapsed into one "last alive" time** — the driver keeps three stamps (`liveness`): `lastWriteAt` (data landed in the cache: an applied delta, or a LIST that wrote rows), `lastProofAt` (the last strong proof of either kind — a write, a **bookmark**, or a LIST that found nothing new; a write stamps both, so this is always the freshness), and `firstConnectAt` (a watch established). RetryWatcher swallows bookmarks, so the driver taps the underlying watch ahead of it via `watch.Filter`; bookmarks also advance the cookie, but only once every delta forwarded before them has applied, and only while the tap's **watch epoch** is still current, so a straggler can't resurrect a cookie a concurrent LIST just deleted. Only the two **strong** proofs (write/proof) count as freshness; a connect is deliberately weak. That split closes a real blind spot: a watch that *accepts* the connection and then errors re-establishes every cycle (RetryWatcher retries a 5xx internally, without ever ending the phase or reaching the error budget), so if a bare connect could refresh freshness such a loop would report `Watching` forever while the cache received nothing. Instead a connect only opens a no-proof **episode** (`firstConnectAt`, which later connects within the episode don't move and any strong proof clears), so the stale clock runs from the *first* connect of the episode and a watch that establishes but never streams — one dead connection or a reconnect loop alike — ages into `StateStale` with cause `CauseWatchNotStreaming`. Nothing is stamped on merely entering a watch phase, so a cluster that can LIST but never WATCH can't refresh its way to looking healthy. Each phase bounds the wait for the watch to *connect* (`defaultEstablishTimeout`, 30s) because RetryWatcher retries retriable errors internally without ever closing its channel — without it a never-connecting watch would block forever, never spending its budget. Consecutive failures charge a per-worker **error budget** — a failed LIST, or a watch phase that carried nothing (no delta, no bookmark). **Establishing is not itself credit**: a watch the server accepts and then ends without streaming re-establishes on every pass, so crediting the open would refill the budget forever and the sync would re-LIST the whole collection every backoff step for the life of the process; the phase's `established` flag only picks the cause it reports (`CauseWatchNotStreaming` vs `CauseWatchFailed`). at `defaultStuckThreshold` the worker is marked stuck, drops to a slow retry cadence (`defaultStuckRetryInterval`, 3m) so a broken sync stops hammering the API server, and reports immediately. A `livenessMonitor` tick (30s) then reports `StateStale` with a **cause** — `CauseListFailed` / `CauseWatchFailed` / `CauseWatchStalled` (a stream that was live and went quiet) / `CauseWatchNotStreaming` (connected since the last proof but nothing ever streamed over it) — which the controller renders into an actionable message ("the events watch cannot be established") rather than a bare "not receiving updates"; the same tick doubles as the freshness heartbeat that keeps the stamps current.

  **Reporting.** The worker reports coarse state through its `Sink` (`StateSyncing` → `StateWatching` → `StateErrored`/`StateStale`), and the controller folds each report into the object's `Synced` condition **and** its beehive event timeline (category `SyncEventCategory` = `"sync"`). The condition names the current state; the event log speaks a transition vocabulary in start/complete pairs split on `ColdStart` — `SyncStart`→`SyncComplete` cold, `ResyncStart`→`ResyncComplete` warm, plus `SyncDegraded` / `SyncStale`. Each report carries **two** stamps, `LastUpdateAt` (writes only — the one a "last update received" line may honestly show) and `LastLiveAt` (the strong proofs — what staleness is judged on); the controller carries each forward when a report doesn't advance it, since a quiet cluster's reports carry no `LastUpdateAt` for hours. Events are recorded **only on a change in the reported `(State, Cause)` pair**, so the 30s heartbeat refreshes the stamps without growing a steady run into a meaningless "Watching ×27", and a recovery out of Stale reads as "watch recovered" rather than a second bogus "initial sync complete". `Status.CaughtUpIn` is zero on a monitor re-report, which is what distinguishes a heartbeat from a real catch-up.

  **Per-kind object sync** (`internal/cluster/cache/objectsync`) — the other kubesync store, one per served kind. It supplies the `Store` alone (plus `Kind`, the identity a caller addresses a collection by); the source is `kubesync.NewDynamicSource` over that kind's GVR. The store is that kind's slice of the cache's **shared** `objects` table, which is the whole difference from the events store: the events table has one owner, so every statement here is instead kind-scoped — the relist prunes only this kind's rows, and the resume cookie is keyed `<apiVersion>/<Kind>.last_list_rv` in the same `cluster_meta` namespace. **The relist reconciles by mark-and-sweep**, not by remembering what it saw: every page stamps `updated_at`, and `Commit` deletes this kind's rows still below the session's mark, in three subquery statements with no read-back. A keep-set of every uid in the collection would defeat the point of paginating, and a per-stale-row delete would be three statements each. The mark is one millisecond *past* the session start, because `updated_at` has millisecond resolution and a row written in the same tick would otherwise masquerade as one this pass wrote (`TestReplacePrunesRowsWrittenInTheSameMillisecond` pins it, against a frozen clock — the real clock decides that case by coin flip). `Count` reads the trigger-maintained `kind_counts` aggregate rather than counting rows, since it runs at every worker start and a cache warm-resuming its hundred kinds would otherwise scan the shared table a hundred times. A write lands the object, rewrites its `owner_refs` + `labels` edges, appends to `status_history` when the object's status **summary changed** (transitions only — a relist rewrites every row whether or not anything moved, so an unconditional insert would bury the real changes under a copy of the collection every resync period), and advances the resume cookie in **one transaction** (each edge table costs at most two statements — one `DELETE`, one multi-row `INSERT` — never one per label) (delete-then-insert, so a dropped label or ownerReference actually disappears rather than lingering and matching a selector the object no longer satisfies), and pings the write broker **resource-keyed**, so an unrelated kind's objects watch never re-reads. Two things happen to the body before it is stored: `metadata.managedFields` and the kubectl last-applied annotation are **stripped** (roughly half the bytes, and nothing reads them — which is what lets `ClusterDataObject` serve `raw_json` verbatim), and a **Secret's values are redacted** while its keys are kept (the cache is a plaintext file on the user's machine; the check reads the *body's* own kind, not the worker's configured one, so it can't be bypassed by how the collection was addressed). Each worker also owns its kind's `kind_catalog` row: `New` upserts it before the first object lands (it is what makes the kind readable at all — `store.Objects` resolves the plural resource back to the Kind through it — and what puts the kind in the dashboard nav), and `Forget` drops the kind's rows, edges, catalog entry and cookie together. `is_crd` is decided from the api group (core, the legacy unsuffixed groups, and `*.k8s.io` are built-ins; anything else is somebody's own domain) because discovery doesn't say and asking would cost a request per kind — a display nuance if wrong, not a correctness one. The **materialized status columns** (`status_summary`/`ready_count`/`total_count`/`restart_count`/`host`) are written here too, by the one piece of kind-specific code in the write path (`status.go`): a per-kind reading for the built-ins, and the conventional `.status.conditions` form as the fallback that covers most CRDs. They are **not** what the dashboard renders — the frontend derives its cells client-side from the body, which is the whole point of serving `rawJSON` verbatim — they exist to make the cache *queryable in SQL* ("which pods are not ready") without unpacking a blob per row. Every column is nullable: a kind with no meaningful reading stores NULL rather than a zero that would read as "none ready", and being wrong here is a query nuance, never a correctness problem.

The GraphQL `Cluster` mirrors beehive's owner chain (the schema **is** the domain shape — see gqlgen.yml's bindings, every GraphQL type pointing at the identically-named `internal/cluster` type, no wrapper): `spec`/`status` bind directly to `cluster.ClusterSpec`/`cluster.ClusterStatus` (the stored Cluster-kind status, served as-is). The `Cluster` type has **no** `caches`/`activeCache` fields — a `ClusterCache` is its own top-level entity, streamed via `clusterCachesWatch` and bound to `cluster.ClusterCache`, carrying its identity (`id`, `clusterID`, `serverUid`), the ClusterCache kind's conditions, plus live on-disk `stats` (a **resolver** on `ClusterCache`, read for `exists` — whether a cache file is on disk at all). **Its contents are NOT read from there**: see the gauge rule below. The client joins caches onto clusters by `clusterID` and treats the cache whose `serverUid` matches the cluster's `status.server.uid` as the active one. `ClusterSpecSource`/`ClusterSpecSourceKubeconfig` (spec, on the `ClusterSpec.Source` field — 1:1 autobind, no gqlgen `fieldName` override) and `ClusterStatusSource`/`ClusterStatusSourceKubeconfig` (status) bind directly, so the source union is on the wire as nested nullable objects. **The conditions go on the wire as-is**: `Cluster.conditions` and `ClusterCache.conditions` — beside `status`, not inside it, since beehive stores them as object rows — bind straight to `beehive.Condition`, and the webview derives display state from type/status/reason. There is no projection layer, so the `liveness` flag and the `transitionedAt`/`updatedAt` stamps reach the client verbatim; the panel's connection-uptime line reads `transitionedAt`. `ClusterCacheStats`/`ClusterCacheResourceStats` bind to `cluster.ClusterCacheStats`/`cluster.ClusterCacheResourceStats`. **Every cluster resolver delegates to `r.ClusterSvc` (`cluster.ClusterService`)** — they are one-liners: `clusters`/`cluster(id)` → `List()`/`Get()`; `clustersWatch` → `Watch()` and `clusterCachesWatch` → `WatchCaches()` (the two independent delta watches — an `Added` snapshot then per-object `Added`/`Modified`/`Deleted`, each adapted value→pointer through `ptrStream`, the stream counterpart of `ptrSlice` that nearly every subscription resolver uses); a cache's `stats` → `CacheStats(clusterID, cacheID)` (per-cache); `clusterDataKinds(id, cacheID)` → `ClusterDataKinds(clusterID, cacheID)` (one ClusterCache's discovered kind catalog — apiVersion/kind/resource/scope/isCRD, plus a per-kind `count` (a point LEFT JOIN of `kind_catalog` against the trigger-maintained `kind_counts` aggregate — so an advertised-but-empty kind counts 0 and the read is O(kinds), never a scan of `objects`) that backs the object counts in the dashboard nav — read on demand from that cache's `kind_catalog`, **per-cache like `CacheStats`**: keyed by parent cluster id + the cache id (typically the active one), so a cache/identity swap under the same cluster reads the *new* cache's catalog and lets the webview reject stale results by cache id; empty when that cache's db isn't open (never-synced / paused), since only a running sync populates + holds it open) and its live counterpart `clusterDataKindsWatch(id, cacheID)` → `ClusterDataKindsWatch(clusterID, cacheID)` (**the dashboard nav's real-time source** — the same per-cache catalog as a Kubernetes-style delta watch: an `Added` burst on subscribe, then `Added`/`Modified`/`Deleted` per kind, each change carrying its cache's `cacheID` as provenance (so the webview can reject a late frame from a superseded cache after a cache/context switch rather than inferring provenance from render state). The service subscribes to **both** store brokers (`catalogSubscribe`) — the catalog spans both tables, since every synced kind's count comes from the objects triggers and the Event kind's from the events triggers, so following only the object-write broker froze the Events badge on an event-busy, object-quiet cluster; the brokers still stay separate for the *expensive* re-reads, which is the per-kind objects watch — and, on each write ping (debounced by `dataKindsDebounce` — a short trailing throttle so a high-churn cluster can't drive a re-read + emit per object event), re-reads `Kinds` and diffs it against the last snapshot it emitted, keyed by `apiVersion`+`resource`; since `count` tracks the trigger-maintained `kind_counts` aggregate (no object scan), an object write bumps the counter and re-emits its kind as `Modified`, so the frontend's kinds *and* counts stay live. The catalog's own writers ping too: an `objectsync` worker's `EnsureCatalog` on start and its `Forget` on deletion both call `cdb.ObjectsNotify()`, so a CRD installed or uninstalled between runs surfaces as an Add/Delete without waiting for an unrelated object write to ping. The stream **follows the cache db across its lifecycle** via the store `Manager.WatchDB(cacheID)` (a latest-value handle stream — current-on-subscribe, then a fresh value on open/close/replace) rather than binding once to `Lookup`: a subscriber that opens the stream *before* a sync worker opens the cache (the common unsynced-cluster case) binds when the db opens, and a Clear-cache delete+reopen under the same CacheID rebinds to the new handle and keeps diffing (the emptied catalog surfaces as Deletes, the rebuild as Adds). An unopened cache db simply emits nothing until it opens or ctx ends, matching `ClusterDataKinds`' empty posture); `clusterDataEventsWatch(id, cacheID)` → `ClusterDataEventsWatch(clusterID, cacheID)` (**the dashboard events table's real-time source** — one ClusterCache's cached Kubernetes Events (the synced `events.k8s.io`/core Event rows, *not* kstack's own `Event`/`clusterEvents` control-plane timeline) as a Kubernetes-style delta watch: the newest window (`store.Events`' default limit, 500) as an `Added` burst, then `Added`/`Modified`/`Deleted` per event keyed by `uid`, each frame carrying its `cacheID` provenance like the kind watch. It shares one generic mechanism with `ClusterDataKindsWatch` — `cacheDeltaWatch[T]`, which owns the WatchDB cache-lifecycle rebind + coalescing-debounce loop; the two differ only in which store broker they follow, what they read, and the key. Events use a **separate** store broker (`EventsSubscribe`/`EventsNotify`, distinct from the object-write `ObjectsSubscribe`/`ObjectsNotify`) so an event burst wakes only this watch, never the kind-catalog re-read — the whole reason event writes don't ping the object-write broker. Because the read is a bounded window, an event aging out of it as newer ones arrive surfaces as `Deleted`; acceptable for a "latest events" table, and filtering will make it cleaner. Debounced by `dataEventsDebounce` (500ms, coarser than kinds since events are the highest-volume stream). **Open Kubernetes semantics, deliberately not the control-plane `Event`'s closed shape:** `ClusterDataEvent.type` is a plain `String!` (not the `EventType` enum) — k8s doesn't constrain `Event.type`, so an omitted/custom value passes through verbatim instead of producing an out-of-schema enum value; and `firstSeen`/`lastSeen` are **nullable** `Time` via field resolvers (`nilIfZeroTime`) — the domain keeps value `time.Time` (comparable, required by `cacheDeltaWatch`'s diff), so the resolver maps the zero time (a source Event with no timestamp) to null rather than serializing `0001-01-01`); `clusterDataObjectsWatch(id, cacheID, apiVersion, resource)` → `ClusterDataObjectsWatch(...)` (**the dashboard's per-kind object tables** — a Kubernetes-style delta watch of one kind's cached objects, keyed like the kind/events watches **plus** the target kind: an `Added` burst on subscribe, then `Added`/`Modified`/`Deleted` per object keyed by `uid`, each frame carrying its `cacheID` **plus its `apiVersion`/`resource`** provenance — unlike the kinds/events watches this one is keyed by kind, so a client switching resources *within one cache* needs the kind to reject the previous kind's stragglers. `ClusterDataObject` carries the typed universal identity (`uid`/`apiVersion`/`kind`/`namespace`/`name`/`creationTimestamp`) **plus `rawJSON`, the object's full native body**, served through the custom `JSON` scalar (bound to `cluster.RawJSON` in `internal/cluster/rawjson.go` — a comparable Go `string` holding already-serialized JSON whose `MarshalGQL` writes the stored bytes **verbatim**, empty → null). It autobinds (no field resolver: the watch reads the body for every row anyway, so gating its marshal would defer nothing). The body is forwarded as-is from the cache — `metadata.managedFields` and the kubectl last-applied annotation are stripped at **write** time (`objectsync`'s `sanitize`, for every kind — which also redacts Secret values), so the reader is a pure pass-through and stored bytes are ~half the size. Kind-specific columns are derived from the body **client-side** (a per-kind registry in the webview), so the sidecar computes no cell values. `creationTimestamp` is a **nullable** `Time` field resolver (`nilIfZeroTime`, shared with the event timestamps and hoisted to `graph/util.go` so gqlgen doesn't relocate it). It mirrors `ClusterDataEventsWatch` — a `cacheDeltaWatch` over the **object-write** broker (the same broker the kind catalog follows), but **subscribed resource-keyed** (`ObjectsSubscribeResource(apiVersion, resource)`) rather than keyless — the object-write broker routes by that same plural resource, so no resolution is needed, and the key is **stable across a CRD Kind remap** (a CRD recreated with the same `(apiVersion, resource)` but a new Kind keeps the key, so the subscription tracks the replacement driver's writes rather than going stale against the dead Kind); an unrelated resource's write never wakes it. It re-reads `store.Objects(apiVersion, resource)` on each debounced ping (`dataObjectsDebounce`, 250ms), projecting each row to a `ClusterDataObject` keyed by `uid`. The store translates the plural `resource` to its `kind` via a `kind_catalog` subquery (the `objects` table is keyed by `kind`), decompresses each row's `raw_json`, and orders by `(namespace, name)`. Because the body is part of the compared projection (and `RawJSON`'s string underlying type keeps the struct `comparable`, which `cacheDeltaWatch`'s diff requires), an **in-place edit** — a `resourceVersion`/spec change under a stable `uid` — now surfaces as `Modified`, not just `Added`/`Deleted`. Empty posture matches the kind/events watches (no open cache → no frames, closes on ctx). `clusterCacheGVRSyncsWatch(cacheID)` → `WatchGVRSyncs(cacheID)` (**the per-kind sync surface** — one cache's `ClusterCacheGVRSync` records as a delta watch, the only object watch that is cache-scoped, since there is one per synced kind; filtered on the eager-loaded owner edge against the cache's deterministically-named discovery anchor, and empty for a cache whose discovery has never run); `clusterCacheStatsWatch(id, cacheID)` → `ClusterCacheStatsWatch(...)` (**one cache's contents as a live gauge** — current on subscribe, then only when it changes, zeroed when the cache closes; a `cacheGaugeWatch` over the object-write broker. It is a stream and not the `ClusterCache.stats` field for the reason in the gauge rule above: a settled cache's record never changes, so the field froze at subscribe time); `clusterCacheSyncHealthWatch` → `WatchCacheSyncHealth` (**the whole-cache sync verdict** — one record per cache, folded read-side from its per-kind records, keyed by `cacheID` and upserted by the client; unscoped so the always-mounted registry can carry it, unlike the per-kind stream it folds); `clusterEvents`/`clusterEventsWatch` → `ClusterEvents`/`ClusterEventsWatch` (the generic per-cluster event timeline, decoupled from the list watch), the ClusterCache-kind parallel `clusterCacheEvents`/`clusterCacheEventsWatch` → `ClusterCacheEvents`/`ClusterCacheEventsWatch` (the cache's own timeline, decoupled from `clusterCachesWatch`), and the per-kind parallel `clusterCacheGVRSyncEvents`/`clusterCacheGVRSyncEventsWatch` → `ClusterCacheGVRSyncEvents`/`ClusterCacheGVRSyncEventsWatch` (**where the sync-transition history lives**, keyed by one kind's record id); `clusterScheduleWatch` → `ClusterScheduleWatch` (the generic reconcile-schedule gauge / next-attempt countdown, also decoupled from the list); `clusterEnabledSet` → `SetEnabled`; `clusterSyncEnabledSet` → `SetSyncEnabled`; `clusterConnectionRetry` → `RetryConnection` (returns immediately; the outcome lands on conditions and reaches the webview through the cluster watch); `clusterCacheClear` → `ClearCache` (delete the cache files, then **bounce that cache's sync workers** — `DeleteCacheFiles` closes the handle they all hold, and nothing else would rebuild them, since a reconcile leaves a running worker alone while its connection and kind are unchanged; each comes back on the new handle and cold-syncs, its resume cookie having gone with the old file); `clusterDelete` → `Delete` (delete the `Cluster` so GC cascades to `ClusterCache`; if the kube-context still exists the importer re-creates it — same `kubeconfig/{context}` name, but a fresh `ClusterID`/ObjectID, since it is a new record). The resolver field is named `ClusterSvc` (not `Clusters`) to avoid shadowing the generated `queryResolver.Clusters` method. `graph/model` holds only the gqlgen-generated `models_gen.go` plus a permanent stub `models.go` (just the package clause) that keeps the package non-empty across regen. The frontend joins the three delta streams in `src/lib/clusters.tsx`: `ClustersProvider` reduces `clustersWatch`, `clusterCachesWatch`, and `clusterCacheSyncHealthWatch` into id-keyed maps (the first two as Added/Modified/Deleted deltas, the third as a latest-value gauge per cache) and joins them down the chain — each row's `activeCache` client-side (the cache whose `serverUid` matches the cluster's `status.server.uid`), then that cache's `syncHealth` by `cacheID` (a verdict is live only while its cache is in the cache stream — derived there rather than swept out of the gauge's accumulator, so a deletion takes effect on the frame that reports it instead of waiting on unrelated verdict traffic) — so `useClusters()` exposes a Kubernetes-shaped `Cluster` with `spec`/`status`/`activeCache`, the cache carrying its folded verdict. `cluster-sync-panel.tsx` renders that as a grouped Active/Orphaned table keyed on `status.source.kubeconfig?.isPresent`, with a "pending" row state derived from `status.server.uid == null`, an enable/disable toggle (`clusterEnabledSet`), and a sync play/pause (`clusterSyncEnabledSet`); the kube-context picker (`kube-config.tsx`) shows only `spec.enabled` + present records. Both status columns are **expandable disclosures** sharing one `EventRunList` (a newest-first, upsert-by-id run list): the **connection** label opens a `ConnectionDetail` (uptime, next-check countdown, "Recent attempts" from `clusterEventsWatch(category:"connection")` + `clusterScheduleWatch`), and the **sync** label — a disclosure only once the row's sync verdict has streamed in — opens a `SyncDetail` — everything in it subscribed only while the row is expanded, which is what makes the ~100-record per-kind stream affordable (the two watches whose operations carry no per-row identity — the cache-contents gauge and the fleet-wide discovery stream — are instead subscribed ONCE, by the row and by the panel respectively, and handed down: urql shares one operation between identical subscribers, and its replay is query-only, so a second subscriber to a subscription joins mid-stream and sees nothing until the next frame) — showing the cache's contents from **`clusterCacheStatsWatch`** (a live gauge, *not* the cache record's `stats`), a **"Kinds syncing"** line from the cache-scoped **`clusterCacheGVRSyncsWatch`** (naming the kinds whose own `Synced` is not `Watching`, since a cache's kinds sync on independent workers and one forbidden CRD is invisible in every other reading; an `unconfirmed` pre-restart condition counts as neither healthy nor broken), and two live **freshness lines** rolled up across kinds — "last update received" (the newest write anywhere) beside "sync verified" (the OLDEST proof, since a cache is only as verified as its least-recently proven watch), kept apart because on a quiet cluster the first legitimately reads hours old while the second is seconds old — an amber **"Possibly stale"** banner when the rollup's reason is `Stale`, naming the kinds behind it (sync-derived — the client never infers staleness from a stamp's age), and the "Recent sync events" transition log from `clusterCacheGVRSyncEventsWatch`, keyed to the kind worth reading: whichever is behind an unhealthy verdict, else Events (reason codes mapped to friendly labels — `SyncComplete`→"Initial sync complete", `ResyncStart`→"Starting re-sync", `SyncStale`→"Watch stalled", etc.). The row's **Cache size** column streams from `clusterCacheStatsWatch` too — the size is a file stat that grows with every write, so it had the same freeze; the cache record's `stats` field is now read only for `exists`. The sync column reads the rollup's reason — `Watching`→"Synced" (ok), `Stale`→amber, `SyncFailed`→"Error", `NoConnection`→muted "Connecting" — never the cache's coarse one. Each per-row subscription mounts only while its detail is open, so idle clusters cost nothing.

The data dir (`--data-dir` / env `KSTACK_DATA_DIR`) is **required** — `app.New` errors when it's empty; the Tauri host wires its `app_local_data_dir()`, tests supply `t.TempDir()`. `<data-dir>/app.db` is **owned by `internal/appdb`**, which opens it, holds its one migration sequence, and hands the `*sql.DB` to feature packages (a SQLite file has a single `schema_migrations` sequence, so its schema can't be co-owned; add a new app-level table as a numbered migration in `appdb/migrations/`, not as a second embed against the same file).

## Auth / identity (`internal/auth`) — the local-first lower layer

User accounts backed by kstack-cloud's Hydra OAuth server (`https://oauth.kstack.sh/`). The whole flow is **sidecar-owned**: the sidecar opens the system browser (auth-code + PKCE, ephemeral loopback redirect), runs the loopback listener, exchanges + verifies the code, **and persists the refresh token in the OS keyring itself** (via an internal `keyringStore` over `zalando/go-keyring` — loopback OAuth already pins the browser to this machine, so there's no host round-trip and **no gRPC credentials channel**). This is **local-first**: a user stays signed in offline — identity is read back from a locally-stored ID token, and a present refresh token is what marks "signed in." It's deliberately **independent of the cloud settings feature**: the settings-sync subsystem (`internal/cloud`) depends on `auth` (for an `oauth2.TokenSource` and the latest-value session `State` stream), **not the reverse**. Like `cluster`/`cloud`, it's fronted by one composition owner and **degrades** when neither a keychain service name nor a credentials store is configured (signed-out, login errors, logout is a no-op, `TokenSource()` nil). The composition root (`internal/app`) configures auth by name, not by wiring (`main.go` passes `OAuthIssuerURL`/`OAuthClientID` — from `KSTACK_OAUTH_ISSUER`/`KSTACK_OAUTH_CLIENT_ID` — plus the keychain service name to `app.Config`, which hands them to `auth.New` as `Config.IssuerURL`/`ClientID`/`KeychainService`. `auth.New` then builds its **own** dependencies: it derives Hydra's standard endpoint paths from the issuer via `newHydraOAuthConfig` (a caller-side helper in `auth.go`; the `auth/oauth` sub-package stays Hydra-agnostic, taking resolved endpoint URLs), and builds its own `keyringStore` over the service name — so only the issuer, client id, and keychain name are configured, no constructed store/config is passed in. `Config` carries **only production knobs** (`IssuerURL`/`ClientID`/`Scopes`/`KeychainService`) — nothing on it lets a caller bypass the real OAuth flow, and `New(Config)` takes no other arguments. The test seams are **unexported functional options** applied by an unexported `newWithOptions(cfg, opts...)` builder that `New` wraps (`withOAuthConfig` → httptest endpoints, `withCredentialsStore` → in-memory store, `withOAuthFlow`/`withLoopback`/`withBrowserOpener` → fakes); they resolve at construction (they pick the store/oauth client the grant is built over) and are reachable only from `auth`'s own (white-box) tests. Auth degrades to signed-out when neither a keychain name nor a `withCredentialsStore` option is given.) It threads the `auth.Service` into the `graph.Resolver` as one `Auth` field — always non-nil; the service itself degrades (signed-out, erroring login) when unconfigured — backing the `authState` query, `authLoginStart`/`authLogout` mutations, and `authStateWatch` subscription (built/consumed by the webview's `src/lib/auth.tsx`).

**Mostly flat, one carved-out sub-package.** The root `package auth` is deliberately flat (no `session`/`credentials` sub-packages — those files share a dense web of value types and would only have to export private state-machine internals to live apart). It's organized **by domain into four files**: `auth.go` (the service facade — the public `Service` interface, the `State`/`TokenSet` value types, the `Token`/`Identity` aliases, `Config` + the test options, and the composition owner; named to match the `cluster.go`/`cloud.go` convention), `grant.go` (the **grant aggregate** plus everything it owns — the credential state machine, its `CredentialsStore`/`RefreshFunc` ports + `ErrSignedOut` defined consumer-side, and the `grantTokenSource` `oauth2.TokenSource` adapter), `login.go` (the **interactive login flow** — the unexported `loginFlow` that runs loopback → browser → exchange → verify, the PKCE verifier/state generation + browser opener that feed it, the flow's seam interfaces `OAuthFlow`/`Loopback`/`LoopbackFunc` and the `loginStarter`/`pendingLogin` types the service holds the login step behind, **and the 127.0.0.1 `loopbackServer` redirect listener** that implements the flow's own `Loopback` seam — `(*loginFlow).start` runs the **synchronous setup** (loopback bind + browser open) and returns a `pendingLogin` for the slow async tail), and `keyring.go` (the OS-keyring credential persistence — the unexported `keyringStore`, the lone concrete `CredentialsStore` impl, kept apart from the aggregate since it carries its own `zalando/go-keyring` dependency).

The **one** piece carved out is `internal/auth/oauth` (`package oauth`) — the OAuth2/OIDC **protocol layer**, the subsystem's one genuine deep module (PKCE S256, JWKS verification via go-oidc, RFC 7009 revocation, token exchange/refresh) behind a small `Client` surface. It is a **leaf**: `auth` builds an `oauth.Client` (via `oauth.NewClient(oauth.Config)`) and drives it, so `oauth` must not import `auth`. Because `oauth.Client` *produces* the `Token` and `Identity` value types, those types **live in `oauth`** (avoiding the import cycle that keeping them in root would force), and `auth.go` re-exports them as true type aliases (`type Token = oauth.Token`, `type Identity = oauth.Identity`) so the rest of `auth` and external consumers (`graph`, `cloud`) keep naming them `auth.Token`/`auth.Identity` with no conversion and no sub-package import. `oauth.ParseIdentityUnverified` (display-only claim decode, used by the grant on cache restore) is the one other exported helper `auth` calls across the boundary.

The grant aggregate, the loopback listener, the login flow, and the keyring store remain **unexported** (`grant`/`loopbackServer`/`loginFlow`/`keyringStore`); the root's exported surface is the `Service` interface, its `New(Config)` constructor (with an unexported `newWithOptions(cfg, opts...)` builder that white-box tests use to inject `option` seams), the seam interfaces (`OAuthFlow`/`Loopback`/`LoopbackFunc`), the `Token`/`Identity` aliases, and the persistence types. External consumers (`graph`, `cloud`) that need a stand-in fake the `Service` interface directly rather than constructing a real service with seams.

- **`Service`** is an **interface** (`auth.New(Config) (Service, error)`), passed around to consumers like the cloud client. It owns **no long-lived goroutines, so there's no `Start`/`Close`** (restore happens in `newGrant`; revocation is a per-`Logout` fire-and-forget, and `StartLogin`'s async tail is likewise bounded fire-and-forget — see below). Methods: `Current(ctx) (State, error)` (the current `State` — `Authenticated` + `Identity` + `TokenSet`, no forced refresh), `StartLogin(ctx)` (runs the `loginFlow`'s **synchronous setup** — loopback bind + browser open — under the caller's ctx and **returns its error synchronously** so the `login` mutation can surface a setup failure to the UI; the slow tail — wait for redirect → exchange → `Verify` → `grant.set(tok, identity)`, which persists before publishing the signed-in `State` — then runs in a **bounded, detached fire-and-forget goroutine** (`loginTimeout`, not tied to shutdown — like `Logout`'s revoke), its completion observed via `Subscribe`/`authStateWatch`; a tail failure is logged and stays signed-out. The flow's two phases are tested directly in `login_test.go`, while a service-level test fakes the whole login step via the `withLoginStarter` option — so the per-part flow seams don't leak onto the service's build path), `Logout(ctx)` (captures the refresh token, `grant.clear()`s local-first — publishes the signed-out `State` — then `Revoke`s fire-and-forget on its own bounded context; if the keychain write fails it returns the error and stays signed in), `TokenSource(ctx) oauth2.TokenSource` (a `grantTokenSource` adapter capturing `ctx` for the lazy refresh exchange; **nil when degraded**), and `Subscribe() (<-chan State, func())` (a **latest-value** session-state stream — current-on-subscribe, then each change — plus cancel).

**The grant aggregate models the OAuth grant.** The unexported `grant` aggregate owns the **token set as the source of truth** plus the cached identity; `State.Authenticated` and `State.Identity` are **derived** (signed-in ⇔ a refresh token is present), never stored alongside, so credential state and the published `State` can't drift. It owns the token (cache + **lazy refresh**, mutex serializing a burst into a single refresh, persist-before-cache) and a `gochan/watch` hub publishing the **current session `State`** (latest-value, current-on-subscribe; seeded with the restored State at construction). A sign-in/out republishes a flipped `Authenticated`; a routine refresh republishes the same `Authenticated` bit with a renewed `Tokens` projection — so a consumer that keys off the sign-in bit sees no transition on refresh, without any event-type tagging. `newGrant(store, refresh, opts)` restores from the store (decode identity via `parseIdentityUnverified` — display-only; the cloud re-verifies the access token per request). `validToken`/`current`/`set`/`clear`/`state`/`subscribe` are the internal ports. **Refresh decision:** the cache/refresh/dedup is hand-rolled (we keep per-call `ctx` into refresh, which a long-lived `oauth2.ReuseTokenSource` would bake in at construction); only the refresh *HTTP exchange* is delegated to `golang.org/x/oauth2` inside the oauth client's `Refresh`.

**Token-source shape & leak posture.** Downstream consumers get an **`oauth2.TokenSource`** (the cloud api client builds one per request from the request `ctx` via `Service.TokenSource`, so the bounded token-fetch timeout governs each refresh). This is the idiomatic shape but **does expose the refresh token** on the returned `*oauth2.Token` — the api client simply reads `AccessToken` and never inspects the rest. The resolver still maps only the tokenless projection (`State.Authenticated` + `State.Identity` → `AuthState { authenticated, identity }`); `State.Tokens` (a `TokenSet`) rides along for in-process callers but is dropped by the GraphQL projection.

**Hydra OIDC mechanics** (the `auth/oauth` sub-package, plus the loopback listener in `login.go`): PKCE (`generateVerifier` in `login.go` / `s256Challenge` in `oauth`), `Client.AuthCodeURL`, a 127.0.0.1 `loopbackServer` redirect listener (in `login.go`, behind the exported `Loopback` seam), `Client.Exchange`/`Refresh` (via `golang.org/x/oauth2`), `Client.Revoke` (RFC 7009 token revocation — public client, posts `token`+`client_id` to `oauth.Config.RevocationURL`; revoking the refresh token also kills the grant's access tokens), and `Client.Verify` (ID-token signature/iss/aud/exp via `github.com/coreos/go-oidc/v3` against Hydra's JWKS) → `Identity{UserID,Email,Name}` (claim `sub` → `UserID`). **Identity comes from the verified ID token**, so no extra profile round-trip.

## Cloud settings sync (`internal/cloud`) — depends on `auth`

Cloud-synced settings (later AI-model routing) backed by kstack-cloud's API. Settings are **local-first**: an edit applies to a local JSON file immediately and is queued for the cloud, surviving offline/restart. The subsystem **depends on `internal/auth`** — it authenticates the api client from `authSvc.TokenSource`, and **wakes its sync engine by observing `authSvc.Subscribe()` session `State`** (`auth` knows nothing about the engine). It **degrades** when unconfigured (no cloud URL / data dir ⇒ no settings sync). The composition root (`internal/app`) wires CloudURL (`KSTACK_CLOUD_URL`) and hands the `auth.Service` to `cloud.New(dataDir, cloudURL, authSvc)`.

- `internal/cloud` (root package `cloud`) — **composition + lifecycle owner**, mirroring `cluster.Service`. `cloud.New(dataDir, cloudURL string, authSvc auth.Service, pokeSvc *poke.Service)` wires prefs + queue + engine, building the api upstream from `authSvc.TokenSource` (degraded — no engine — without a data dir, or without a cloud URL + a non-nil token source); `pokeSvc` is the shared resync broadcaster handed to the engine (nil disables external wake signals). `Start(ctx) (stop func(context.Context) error, error)` runs the settings-sync engine (idempotent — a second `Start` returns a no-op stop so it can't leak an engine goroutine) **plus a goroutine that observes the auth session `State` and pokes the engine only when `Authenticated` flips** (sign-in → authenticate + sync now; sign-out → cancel the in-flight authenticated watch). The stream is latest-value (current-on-subscribe), so the goroutine seeds its baseline from the first `State` without poking, and a routine token refresh — which leaves `Authenticated` unchanged — never wakes the engine. Tracking the single `Authenticated` bit (not the whole `State`) is what makes refresh a non-event. `ctx` scopes initialization only; the returned `stop` cancels the engine **and** the poke goroutine and blocks until both unwind, honoring its own drain-deadline context (there's no `Close` — the stop func replaces it). Exposes `Prefs()` (the settings store, nil when degraded). The required production inputs are positional constructor args (`dataDir`, `cloudURL`, `authSvc`, `pokeSvc`), not a config struct; the test seam (a fake sync upstream instead of the api client) is an **unexported functional option** — `withUpstream`, applied by an unexported `newWithOptions(dataDir, cloudURL, authSvc, pokeSvc, opts...)` builder that `New` wraps and reachable only from `cloud`'s own (white-box) tests, mirroring the `auth` subsystem's option pattern.

Sub-packages (leaf-first):

- `internal/cloud/syncstore` — generic `Envelope[T]{Data, Version, LastSyncedAt, LastEventAt}` + `Store[T]` over `internal/atomicjson` (crash-safe JSON; serialized writers). The reconcile-state file primitive.
- `internal/cloud/prefs` — the `Settings` type (**pointer fields + omitempty** so absent ≠ cleared, for the cloud's deep-merge), `Merge(base, patch)` (the local-first reconcile primitive), `Clone` (deep copy), and `Store` (persist + a `gochan/watch` hub that publishes current-on-subscribe, with an equality guard so an unchanged `Set` neither writes disk nor publishes). Because `Settings` holds pointers, the `Store` (Set/Get) and the `mutationqueue` (Enqueue/Pending) **deep-copy at their boundaries** so a caller mutating a string it passed in (or one it got back) can't desync in-memory state from the persisted JSON or queued payload.
- `internal/cloud/mutationqueue` — durable FIFO of pending local patches (atomicjson-backed, monotonic non-random ids). `Enqueue`/`Pending`/`Ack`; survives restart so offline edits still reach the cloud.
- `internal/cloud/api` — minimal GraphQL-over-HTTP cloud client (POST + SSE `WatchSettings`), authenticating every request from a per-request `oauth2.TokenSource` built from a `func(context.Context) oauth2.TokenSource` factory (`auth.Service.TokenSource`), reading its `AccessToken` — not a per-call token threaded through.
- `internal/cloud/prefsync` — the always-on reconcile `Engine` + `Upstream` interface (`Snapshot`/`Watch`/`Update`). `Watch` returns the settings channel **plus a buffered terminal-error channel** (nil = clean end / ctx cancel; non-nil = a read/transport failure **or** a GraphQL subscription error frame, which ends the stream rather than being silently skipped) so the engine distinguishes an errored close (record `LastError`, keep escalating backoff) from a healthy one — a nil error channel is treated as a clean end. Supervised connection with exponential backoff + poke. Production builds with `New(up, store, queue, notifier)` (defaults only); the deterministic `Now`/`Sleep`/`Jitter`/backoff seams are **unexported functional options** (`withNow`/`withSleep`/`withJitter`/`withBackoff`) applied by an unexported `newWithOptions(..., opts ...option)` builder that `New` wraps — reachable only from the package's white-box tests, mirroring the `auth`/`cloud` option pattern (so prefsync's tests are `package prefsync`, not `_test`). Wake/resync signals arrive via the `*poke.Service` passed to `New` (the shared broadcaster) — a wired-in dependency alongside `up`/`store`/`queue`, *not* a tunable option; nil disables external wake signals (tests, degraded runs). It's the concrete type, not an interface: `prefsync` already imports `poke` (the signals are `poke.Signal`), so an interface would decouple nothing — `poke` stays a leaf because it never imports `prefsync`, interface or not. `Set` is **local-first** (write store + enqueue + poke); on Live it **drains the queue** via `Upstream.Update` and acks; incoming snapshots/events have **still-pending patches re-layered on top** (`prefs.Merge`) so a stale cloud snapshot can't clobber an unacked local edit.

## Resync broadcaster (`internal/poke`)

`internal/poke` is a **cross-subsystem, leaf package** — no imports from other `internal/` packages. It owns two jobs:

1. **Wall-clock gap detector**: runs a ticker and compares the elapsed wall-clock time against the expected interval (default 15s tick, 2× gap factor). A jump larger than the threshold means the process was frozen (machine sleep, SIGSTOP, VM pause) — it fires a `Poke(SourceWallClock)`. This is the backstop that needs no OS event and works headless.
2. **Fan-out broadcaster**: every poke (from the detector or a direct `Poke(SourceHost)` call) is broadcast to all current subscribers via a `github.com/amorey/gochan/broadcast` hub. The `SourceHost` entry point is driven by the host gRPC `PokeService.Poke` handler (`grpc/poke_server.go`) — the host calls it on OS resume / network-on. (The Rust host trigger that actually calls the RPC is a separate `src-tauri/` change.)

**API**: `New()` → `*Service` (no arguments — production tunes nothing); `Start(ctx) (stop func(context.Context) error, error)` (the composition-root lifecycle entry, mirroring `cluster.Service`/`cloud.Service` — `Start` runs the detector in a goroutine and returns a `stop` func that cancels and waits, closing the hub, bounded by its own drain-deadline context) or the lower-level `Run(ctx)` it wraps (blocks, used directly by tests); `Poke(src)` (never blocks, safe from any goroutine); `Subscribe()` (returns `(<-chan Signal, func())`). `internal/app` owns the one `*poke.Service`'s lifecycle and hands it to `cluster.New`, `cloud.New`, and `grpcserver.NewServer`. The integrations sharing the one broadcaster: the settings engine receives signals via the `*poke.Service` it's given in `prefsync.New`; the host gRPC `PokeService` produces `SourceHost` pokes; and **the core and per-kind-sync controllers subscribe to the bus directly** (each fed the `*poke.Service` via `cluster.New`). On a poke the `ClusterCoreController` re-probes every eligible cluster's connection immediately, and the `ClusterCacheGVRSyncController` restarts its live workers in place — each re-dials and resumes cheaply from its persisted resourceVersion. This is a **fan-out, not a cascade**: a poke is an ephemeral "re-establish now" event delivered to both consumers in parallel; it is deliberately *not* routed through a durable spec counter or through connection-status conditions (a clean resume produces no condition transition, so a cascade would silently fail to restart the now-stale watches). Conditions remain the *output* the webview reads, never the poke transport.

Test seams: the gap-detector tuning (`tick`/`gapFactor`) and the clock/ticker (`now`/`newTicker`) are **unexported functional options** (`withTick`/`withGapFactor`/`withNow`/`withTicker`) applied by an unexported `newWithOptions(opts ...option)` builder that `New` wraps — reachable only from poke's own white-box tests, mirroring the `auth`/`cloud`/`prefsync` option pattern. Production never tunes them (the gap detector's defaults are fixed and the gRPC `PokeService` only calls `Poke`, never reconfigures the detector), so `New` exposes no knobs; the external consumers that hold a `*poke.Service` in tests just call `New()` and drive `Poke` directly.

## gRPC + GraphQL over one socket (h2c)

gRPC needs HTTP/2; GraphQL stays HTTP/1.1. `internal/app` wraps the GraphQL/control mux in `h2c.NewHandler` whose dispatcher routes requests matching `grpcserver.IsGRPCRequest` to the `*grpc.Server` and everything else to the mux. The predicate lives in `grpc/` because it *is* the definition of a gRPC request (HTTP/2 *and* `application/grpc`); the composition root owns the dispatch + h2c wiring (the decision that these two surfaces share one socket). Each concern stays with its owner without a separate multiplexer package — `grpc/` owns "what is a gRPC request", `app` owns the topology. HTTP/1.1 GraphQL POST + SSE are untouched (they keep `ProtoMajor==1` and a Flusher-backed writer). An idle `AuthStateWatch` stream is kept alive under the server's 60s `IdleTimeout` by a gRPC keepalive ping. The webview uses GraphQL; the host (tray) uses gRPC (auth-state watch + login/logout, resync poke). The cluster surface is GraphQL-only (`clusters`/`clustersWatch` + `clusterCachesWatch` + cluster mutations).

**Shutdown** is driven through the `App` surface from `main.go`. `srv.RegisterOnShutdown(app.NotifyShutdown)` fires the moment `srv.Shutdown` begins, then:

1. **`app.NotifyShutdown()`** fans out to both sub-servers: `grpcServer.NotifyShutdown()` cancels the serving context (every `Watch` handler returns `nil` → grpc writes its OK trailers → each client sees a clean `io.EOF`), and `graphqlServer.NotifyShutdown()` closes a `shutdownCh` that cancels each active SSE subscription's request context (gqlgen flushes its terminal `event: complete`).
2. **`srv.Shutdown(ctx)`** stops accepting and waits for the non-hijacked GraphQL requests to finish — the SSE streams, now cancelled, flush and return.
3. **`app.DrainWithContext(ctx)`** waits on *both* sub-servers' `WaitGroup`s. This is the essential wait for the **hijacked h2c gRPC streams** that `srv.Shutdown` does not track; for GraphQL it's belt-and-suspenders.
4. **the `stop` func from `app.Start`** drains the services — `clusterSvcStop` → `cloudSvcStop` → `pokeSvcStop` (poke's hub closes last, after the cluster controllers that subscribe to it have drained) — then **`app.Close()`** stops the gRPC transports (`grpcServer.Stop()`) and `clusterSvc.Close()` (which owns the whole cluster control-plane teardown order: stop writers → stop beehive's controllers, then the sync workers → shut the per-cluster cache → close the beehive store). main() calls `stop(stopCtx)` before `Close`.

Why it's built this way (the non-obvious parts): grpc's own `GracefulStop` **panics** on the `ServeHTTP`/h2c path, so the stream must end on its own serving context instead, and `Stop` only runs in step 4 after the streams have drained. The GraphQL SSE drain is **per-request** (`graph.Server.ServeHTTP` wires each SSE request's context to `shutdownCh`), deliberately **not** via `http.Server.BaseContext`: a `BaseContext` cancel would tear down the shared h2c connection carrying gRPC mid-stream. Because nothing touches `BaseContext`, the two transports are independent — `NotifyShutdown` signals both at once and there is no required gRPC-before-GraphQL ordering. (The h2c dispatcher also routes gRPC away *before* the GraphQL server's `ServeHTTP`, so a long-lived gRPC connection is never counted in the GraphQL `WaitGroup`.)

## Patterns

- **Resolver deps are always non-nil**: the composition root (`internal/app`) wires every `Resolver` field, and resolvers call their deps without nil guards — degraded behavior (e.g. no cloud account) lives inside the services themselves (`auth.New` degrades internally; the data dir is simply required). Tests construct the `Resolver` with fakes (e.g. `newFakeAuth`) rather than relying on nil tolerance.
- **Pub/sub**: `github.com/amorey/gochan` hubs fan snapshots to subscribers — `watch` for latest-value "current state" streams (the kubeconfig watcher and the auth session-`State` stream, both delivering the current snapshot on subscribe — a consumer needs no separate "read current" call to seed itself), `broadcast` for fan-out streams whose subscribers supply their own initial snapshot (the `poke` resync broadcaster). Watchers use fsnotify + a debounce, then publish the new snapshot.
- **Subscription resolvers**: return a channel that **emits the current snapshot first, then deltas**. Hub-backed sources forward through `mapStream` (`graph/util.go` — the source is current-on-subscribe, so its first value IS the snapshot; see `authStateWatch`). `clustersWatch`/`clusterCachesWatch` follow the same rule the Kubernetes way: the service's `watchListChan` pump replays beehive's `WatchList` snapshot as `Added` changes then streams the `Added`/`Modified`/`Deleted` above it, so the resolver just `mapStream`s each value change to a pointer. Honor `ctx.Done()`.

## Tests & checks

- testify + `net/http/httptest`. Resolver-level GraphQL tests stand up `graph.NewServer(&graph.Resolver{...})` and `POST /graphql` (in `graph/`); h2c/control/lifecycle tests stand up `app.New(...)` (in `internal/app/`). Filesystem via `t.TempDir()` / `os.MkdirTemp`.
- **White-box tests by default** — a package's tests live in the same `package foo` (not `package foo_test`), so they can exercise unexported helpers directly with no export-tax. This mirrors the flat-package philosophy elsewhere in the tree (e.g. `internal/auth`): boundaries inside a package are kept by discipline + file ownership, not by the compiler, and the test layer follows the same rule. **Escape hatch:** reach for an external `package foo_test` only when a test's *purpose* is to pin the public contract and you want the compiler to *guarantee* it touches only the exported surface — then say so in a comment. Don't mix the two styles within one package without that reason.
- **Avoid magic sleeps.** Don't `time.Sleep` to wait for async work (fsnotify reloads, hub publishes) — block on the actual event with `<-sub.Chan()` guarded by a `select { case … : case <-time.After(deadline): t.Fatal(…) }` timeout, as the watcher tests do. A `time.After` deadline is fine; a fixed sleep is flaky and slow.
- `make test-go` (`cd sidecar && go test ./...`).
- `make lint-go` (gofmt) and `make vet-go` (`go vet`). Run `gofmt -w` before committing.

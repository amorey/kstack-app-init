# sidecar — Go backend

A standalone Go binary started by the Tauri host. It exposes the app's GraphQL API (and a gRPC control channel) and owns all Kubernetes logic. **No TCP** — it listens on a Unix domain socket (named pipe on Windows), prints `READY unix:<path>` to stdout so the host can dial it, and shuts down on `SIGINT`/`SIGTERM` or **stdin EOF** (the host closing its end = "parent gone").

## Layout

The codebase mirrors the **kubetail layout**: `main.go` is lifecycle only, `internal/app` is the composition root + routing, and the GraphQL server lives in `graph` (alongside the resolvers). There is **no `server` package**; "the server" is the thin listener in `main.go`.

- `main.go` — **lifecycle only**. Parses flags, binds the socket, builds the `*app.App`, mounts it on an `http.Server`, registers `app.NotifyShutdown` via `srv.RegisterOnShutdown`, serves, and drives graceful shutdown (`srv.Shutdown` → `app.DrainWithContext` → `app.Close`). No composition logic.
- `internal/app/` — **composition root + routing + lifecycle owner**. `app.go` (`app.New(Config{...})`) builds the shared pieces (the `*poke.Service`, then `cluster.New(...)` → `*cluster.Service` — which owns its own kubeconfig watcher and beehive store/instance — plus `auth.Service` and `cloud.Service`), constructs the `graph.Resolver` (holding the `ClusterService` + `auth.Service`), wires the GraphQL server (`graph.NewServer`) and gRPC server (`grpcserver.NewServer`), mounts them on a mux, and multiplexes onto one h2c handler: an `h2c.NewHandler` whose dispatcher sends `grpcserver.IsGRPCRequest` traffic to the gRPC server and everything else to the mux. It owns this *composition* — that these two surfaces share a socket and the h2c wiring itself — while `grpc/` owns the gRPC-request predicate. `App` is a thin `http.Handler`: it holds the two sub-servers and the services, delegating `Start`/`Close` to them and fanning `NotifyShutdown`/`DrainWithContext`/`Close` out to the sub-servers. `App.Start(ctx)` returns a drain-func (matching `cluster.Service.Start`) — it starts the services (`pokeSvc.Start` → `clusterSvc.Start`, which starts beehive + watcher internally, → `cloudSvc.Start`, each returning its own stop func) and returns one `stop` that fans out to `clusterSvcStop(ctx)` → `cloudSvcStop(ctx)` → `pokeSvcStop(ctx)` (poke last, so its hub — the controllers' resync subscription — is closed only after cluster has drained; the left-to-right arg evaluation in the `errors.Join` enforces this). `App.Close` then only stops the gRPC transports and calls `clusterSvc.Close` (the poke broadcaster and cloud engine are already drained by `stop`); `clusterSvc.Close` owns the full watcher + beehive + cache teardown order internally.
- `graph/` — GraphQL: `schema.graphqls`, generated code, resolvers, and **`server.go`** — `graph.Server` (`NewServer(*Resolver)`), the gqlgen handler with the bearer-token plumbing, SSE shutdown lifecycle, and `NotifyShutdown`/`DrainWithContext` (see Shutdown below). The `Resolver`'s dependencies must be non-nil — tests wire fakes (e.g. a fake `auth.Service`); degraded behavior lives inside the services, not behind resolver nil-guards.
- `grpc/` — gRPC surface. `grpc/server.go`: `grpcserver.NewServer(authSvc, pokeSvc)` wraps a `*grpc.Server` (registering `AuthService` and `PokeService`; `AuthService.AuthStateWatch` is the lone server-streaming RPC and joins the `streams` WaitGroup so it drains at shutdown — `PokeService` is unary-only so it doesn't) with the `NotifyShutdown`/`DrainWithContext`/`Stop` lifecycle surface. `grpc/auth_server.go` implements `AuthService` over `auth.Service`: `StartLogin`/`Logout` (unary, nil-service → `Unavailable`) and `AuthStateWatch` (server-streaming, latest-value from `auth.Subscribe()`, nil-service → end immediately). `grpc/poke_server.go` implements `PokeService` over `*poke.Service`: one unary `Poke` (nil-service → `Unavailable`) that broadcasts `Poke(SourceHost)` — the host calls it on OS resume / network-on to resync long-lived connections. `grpc/authpb/` holds the committed protoc output for `proto/auth.proto`; `grpc/pokepb/` for `proto/poke.proto`. Regenerate all with `make proto` (or `go generate ./grpc/...`); never hand-edit `*.pb.go`. (Kube/cluster data is **not** a gRPC service — it lives only on the GraphQL surface: `clusters`/`cluster` queries, `clustersWatch` + `clusterCachesWatch` subscriptions, cluster mutations.) The predicate `IsGRPCRequest` lives in `grpc/server.go`; the composition root uses it to route the shared h2c socket.
- `internal/` — building blocks: `app` (composition root, above), `ipc` (binds the per-OS IPC endpoint — AF_UNIX socket / named pipe — with user-only access; `main.go` uses `ipc.Listen`/`DefaultSocketPath`/`Scheme`), `k8shelpers` (the kubeconfig watcher — `KubeConfigWatcher`, consumed by `internal/cluster`), `atomicjson` (crash-safe single-file JSON read/write), `logging`, `sqlitemigrate` (shared forward-only SQLite migration runner), `appdb` (owns the app-level `app.db` — its connection pool and single migration sequence — and hands the `*sql.DB` to consumers), **`poke`** (cross-subsystem resync broadcaster — see below), plus the **cluster** package under `internal/cluster/` (the Kubernetes/cluster subsystem behind `ClusterService` — see *Cluster subsystem* below), the **auth** packages under `internal/auth/` (the mostly-flat root `auth` package — `auth.Service`, the local-first identity layer — with the OAuth2/OIDC protocol layer carved into the `auth/oauth` sub-package), and the **cloud** packages under `internal/cloud/` (the root `cloud` package — `cloud.Service`, the cloud-synced settings feature that *depends on* `auth` — and its settings sub-packages; see *Auth / identity* and *Cloud settings sync* below).

## Cluster subsystem (`internal/cluster`)

The cluster subsystem is one flat package, `internal/cluster` (`package cluster`), fronted by **`ClusterService`** — the single boundary between the frontend and the cluster backend. Beehive (`github.com/amorey/beehive`) is the control plane: a SQLite-backed, level-triggered controller framework (a small operator runtime). The service owns its beehive store (at `<dataDir>/beehive.db`) and instance outright — beehive is cluster-only, so there's no reason for the composition root to hold it; if a non-cluster kind ever needs beehive, hoist the store/instance back up to `internal/app` and pass `*beehive.Beehive` into `cluster.New`. Beehive (**v0.13.0**) hosts two resource kinds in an **owner chain** — `Cluster → ClusterCache` — so deleting a cluster cascades (beehive GC) to its ClusterCache children. Each `ClusterCache` carries a **`kstack.io/cache-files` finalizer** so its deletion (a UID-switch prune or a cluster cascade) blocks until the cache controller has stopped the engine and removed the on-disk `.db` file — the file can't be orphaned. A `Cluster` owns **zero or one** `ClusterCache` at steady state (none until its first successful probe; the cache for its current physical identity thereafter) — a physical-cluster migration to a new kube-system UID creates the new identity's cache and **deletes the superseded one** (so the two coexist only briefly during the hand-over). The children are enumerated via the owner edge (`Client.ListOwned`), not by re-deriving a slug. (There is no separate per-context intake kind: the kubeconfig importer reconciles contexts directly into `Cluster` objects, 1:1.)

The package holds (flat, by file): the **domain types** (`types.go`, `helpers.go` — the spec/status split, `ClusterID`, slugs, condition helpers, `ConnectionEligible`), the **two beehive controllers** (`core_controller.go` = `ClusterCoreController`, with its liveness watch in `connection_sentinel.go`; `cache_controller.go` = `ClusterCacheController`), the **kubeconfig importer** (`kubeconfig_importer.go` — the sole creator of `Cluster` objects), and the **service boundary** (`service.go`). Two genuine deep modules are carved out as leaf sub-packages (the `auth/oauth` precedent), neither importing the root, grouped under `internal/cluster/cache/`: `internal/cluster/cache/store` (`package store` — the per-cluster SQLite cache `Manager`) and `internal/cluster/cache/engine` (`package engine` — the sync engine). The `cache/` parent is a namespace directory only (no Go files); the `ClusterCacheController` that drives these two stays in the root `cluster` package (it's glue — coupled to the root's beehive kind types + condition/eligibility helpers, and registered by `service.go` — so moving it under `cache/` would cycle). All cluster tests are **white-box** (`package cluster`), matching the tree's white-box-by-default rule; shared fixtures (kubeconfig sources, a memory-backed beehive with the kinds registered, a no-op controller) live in `testutil_test.go`. They're an in-package `_test.go` file rather than a separate `testutil` package on purpose: a `package cluster` test importing a `testutil` that itself imports `cluster` would be an import cycle, and the `_test.go` suffix keeps the `testing`/`testify`/`sqlite` deps out of the production build.

**`ClusterService` (`service.go`) is the boundary.** `cluster.New(dataDir, kubeconfigPath, pokeSvc) (*Service, error)` builds the kubeconfig watcher (over `kubeconfigPath`), opens the beehive store + instance (at `<dataDir>/beehive.db`), builds the two beehive clients (one per kind), constructs and **registers the two controllers** with beehive, and builds the importer and the per-cluster cache `store.Manager` (rooted at `<dataDir>/clusters/<ClusterID>/`, keyed by beehive ObjectIDs — see Per-cluster cache below); the returned `*Service` implements the `ClusterService` interface — the GraphQL-facing domain surface: `List`/`Get` (a Cluster alone — no cache join), `Watch`/`WatchCaches` (two **independent Kubernetes-style delta watches** — the Cluster kind and the ClusterCache kind, each forwarded from beehive's per-kind `WatchList` as `Added`/`Modified`/`Deleted` changes; the ClusterCache stream is standalone and joined onto clusters **client-side**, so cache churn never re-emits a cluster), `CacheStats`, `SetEnabled`/`SetSyncEnabled`/`RetryConnection`/`ClearCache`/`Delete`. Every beehive detail (the store itself, slugs, the owner chain, the spec/status split, the delta-watch mapping) and the cache files live behind it; callers deal only in the domain `Cluster`/`ClusterCache`. `*Service` additionally owns the full control-plane lifecycle off the interface: `Start(ctx)` starts beehive, then the importer; the resync poke bus is **not** wired by the Service — the two controllers subscribe to it directly in their own beehive `Start` (see below). `Close(ctx)` tears down in dependency order — close the watcher + stop the importer, stop beehive (every controller — which unsubscribes from the poke bus — + sync engine), shut down the cache (safe only now the engines are gone), then close the beehive store. The composition root (`internal/app`) holds the concrete `*Service` (for `Start`/`Close`), hands it to `graph.Resolver` typed as the interface, and owns only the shared poke bus — the cluster-shutdown ordering invariant lives entirely inside `Service.Close`.

Adding a future cluster-creator (manual creation, kstack-cloud sync) means a new `ClusterSpecSource` *variant* (the discriminated union on `ClusterSpec.Source`) + a new importer peer writing `Cluster` objects with that variant + a sibling block in `ClusterStatusSource`, plus a per-variant credential-resolution case in `ClusterCoreController` (today it hard-codes the kubeconfig variant). All creators share the one `Cluster` kind; reintroduce a separate intake kind only if two sources must ever *dedup* into one `Cluster` (e.g. a kubeconfig context and a cloud record naming the same physical cluster) — until then the 1:1 importer→`Cluster` mapping is the simpler shape.

- **Kubeconfig watcher** (`internal/k8shelpers`, `k8shelpers.KubeConfigWatcher` — a self-contained, reusable building block in its own package, but the cluster service owns the *instance*: `cluster.New` constructs it from `kubeconfigPath` and `Service.Start`/`Close` drive its `Start`/`Close`) — fsnotify + 100ms debounce over the kubeconfig precedence paths, publishing full `*api.Config` snapshots on a latest-value hub (current-on-subscribe). The importer and `ClusterCoreController` consume it through the package-local `KubeConfigSource` interface (`Get`/`Subscribe`; tests substitute a static fake): the importer consumes the snapshot stream, the controller only reads `Get()` for credential resolution.
- **Domain types** (`types.go`, `helpers.go`) — `Cluster{ID, Generation, CreatedAt, DeletionRequestedAt, Spec, Status}` (a Cluster alone — its ClusterCache children are **not** joined in; they stream standalone via `WatchCaches` and are joined client-side. `DeletionRequestedAt` carries beehive's soft-delete tombstone under its own name, surfaced as-is — no rename at the domain boundary), keyed by a `ClusterID` that IS the beehive **ObjectID** (`type ClusterID = ObjectID`, an alias of the generic `cluster.ObjectID int64` identity type) — opaque, source-agnostic, and stable for the record's life (a departed kube-context is orphaned not deleted, so its id survives a return; the id changes only on an explicit Delete). The id is deliberately *not* the remote cluster's UID; cross-source dedup, if ever needed, is a read-side grouping on the probed `Server.UID`. The source's natural key (e.g. a kube-context name) lives only on the beehive **slug** — an importer-internal reconcile/uniqueness key, never the identity: a kubeconfig Cluster is *created* with the slug `kubeconfig/{context}` (so beehive's per-kind slug-uniqueness rules out a duplicate for a context), but nothing reads it back by that slug — lookups go through `Get(ctx, beehive.ObjectID(id))`. On the wire every object id is **one shared GraphQL scalar** (`scalar ObjectID`, bound to `cluster.ObjectID` in gqlgen.yml) carrying a decimal string (`"42"`) via `MarshalGQL`/`UnmarshalGQL` — so gqlgen hands the cluster resolvers an already-typed `cluster.ObjectID` (= `ClusterID`) argument, no per-resolver parsing. The single scalar + marshalling path is reused by every kind (`ClusterCacheID` is the second such alias, naming a ClusterCache's own ObjectID), instead of a per-kind scalar. The frontend codegen maps the scalar to `string` (`codegen.ts`), so the webview still sees an opaque string. (The on-disk cache is keyed by the same beehive ObjectIDs — see Per-cluster cache.) The GraphQL types bind **1:1 by name** to these (see gqlgen.yml), and the schema mirrors beehive's `Cluster → ClusterCache` owner chain: there is **no merge/projection type**. `ClusterSpec` is user/API-owned (`Name`, `Enabled`, `SyncEnabled` — declarative names, no `is` prefix; `Source` — the source *reference*, a discriminated union `ClusterSpecSource{Kubeconfig *ClusterSpecSourceKubeconfig{Context}}`, Manual/Cloud later). The matching *observation* (cluster/user names, presence, isDefault) is **not** in spec: the `ClusterCoreController` observes it live from the kubeconfig each reconcile and writes it to `ClusterStatus.Source` (the importer is creation-only — see below). The spec/status split of the source is named for the path: `ClusterSpecSource`/`ClusterSpecSourceKubeconfig` (the reference) vs `ClusterStatusSource`/`ClusterStatusSourceKubeconfig` (the observation). `Enabled` is the master "use this cluster in the app" switch — it gates `ConnectionEligible` and the webview's context picker / cluster lists; `SyncEnabled` is the sub-toggle gating the cache engine (`syncEligible = Enabled && SyncEnabled`). The spec carries **no trigger/counter fields**: a targeted retry (`RetryConnection`) forces an immediate out-of-band re-probe via the core controller's retry bus (`Reprobe`) — backoff-neutral, so a failed "check once more" retry neither resets the ladder to the fast 1s ramp nor advances the schedule; the automatic cadence is undisturbed by manual clicks (only a successful probe clears backoff) — and resync pokes drive an out-of-band reconcile — never through a spec write. The beehive **stored** types are `ClusterStatus` (Cluster kind: `Source`/`Server`/`Principal`/`LastConnectedAt` + `Connected`/`Healthy` conditions — both stored *and* served, no copy) and `ClusterCacheStatus` (ClusterCache kind: the `Synced` condition + `LastSyncedAt`). Two live-but-unstored facts are **not** `Cluster` fields at all — a scheduling change and a recorded probe both fire no object `WatchList`, so folding them onto the list would force a re-emit on every backoff cycle. Instead each is its own per-cluster gauge/log watch: the **next-attempt countdown** streams via `clusterScheduleWatch` (beehive's `WatchSchedule`) and the **probe-outcome history** via the events surface (`clusterEvents`/`clusterEventsWatch`); see below.

**Connection-attempt history rides beehive's event log, exposed through a generic events surface — not a `Cluster` field.** The `ClusterCoreController` records each probe outcome via `ControllerClient.RecordEvent` under the `ConnectionEventCategory` (`"connection"`) category — Normal/`Connected` on success, Warning/`ProbeFailed`|`ResolveFailed` on failure. beehive coalesces consecutive same-`(category, type, reason)` outcomes into one aggregated **run** (`Event{ID, Count, FirstAt, LastAt}`, message/detail sampled latest-wins), so a flapping cluster reads as a compact transition timeline and a stuck-down one as a single high-count run. Retention is beehive's: `beehive.New(..., WithEventRetention(maxConnectionAttempts, 0))` bounds each cluster's timeline to the newest `maxConnectionAttempts` (20) runs, GC-swept.

**Generic events surface (`clusterEvents` / `clusterEventsWatch`).** Rather than a bespoke per-timeline type, the event log is exposed generically, keyed by object id: `service.events(ctx, client, id, category, limit)` reads a run timeline (newest first) and `service.watchEvents(...)` streams it as bare runs (snapshot then live, conflated per run id — the consumer **upserts by `Event.ID`**), both kind-agnostic (any beehive kind client satisfies the small `eventClient` interface; `ListEvents` is object-id-only, so a single reader serves every kind). The Cluster-kind entrypoints `ClusterEvents`/`ClusterEventsWatch` sit on `ClusterService`, backing the GraphQL `clusterEvents(id, category, limit): [Event!]!` query and `clusterEventsWatch(id, category): Event!` subscription. The **ClusterCache kind** has the exact parallel — `ClusterCacheEvents`/`ClusterCacheEventsWatch` (same generic `events`/`watchEvents` over `s.cacheClient`, keyed by the cache's own `ClusterCacheID`), backing `clusterCacheEvents(id, category, limit)` / `clusterCacheEventsWatch(id, category)` — carrying the cache-sync history the cache controller records under category `"sync"`. The domain `Event{ID ObjectID, Category, Type beehive.EventType, Reason, Message, Count, FirstAt, LastAt}` binds 1:1 to the GraphQL `Event` (its run `id` rides the shared `ObjectID` scalar — no dedicated event-id scalar; `type` binds straight to `beehive.EventType`, the same external-enum pattern as `ConditionStatus`). The subscription streams **bare** `Event`s (mirroring beehive's `WatchEvents`), not an ADDED/MODIFIED delta — the client's upsert-by-id makes the distinction redundant. This is what keeps per-probe chatter **off** the status watch: a repeated identical failure records an event (bumping a run's count) without rewriting `ClusterStatus` (the core controller skips the status write when `ClusterStatusEqual`), so a failing cluster does not churn its status/conditions every probe, and the probe history is fetched/streamed **per cluster** by whatever view wants it (the panel subscribes only while a row's diagnostics are open) rather than riding the whole-list `clustersWatch`. The frontend derives the `ok` boolean as `type === 'Normal'`.

**The next-attempt countdown rides a schedule gauge, not the list.** `Service.Watch` forwards the Cluster kind's `WatchList` as a delta stream (`Added`/`Modified`/`Deleted` per cluster) — it holds no per-cluster event or schedule watchers, and cache changes are on the **separate** `WatchCaches` stream, not folded in. The "Next check" countdown is a beehive **schedule gauge**: `beehive.Client.WatchSchedule(id)` streams `Schedule{NextRequeueAt}` as a latest-value gauge (current-on-subscribe, then on every (re)schedule — backoff step, `RequeueAfter`, poke, out-of-band `Requeue`), none of which fire the object `WatchList`. The service maps it (`scheduleWatch` → domain `Schedule{NextRequeueAt *time.Time}`, zero → nil) behind `ClusterScheduleWatch(id)`, exposed as the GraphQL `clusterScheduleWatch(id): Schedule!` subscription. Like `Event`, the wire `Schedule` type is **generic** (kind-agnostic) even though the entrypoint is kind-scoped. This is the only correct source for the countdown: only the scheduler knows authoritatively when the next reconcile moves, and it moves for reasons (poke, spec edit, out-of-band requeue) that no status/event proxy fully captures. **The gauge also carries an in-flight probe flag (`Schedule.Probing`, GraphQL `probing: Boolean!`)** so the webview can show a definite "checking now" during a probe rather than inferring it from a momentarily-absent `NextRequeueAt`. `Probing` is *not* a scheduler fact — it is owned by the `ClusterCoreController`, which `setProbing(id, true)` at the top of the eligible branch of `converge` and clears it via `defer` when converge returns (success, failure, or resolve error alike; it already holds `writeMu` across the whole probe). The controller fans each transition out over a `gochan/broadcast` hub (`WatchProbe(ctx, id) <-chan bool`, current-on-subscribe: a subscriber opening mid-probe sees `true`); `ClusterScheduleWatch` **merges** that stream with the beehive schedule gauge (`mergeSchedule` — re-emits the combined latest as either side moves, drops a closed sub-source without ending the stream). Because both sub-sources are current-on-subscribe, the merged subscription drives *both* the "Next check" countdown and the "checking now" state from one channel. (`coreController` — the service's seam over `*ClusterCoreController` — gained `WatchProbe`; the service holds the concrete controller so the merge reaches it directly.) The frontend's detail row subscribes to it (and `clusterEventsWatch`) only while open, so an idle cluster costs nothing. The ClusterCache kind's **spec** carries `ServerUID` — the kube-system namespace UID of the physical cluster that cache mirrors (the identity a migration turns over; named to match the `ClusterStatus.Server.UID` it is compared against). The domain `ClusterCache{ID ClusterCacheID, ClusterID, ServerUID, Status}` is a standalone record on the `WatchCaches` stream — `ID`+`ClusterID` locate the on-disk file and let the client join the cache onto its cluster (`ClusterID` is resolved from beehive's owner edge — `GetOwner` — in `buildClusterCache`), `ServerUID` marks which physical identity it mirrors. **Active-ness is deliberately *not* a field**: the active cache is the one whose `ServerUID` matches the cluster's last-probed `Status.Server.UID`, but that parent UID changes with *no* cache event (a migration flips it on the Cluster), so a per-cache stream could never keep an `Enabled`/active flag fresh — only the client's live join against the current `clusterStatus.server.uid` is correct, so the derivation is the client's. `Condition` is k8s-style `{Type, Status, Reason, Message, ObservedGeneration, LastTransitionTime}` (unprefixed shared vocabulary — the same type rides both the Cluster kind's status and the ClusterCache kind's, so it belongs to no single storage provenance), folded via `SetCondition` (apimachinery `SetStatusCondition` semantics); the wire exposes `Cluster.generation` so a consumer can compare it against a condition's `observedGeneration` for staleness. gqlgen binds the GraphQL `Cluster` straight to these types.
- **ClusterCoreController** (`core_controller.go`) — the connection/health controller, and the **owner of the kubeconfig source observation** (it writes `status.Source` live; the importer writes only the spec source reference). Each reconcile: observe the kubeconfig into `status.Source` (a departed context keeps its last-known names, `IsPresent=false`) → eligibility gate (`connectionEligible`: kubeconfig-sourced, freshly-observed present, enabled, not deletion-requested) → resolve credentials → identity probe (ServerVersion, kube-system UID, SelfSubjectReview) → `/readyz` health check, folding observations into the `Connected`/`Healthy` conditions and refreshing `Server`/`Principal`/`LastConnectedAt` on success. A probe failure is **returned as an error** (after the status write lands) so beehive applies its own exponential backoff — base 1s, ×2, capped at 2m via `WithMaxRetryInterval` at registration — and resets it on the next success; a success returns the ~30s health cadence via `RequeueAfter`. Out-of-band reprobes bypass beehive's worker, so their failures don't disturb the scheduled backoff. `probe`/`check` default to the real network implementations; tests inject fakes. After a **successful probe** (so the kube-system UID is known) it ensures a `ClusterCache` child exists for that identity (`ensureClusterCache`, idempotent via the UID-keyed slug's UNIQUE — concurrent reconciles can race the create; the child is created with the `kstack.io/cache-files` finalizer), then **prunes superseded caches** (`pruneSupersededCaches`: `ListOwned` the cluster's caches and request deletion of any whose `ServerUID` differs from the just-probed one). Both steps are **gated on a confirmed UID**, not eager: a never-probed cluster has no cache, and a transient disconnect (`Server.UID == nil`) never prunes — so a physical migration to a new UID creates the new identity's cache and deletes the old, leaving one cache per cluster. A create/prune error is non-fatal (logged; the next reconcile retries) so it doesn't lose the just-observed connection status. **Reconciles serialize on `writeMu` and re-read the object fresh under it**: beehive status writes carry no resourceVersion guard, so without this an out-of-band reconcile holding a stale snapshot could clobber the status-owned observation. It drives three **out-of-band** triggers from a single background worker (`StartBackground`/`StopBackground`) that `select`s over all sources, each re-running `Reconcile` in-memory (a controller writes status, not spec): (1) the **in-process retry bus** (`Reprobe(id)` → buffered `retryCh`), whose producers are the **connection sentinel** (see below) and **`Service.RetryConnection`** (the user-initiated "retry now"), both re-probing one targeted cluster out-of-band — backoff-neutral, since an off-worker reprobe failure never reaches beehive's scheduled backoff (it neither resets nor advances the ladder); (2) the **resync poke bus**, which on a poke (OS resume / network-on) re-reconciles every cluster; and (3) the **kubeconfig watcher** (subscribed here), which on a kubeconfig change re-reconciles every cluster so presence/isDefault updates promptly and the resulting status write wakes each `ClusterCache` dependent. The core controller folds the poke + watcher buses into this combined worker instead of the shared `pokeSubscription` helper (which the cache controller still uses via `StartPoke`/`StopPoke`); the `Service` sequences `StartBackground`/`StopBackground` around the beehive lifecycle. **Connection sentinel** (`connection_sentinel.go`): after a **successful probe** `converge` opens one long-lived liveness watch on the cluster's `kube-system` namespace (`ensureSentinel`, keyed by the connection-config fingerprint so a credential rotation restarts it; torn down by `stopSentinel` the moment the cluster goes ineligible / fails to probe). The controller reacts only to the **watch stream closing** — the earliest connection-loss signal — by firing one `Reprobe` and exiting; the re-probe re-confirms the connection and, on success, `converge` opens a fresh sentinel. A persistently-down cluster runs **no** sentinel (only beehive's backoff retries), so it never spins; a benign server-side watch timeout just triggers one idempotent re-probe. This makes fast connection-loss detection a property of the connection controller itself — **independent of whether sync is running** — which is why there is no cache-engine → connection hook. The sentinel goroutines anchor to `StartBackground`'s context and are joined in `StopBackground`. **HTTP/2 keepalive:** the composition root calls `cluster.ConfigureKubeHTTP2Keepalive()` once at startup (`internal/app`), tightening client-go's HTTP/2 connection health check (the `HTTP2_READ_IDLE_TIMEOUT_SECONDS` / `HTTP2_PING_TIMEOUT_SECONDS` env vars apimachinery reads, set only when unset so an operator override wins) from the 30s/15s default to 10s/5s — so a silently-dropped API-server connection is torn down in ~15s instead of ~45s, which is what makes the sentinel's watch close (→ re-probe) promptly.
- **ClusterCacheController** (`cache_controller.go`) — the cache-sync controller: converges a runtime map of **running engines** (keyed by the **ClusterCache's own ObjectID**, since a cluster can own several and the controller reconciles each independently) toward each record's spec. It finds its parent Cluster's ClusterID via the **owner edge** — `client.GetOwner(ctx, obj.ID)` (beehive's `owned_by`), not by parsing the cache slug — so identity comes from beehive's object graph. It adds a `DependsOn` edge to the parent Cluster (so a parent change re-queues it) **then re-reads the parent** — the edge now matters for both spec changes (e.g. `SyncEnabled` toggled) AND the parent's *status* writes, since eligibility's presence is read from the `ClusterCoreController`-written `status.Source` (beehive's `wakeDependents` fires on a status `Modified`, so the cache free-rides on the core controller's observation writes). Re-reading after `AddDependency` closes the race where the parent is stamped between the cache's first read and the edge being added. It runs an engine only for the **active** cache: it gates on `syncEligible` (`ConnectionEligible && SyncEnabled`) **AND** on this cache being the parent's current identity (`obj.Spec.ServerUID == parent.Status.Server.UID`) — a cache left behind by a migration is *paused* (no engine) in the brief window before the core controller's prune deletes it, so the engine never writes the new cluster's data into a stale identity's file. On its **deletion** path (`DeletionRequestedAt != nil`, set by a prune or a cluster cascade) it stops the engine, deletes the on-disk cache file via the `store.Manager`, then clears the `kstack.io/cache-files` finalizer so GC can collect the row — a file-delete error returns without clearing the finalizer, so the row lingers and the next reconcile retries (the file is never orphaned). When eligible+active it resolves credentials, computes `engine.ConfigFingerprint`, and starts/stops/restarts the engine — restart on fingerprint change (credential rotation). Sync is deliberately **not** gated on `Connected` (the engine owns its own dial/backoff). Engine outcomes land through a per-engine sink, folding the engine state into the `Synced` condition **and** recording transitions as beehive events on the ClusterCache's own timeline (`recordSyncEvent`, category `SyncEventCategory` = `"sync"` — the sync-side parallel of the core controller's connection-event history). The **condition** names the current state (`syncedCondition`: `Watching`→True/`Watching`, `Errored`→False/`SyncFailed`+LastError, `Stale`→False/`Stale`, `Syncing`→False/`Syncing`). The **event log** speaks a separate, transition-oriented vocabulary (`syncEvent`) in symmetric **start/complete pairs**: a cold build is `SyncStart`→`SyncComplete`, a resume is `ResyncStart`→`ResyncComplete`. The messages deliberately differ between the cold and warm paths to match what each actually did: a cold `SyncComplete` genuinely populated the cache, so it reports the object total ("cached N objects across M kinds in Ds"); a warm resume only re-opens watches (the objects it already holds stream back as deltas afterward — they are **not** re-fetched), so `ResyncStart` reports the *warm-cache size* it's resuming from ("N objects across M kinds, resuming watches from saved positions") and `ResyncComplete` reports the *completion state* — how many watches resumed, not an object total ("resumed watches for M kinds in Ds"), precisely so it can't misread as "processed N objects in 0s". A resume is **not always** a clean reconnect, though: per kind, a missing/expired resume cookie forces a full re-list (metadata-diff or LIST), so when some kinds did that real work `ResyncComplete` names it ("… — re-synced X objects in R of them — in Ds") — the true re-pulled delta, scoped to the kinds that re-listed, not the whole-cache total. All from the engine's `EngineStatus` facts `ColdStart`/`SyncedObjects`/`SyncedKinds`/`CaughtUpIn` plus `ResyncedKinds`/`ResyncedObjects` (the per-driver re-sync work — did the kind fall back to a full re-list, and how many bodies it re-pulled — aggregated across drivers onto the caught-up report; the warm-cache size for `ResyncStart` is read onto the `EngineSyncing` start report). Note "Syncing" is deliberately **not** an event reason (it stays a *condition* reason only — an event name would collide with the same-named condition state); the message is also what disambiguates `ResyncComplete`'s two shapes — a real catch-up vs a bare liveness recovery (counts cleared → "watch recovered, streaming updates again") — so no separate recovery reason is needed. A failure is `SyncDegraded`, a stalled watch is `SyncStale` (naming the wedged kinds and each one's cause — list-failed / watch-failed / watch-stalled), and a user-facing pause/ineligibility is `SyncStopped` (recorded from `converge`, not the sink, only on a real running→stopped transition). Unlike the connection side's `recordAttempt`, the sink records **only on a transition** (a change in the recorded `(type, reason)`, tracked on the `engineEntry`): the engine's ~30s freshness heartbeat re-reports the current state to refresh `LastSyncedAt` but does not append a redundant event, so a steady cluster is a single catch-up event (not a growing "Watching ×27"), while `LastSyncedAt` still updates on every report. **Staleness is watch-liveness, not data-recency:** the engine's per-run `livenessMonitor` flags `EngineStale` when a caught-up driver stops proving its watch is alive (no delta, bookmark, or reconnect) past `staleThreshold`, and recovers when liveness returns — so a quiet-but-healthy cluster (still receiving the API server's periodic watch bookmarks, which the driver taps ahead of RetryWatcher) is never flagged, only a silently-wedged watch is. (Hard connection loss is still **not** the cache controller's job: the `ClusterCoreController`'s own liveness sentinel catches it far faster, flipping the connection axis — there is no engine→connection re-probe hook.) It **subscribes to the poke bus** in its beehive `Start`: on a resync poke it restarts every live engine in place (`restartLiveEngines`, under `writeMu` so it serializes with reconcile + the sinks), reusing each engine's stored `restCfg` — the engines are in-memory runtime state the controller owns, so a poke needs no spec write. `Service.ClearCache` reaches the same path via the exported `RestartEngine(clusterID)` (restarts the cluster's live engine — its active cache) after deleting the cache files.
- **Kubeconfig importer** (`kubeconfig_importer.go`) — the kubeconfig-sourced creator and **sole creator of `Cluster` objects**, **creation-only**: it consumes watcher snapshots and, for every context not already referenced by a (non-deleting) `Cluster`, creates one with the deterministic slug `kubeconfig/{context}` (the context's natural key), writing only the `Source` reference. The deterministic slug means beehive's per-kind slug-uniqueness rules out a duplicate even under a concurrent create. It never updates, orphans, or deletes — a departed context is orphaned by the `ClusterCoreController` flipping `status.Source.Kubeconfig.IsPresent=false`, and a returning context reuses its never-deleted `Cluster` (the importer finds it by context and skips re-creation). An already-tracked snapshot writes nothing. A pure beehive writer — it doesn't know `ClusterCoreController` exists; its `Start`/`Stop` are owned by `Service`. (Today it enumerates via `List()` + a context match; a future `cloud/` source would scope by slug prefix — deferred until a second source exists.)
- **Per-cluster cache** (`internal/cluster/cache/store`) — one SQLite file per cache incarnation at `<dataDir>/clusters/<ClusterID>/<ClusterCacheObjID>.db`, addressed by a `store.CacheRef{ClusterID, CacheID int64}` of the parent `Cluster` and `ClusterCache` **beehive ObjectIDs** (the ids are `AUTOINCREMENT`, so a delete+recreate yields a fresh, never-reused file with no finalize-vs-recreate race). Pure-Go modernc driver, WAL; single-conn writer pool + 4-conn reader pool, owned by a `Manager` (`Open(ctx, CacheRef)`/`Lookup(cacheID)`/`WatchDB(cacheID)` (a latest-value stream of a CacheID's open handle across its lifecycle — current-on-subscribe (nil when not open), then a fresh value on open/close/replace; long-lived readers like `ClusterDataKindsWatch` use it to bind to a cache that opens *after* they subscribe or rebind when it's swapped, instead of binding once to `Lookup`)/`CacheBytes(CacheRef)` (stat-only, works closed)/`ResourceStats`/`Kinds` (the discovered `kind_catalog` rows, backing `ClusterDataKinds`)/`Events(ctx, limit)` (the newest cached events, ordered by `last_seen DESC`, flattening the involved-object identity — backs `ClusterDataEventsWatch`)/`Objects(ctx, apiVersion, resource)` (one kind's cached objects — the universal-identity `ObjectRow` projection, `resource`→`kind` translated via a `kind_catalog` subquery, ordered by `(namespace, name)`; backs `ClusterDataObjectsWatch`)/`DeleteCacheFiles(ctx, CacheRef)` (also reaps the now-empty per-cluster dir)/`Shutdown`). Each `ClusterDB` carries **two independent coalescing write-notify brokers** (one `notifyBroker` type, reused): `ObjectsSubscribe`/`ObjectsNotify` for object writes (drives the kind-catalog and objects watches — kinds are a read projection of object writes) and `EventsSubscribe`/`EventsNotify` for event writes (drives the events watch) — kept separate so an event burst never wakes the object-write re-reads. The service resolves the **active** cache's `CacheRef` from a domain `ClusterID` (`cacheRef` helper): the `ClusterID` *is* the parent Cluster's ObjectID (the directory), and the file id is the `ClusterCache` for the cluster's currently-connected identity — found by reading the parent's `Status.Server.UID` and looking up the slug `{ClusterID}/{serverUID}` (no `caches/` prefix: ClusterCache is its own beehive kind, so its slugs already sit in a disjoint namespace). `newCacheRef(clusterObjID, cacheObjID)` is the one `beehive.ObjectID→int64` conversion point (keeps the leaf `store` beehive-free). The live-stats resolver instead builds the `CacheRef` straight from the domain `ClusterCache{ClusterID, ID}` it already holds, so per-cache stats need no slug lookup. Open runs an integrity check (corrupt → quarantined as `.corrupt-<stamp>`), migrations (its own embedded sequence — agent-optimized schema: universal `objects` + `owner_refs`/`labels`/`status_history`/`events`(+FTS)/`kind_catalog`/`kind_counts` (per-kind object counts kept exact by triggers on `objects`, so the dashboard nav's counts read O(kinds) instead of a grouped scan)/`cluster_meta`; `raw_json` zlib-compressed, Secrets redacted before persist), and a per-cluster janitor (status-history TTL sweeps + incremental vacuum — events are **not** janitor-managed; their retention is server-mirrored by the sync engine's relist prune). The cache never owns syncing — engines are the cache controller's.
- **Sync engine** (`internal/cluster/cache/engine`) — mirrors one cluster into its cache for as long as it runs; the cache controller starts/stops it (`NewEngine(restCfg, cdb, sink)`/`Start`/`Stop`). A supervised run walks `/apis` discovery and drives one `kindDriver` per GVR. The design is **watch-for-latency, poll-for-correctness**: the watch path makes the steady state fast and is allowed to be lossy, while two pull-based backstops guarantee correctness, so known edge cases (a denied watch, a dropped delta, a stale resume cookie, a built-in API surface change) are permitted to slip through and self-heal within one interval instead of being closed by exact, stateful edge-handling.

  **Per-kind driver (`kindDriver`).** Built instead of a raw Reflector so a wake resumes cheaply: at driver start it seeds a RetryWatcher from the kind's persisted resourceVersion (`cluster_meta` resume cookie); on any watch drop/410 thereafter it falls back to a metadata-first `fullResync` (list metadata, GET only changed bodies, delete vanished — or a full LIST when cold/large). The full LIST is **paginated** (`fullList`: `opts.Limit` = `listPageSize`, looping on the `Continue` token) and **streamed page-by-page** into the store through a `replaceSession` (`store.BeginReplace`), so a whole kind's bodies never sit in memory at once, and a `Continue`-token 410 mid-pagination (`listExpired`: `ResourceExpired` or a bare `Gone`) discards the partial pass and re-lists from the top with a fresh session (bounded by `maxListRestarts`); once that budget is spent — a token that keeps expiring at the same point, a kind whose full paginated pass outlives the token lifetime — `fullList` returns `errListRestartBudget` rather than loading the whole kind unpaginated (that would defeat the memory bound and can OOM on a multi-million-object kind). The caller's **per-kind error budget** then surfaces the kind to the user (see the error budget below) instead of retrying a heavy LIST forever. Pagination bounds one kind's LIST to a page; a **run-level `listLimiter`** (`engine.go`, cap `listConcurrency`, 16) bounds how many drivers LIST *at once* — `fullResync` acquires a slot around its list-heavy work (the metadata list + body pages) and releases it before re-entering the indefinite watch phase, so cold-start peak memory is O(N pages) regardless of kind count instead of the sum of *every* kind's in-flight LIST. The **one** limiter is shared by every driver the run starts — the initial cohort *and* mid-run discoveries (both go through `startDriver`) — and gates the periodic resync too, so a CRD bundle installing mid-run or a resync herd can't blow the ceiling; a queued driver just waits its turn (a little cold-start latency for a flat memory ceiling). A slot can't be held forever, but the bound is **read-inactivity, not wall-clock**: every engine client (discovery + dynamic + metadata) is built from a config wrapped with an `idleTimeoutRoundTripper` (`idle_timeout.go`, `defaultListIdleTimeout` 2m) that cancels a request only when it makes **no read progress** for the window — response headers, then every body chunk, count as progress (bumping an atomic counter that a self-rescheduling watchdog checks each tick; because the watchdog re-arms itself and reads never touch the timer, there's no `AfterFunc` Reset-vs-fire hazard, at the cost of coarse [timeout, 2×timeout] detection). So a *wedged* LIST/GET (nothing arriving) is cancelled → its driver errors, releases its slot, and Run backs off (no starving other drivers), while a **slow-but-progressing** transfer — a consistently slow API server, an expensive/huge kind — runs to completion no matter its total duration. This is why the timeout is at the transport (it can watch bytes) rather than a per-call deadline in the driver (which can't tell a slow page from a stalled one). Discovery gets it too: a hung `/apis/<group>/<version>` (a registered-but-unreachable aggregated APIService) would otherwise block the whole run/reconcile. **Watch requests are exempt** (`watch=true`): they're legitimately quiet between bookmarks, and the same dyn/md clients serve them. A session needs no teardown — every unsuccessful `fullList` exit (non-410 error, WritePage/Commit failure, exhausted restart budget) just drops it. Whether a session **prunes** rows absent from the LIST is a per-kind choice: `objectsReplaceSession` accumulates the union of every page's uids and `Commit` reconciles the `(kind, api_version)`-scoped rows to it (delete-missing) — the cache should mirror the cluster, and a partial pass just leaves its committed pages for the *next* pass's prune to reconcile (no per-row rollback needed). `eventsReplaceSession` prunes too, mirroring the server: it accumulates each page's uids and `Commit` reconciles the **whole events table** (not `(kind, api_version)`-scoped — Event is a single kind owning that table) to their union, so an event the apiserver has already GC'd is dropped and the cache reflects the cluster's *current* event set. Event retention is therefore whatever the server enforces (`--event-ttl`, which varies per cluster — no local window); the janitor no longer sweeps events. A row's exits are the relist prune, an explicit watch `Deleted` (`ApplyChange`), or the two combined. (Keeping longer history than the server is deferred to a future archiving feature that persists *interesting* events to a **separate** store outside the pruned set — not a longer TTL on this table.) The two cookie writes (`last_list_rv` + `last_list_at`) are still one transaction per `Commit` regardless of pruning, so a failed persist can't leave `last_list_rv` durably advanced (which would resume the next watch from a newer RV and skip the Added events/deltas before it). Per-page commits trade the relist's single-transaction atomicity for the memory bound (a warm large-churn objects relist is briefly observable mid-stream; a cold cache observes nothing). The **object-level backstop** is a per-driver periodic resync (`resyncPeriod`, 30m, jittered per kind — `resyncDelay`, computed once at construction off a GVK hash via `gvkJitterFraction` so drivers don't relist in lockstep): a watch alive that long ends itself so `Run` re-syncs, reconciling any drift the watch missed. Cheap wakes are preserved — only the slow periodic tick relists; a poke-driven restart still resumes from the cookie. Two complementary guards keep a stale cookie from resuming past missing data. (1) A **completion invariant**, owned by the store: a `replaceSession`'s first `WritePage` durably deletes the resume cookie in the same transaction as the first rows and `Commit` rewrites it only on success, so for objects the cookie means "a full LIST completed on disk" — a pass that fails after writing a page leaves no cookie, so the next start cold-LISTs (its prune reconciling the partial pages) instead of resuming from an RV that no longer matches the half-written rows (a warm big-delta relist that fails this way drops to cold next time — correctness over latency, bounded by `resyncPeriod`). Clearing on the first write, not on `BeginReplace`, means a pass that fails **before any page is written** (the first LIST errors, an app quit) leaves the untouched snapshot's cookie intact, so it still resumes cheaply — a stale cookie and partial durable state can never coexist. A straggler watch **bookmark** can't resurrect a just-deleted cookie either: its tap runs in `watch.Filter`'s un-joined forwarding goroutine, so `onBookmark` persists only while its captured **watch epoch** is still current (bumped when `watchPhase` returns, under the driver's `cookieMu`, before `Run` reaches `fullList`), fencing a straggler from writing into a replace session. For events the clear is now load-bearing the same way: since an events relist prunes, a pass that fails after writing pages but before `Commit` leaves no cookie, so the next start cold-LISTs and its prune reconciles the leftover rows instead of resuming past them. (2) A **resume-eligibility guard** on the seed read: `startDriver` seeds from `kindStore.ResumeRV`, which returns the cookie only when the store still holds the kind's data to apply deltas onto — `objectsStore` gates the cookie read on object existence in one indexed query (a cookie that outlived *all* its objects, a kind removed then re-added with no intervening `fullList`, returns "" → cold full-LIST), while `eventsStore` (its own table) resumes straight. Keeping both the "did a sync complete?" and "should I resume?" decisions on the store — not a GVK special-case in the engine — mirrors the `metadataDiffStore` capability pattern. **Per-driver liveness:** each driver stamps `lastLiveAt` only on a real watch-alive proof — a successful watch **establishment** (`onConnect`), a delta, or a **watch bookmark** (RetryWatcher swallows bookmarks, so the driver taps the underlying watch via `watch.Filter` *ahead* of it — bookmarks also advance the resume cookie). It is NOT stamped merely on entering the watch phase: a kind that can LIST but never WATCH would otherwise refresh its liveness every backoff cycle and hide as healthy — instead its `lastLiveAt` never advances (and the error budget marks it stuck).

  **Mid-run discovery — two layers, one reconcile path.** Discovery is not one-shot. (1) A best-effort **accelerator**: `watchDiscoveryTriggers` runs one RetryWatcher per `discoveryTriggerGVRs` entry — `CustomResourceDefinition` and `APIService` (the objects that mint GVRs; `/apis` itself isn't watchable) — and `watchTriggerSource` signals a re-discovery **only on a delta** (Added/Modified/Deleted). It carries no correctness obligation, so there is no denial/recovery/410/startup-gap state: a denied or idle watch just backs off (a working watch resets it) so it can't hot-loop the API server. (2) The authoritative **backstop**: `discoveryPollLoop` fires the same trigger every `discoveryPoll` (5m) regardless of watch activity, so anything the watches miss — including built-in API surface changes with no watchable object — is reconciled within one interval. Both feed a coalescing cap-1 trigger channel that `discoveryLoop` debounces (`discoveryDebounceDefault`, 1s trailing window, so a CRD bundle collapses into one pass), then **`reconcileDiscovery` runs a SINGLE pass** (no internal retry): it launches a driver for any served GVR not running; **repoints** a driver whose GVR changed under a stable GVK (a CRD recreated under a new resource plural) by `drivers.remove` + relaunch **cold** (`forceCold` → full LIST of the new endpoint). The repoint is the one case the resume guard can't cover — the old rows survive under the same GVK, so `ResumeRV` would still see them — so it **durably deletes the resume cookie** (`deleteResumeRV`) before relaunching: `forceCold` keeps *this* run cold, the cookie delete keeps it cold across a restart in the relaunch window (a failed delete falls back to the resync). It also **transfers the old driver's catch-up token to the replacement** (rather than firing it) so the milestone waits for the replacement's own full LIST instead of reporting Watching while the old endpoint's rows are still present. And, **only on a complete discovery** (`discoverGVRs` returns a completeness flag; removal/prune gate on it so a transiently-down API group doesn't churn live drivers), stops the driver for any vanished kind and prunes its rows + resume cookies (`pruneOrphanedObjects`, best-effort — a failed prune is re-run next complete pass). A partial or errored pass launches what it saw and returns; the next trigger or poll re-walks. `discoverGVRs` refreshes `kind_catalog` (truncate-rewrite on a complete pass, upsert-preserve on a partial one) and `cdb.Notify()`s so the dashboard-nav watch sees CRD installs/removals.

  **Catch-up milestone.** The run's drivers live in a `driverSet` (GVK-keyed handles + a WaitGroup). `remove` is synchronous — it cancels the driver's child context and blocks on `done` until the goroutine stops (so a later prune can't be undone by an in-flight write), then returns the driver's **catch-up token** (`*milestoneToken`, minted by `milestone.token`, one per initial kind, `nil` for a mid-run kind that owes nothing). The token is **re-gate-able**, not a bare one-shot: a kind **resolves** — caught up (`onWatch` → `resolve(true)`), gone stuck (`onStuck` → `resolve(false)`), or removed (`resolve(false)`) — and all three release its gate, but a resolved token can transition again (all state under `milestone.mu`). The milestone's `pending` counts tokens still **holding** the gate and fires **once**, when it hits zero, via `reportCaughtUpOrStale`. Whether it reports Watching or Stale is decided at fire time from **live driver state** (not the tokens); the `SyncComplete` **kind count** is the milestone's own `caughtUp` tally — how many tokens are **currently** resolved by reaching a watch. It is deliberately **not** a `kind_catalog` `COUNT(*)`: at milestone time the catalog isn't the synced set — a partial initial discovery preserves rows for unavailable API groups whose drivers never started, and a mid-run discovery lands a tokenless kind before the cohort finishes, both of which would inflate a raw count. **Why re-gate-able and not a one-shot:** a stuck token releases the gate (so a permanently-broken kind can't wedge Syncing) yet a stuck *initial* kind can still change before the milestone fires — it can **recover** (a later `onWatch` retroactively counts it, so `caughtUp` isn't undercounted) or be **repointed** (`rearm()` re-holds the gate for the never-watched replacement). A one-shot got both wrong: it dropped the late recovery, and — worse — transferred a stuck kind's spent release to the replacement, letting another kind's resolution fire a **false `EngineWatching`** while the replacement was still listing. The stuck path also keeps a kind that can never sync (forbidden, un-paginatable) from wedging Syncing forever — it releases the gate so the cohort resolves. But "resolved" isn't "synced": if a stuck kind closed out the milestone, the engine reports **`EngineStale` naming it directly** (never a false `EngineWatching`/`SyncComplete` that the monitor would only correct one tick later, decided freshly from driver state, not the tokens); only a fully-healthy cohort reports `EngineWatching`. Either way `caughtUp` closes, handing the stale↔recovered tracking to the `livenessMonitor` — which **seeds its baseline from the state the milestone published** (the current `StaleKinds`), so if that stuck kind recovers before the monitor's first tick it still emits the recovery instead of leaving the engine wrongly Stale. A vanished kind resolves its token gone **after** the prune (so the catch-up report reflects the pruned cache and surviving cohort); a repoint **transfers and `rearm()`s** the old token onto the replacement, so a repoint mid-catch-up can't report Watching before the replacement's full LIST lands — even when the old driver had already resolved (caught up, or stuck and released), rearm re-holds the gate (and drops any caught-up count) until the replacement re-earns it; a still-unresolved or nil token needs no special handling. A kind discovered mid-run joins after catch-up (nil `onWatch`) and is surfaced the same way if it gets stuck. **Per-kind error budget:** each driver counts consecutive sync failures — a failed `fullResync` (a forbidden LIST, `errListRestartBudget`, an idle-timeout-cancelled request) **or a `watchPhase` that never established its watch** (list-but-not-watch RBAC, an aggregated API rejecting watch — since LIST alone can't keep the cache current); after `defaultStuckThreshold` (5) `markStuck` sets an atomic flag (surfaced by the liveness monitor) and fires `onStuck` (Run fires it once per stuck episode on the exact threshold crossing; it calls the token's `resolve(false)`, idempotent per state), and the retry drops to a slow cadence (`defaultStuckRetryInterval`, 3m) so a broken kind stops hammering the API server and re-taking a limiter slot every backoff step. The flag clears the moment a watch next **establishes** (`onConnect`) — not on a bare LIST success, so a list-but-not-watch kind can't flap stuck↔clear every loop. **`staleLaggards`** flags a driver two ways, each carrying a **cause**: it's **stuck** (`isStuck`) — reporting the phase that spent its budget (`CauseListFailed` if it couldn't LIST, `CauseWatchFailed` if it could LIST but never established a watch — recorded per failure via the driver's `failCause`/`stuckCause`) — or its watch was live but went quiet past `staleThreshold` (`CauseWatchStalled`, a wedged watch). A never-watched-but-not-stuck driver is legitimately still syncing (a large but progressing LIST — the idle timeout lets it run arbitrarily long) and is **not** flagged. The `livenessMonitor` reads this across drivers after catch-up and reports `EngineStale` — `StaleKinds` a `[]KindStatus` (kind + cause) — when the set is non-empty, recovering to `Watching` when it clears, so a kind that never synced *and* a silently-wedged watch both surface, while a quiet-but-healthy or slow-but-progressing kind never false-alarms. The cache controller renders each cause into the `SyncStale` message per kind (`staleMessage` → "Not receiving updates for Pods (watch failed), Endpoints (watch stalled) — cache may be behind"), so a list-but-not-watch RBAC gap is actionable rather than a bare kind list; the condition **reason** stays the coarse `Stale` — the cause lives in the per-kind detail, not a new reason.

  **Reporting.** The engine reports coarse state through its `Sink` (`Syncing` → `Watching` → `Errored`/`Stale` + capped retry); the `Watching` catch-up report carries `ColdStart`/`SyncedObjects`/`SyncedKinds`/`CaughtUpIn` plus `ResyncedKinds`/`ResyncedObjects` (per-driver `didResync`/`resyncObjects`, aggregated at the handoff), which the controller turns into event messages. `onWatch` never fires before the watch is proven live, and both proofs start from the watch **connecting** (`onConnect`): on the re-sync path (cold start, or re-entry after a 410) the fresh RV can't 410, so *connecting* is the catch-up proof — fired on connect, *not* on watch-phase entry, since firing early would retire the token for a list-but-not-watch-RBAC kind that has no watch; on the cookie-resume path connecting isn't enough (an accepted watch can still 410 the expired cookie), so it arms a `resumeGrace` (2s) **from the connection** and fires on the first delta or a quiet grace with no 410, skipping the fire entirely if the watch 410s first. Arming the grace from `onConnect` rather than phase entry is load-bearing: a slow or denied watch that never connects can't fire a false clean-resume while no watch exists. And because RetryWatcher retries retriable errors (5xx/EOF) internally without ever closing its `ResultChan` — and a hung watch request never returns headers — each watch phase bounds the wait for the connection with an **establishment timeout** (`defaultEstablishTimeout`, 30s, disarmed the moment the watch connects): on timeout the phase returns `errWatchNotEstablished` so Run charges `CauseWatchFailed`, and a persistently-unconnectable kind surfaces as **stuck** rather than blocking the driver forever and wedging the engine in Syncing (a post-connect reconnect wedge stays the liveness monitor's job). This is a monitoring app: a watch that can't establish is surfaced to the user via the error budget, not retried indefinitely. Either way an expired-cookie re-list isn't mis-logged as a clean reconnect, and a WATCH-forbidden or never-connecting kind surfaces as stale rather than a false Watching. The one `stepBackoff` step is shared by the driver, the run loop, and the trigger watch. `ConfigFingerprint` hashes a rest.Config's connection/auth fields (+ kubeconfig proxy-url) — the controller's restart trigger.

The GraphQL `Cluster` mirrors beehive's owner chain (the schema **is** the domain shape — see gqlgen.yml's bindings, every GraphQL type pointing at the identically-named `internal/cluster` type, no wrapper): `spec`/`status` bind directly to `cluster.ClusterSpec`/`cluster.ClusterStatus` (the stored Cluster-kind status, served as-is). The `Cluster` type has **no** `caches`/`activeCache` fields — a `ClusterCache` is its own top-level entity, streamed via `clusterCachesWatch` and bound to `cluster.ClusterCache`, carrying its identity (`id`, `clusterID`, `serverUid`), the ClusterCache kind's `status` (sync conditions + `lastSyncedAt`), plus live on-disk `stats` (a **resolver** on `ClusterCache`, so a query only pays the stat cost when it selects them; it reads the cache's own `id` + `clusterID` for the lookup). The client joins caches onto clusters by `clusterID` and treats the cache whose `serverUid` matches the cluster's `status.server.uid` as the active one. `ClusterSpecSource`/`ClusterSpecSourceKubeconfig` (spec, on the `ClusterSpec.Source` field — 1:1 autobind, no gqlgen `fieldName` override) and `ClusterStatusSource`/`ClusterStatusSourceKubeconfig` (status) bind directly, so the source union is on the wire as nested nullable objects. **The conditions go on the wire as-is**: `status.conditions` and each cache's `status { conditions, lastSyncedAt }` bind straight to `cluster.Condition`/`cluster.ClusterCacheStatus`, and the webview derives display state from type/status/reason — there is no projection layer. `ClusterCacheStats`/`ClusterCacheResourceStats` bind to `cluster.ClusterCacheStats`/`cluster.ClusterCacheResourceStats`. **Every cluster resolver delegates to `r.ClusterSvc` (`cluster.ClusterService`)** — they are one-liners: `clusters`/`cluster(id)` → `List()`/`Get()`; `clustersWatch` → `Watch()` and `clusterCachesWatch` → `WatchCaches()` (the two independent delta watches — an `Added` snapshot then per-object `Added`/`Modified`/`Deleted`, each adapted value→pointer through `mapStream`); a cache's `stats` → `CacheStats(clusterID, cacheID)` (per-cache); `clusterDataKinds(id, cacheID)` → `ClusterDataKinds(clusterID, cacheID)` (one ClusterCache's discovered kind catalog — apiVersion/kind/resource/scope/isCRD, plus a per-kind `count` (a point LEFT JOIN of `kind_catalog` against the trigger-maintained `kind_counts` aggregate — so an advertised-but-empty kind counts 0 and the read is O(kinds), never a scan of `objects`) that backs the object counts in the dashboard nav — read on demand from that cache's `kind_catalog`, **per-cache like `CacheStats`**: keyed by parent cluster id + the cache id (typically the active one), so a cache/identity swap under the same cluster reads the *new* cache's catalog and lets the webview reject stale results by cache id; empty when that cache's db isn't open (never-synced / paused), since only a running engine populates + holds it open) and its live counterpart `clusterDataKindsWatch(id, cacheID)` → `ClusterDataKindsWatch(clusterID, cacheID)` (**the dashboard nav's real-time source** — the same per-cache catalog as a Kubernetes-style delta watch: an `Added` burst on subscribe, then `Added`/`Modified`/`Deleted` per kind, each change carrying its cache's `cacheID` as provenance (so the webview can reject a late frame from a superseded cache after a cache/context switch rather than inferring provenance from render state). The service takes the store's coalescing `ObjectsSubscribe()` and, on each write ping (debounced by `dataKindsDebounce` — a short trailing throttle so a high-churn cluster can't drive a re-read + emit per object event), re-reads `Kinds` and diffs it against the last snapshot it emitted, keyed by `apiVersion`+`resource`; since `count` tracks the trigger-maintained `kind_counts` aggregate (no object scan), an object write bumps the counter and re-emits its kind as `Modified`, so the frontend's kinds *and* counts stay live. The engine's discovery pass pings too: `discoverGVRs` calls `cdb.ObjectsNotify()` after its truncate-and-rewrite of `kind_catalog` (+ the orphan-kind prune), so a CRD installed/uninstalled between runs — most visibly on an in-place engine restart, where the db handle doesn't change and no object write need follow — surfaces as Adds/Deletes without waiting for an unrelated write to ping. The stream **follows the cache db across its lifecycle** via the store `Manager.WatchDB(cacheID)` (a latest-value handle stream — current-on-subscribe, then a fresh value on open/close/replace) rather than binding once to `Lookup`: a subscriber that opens the stream *before* the sync engine opens the cache (the common unsynced-cluster case) binds when the db opens, and a Clear-cache delete+reopen under the same CacheID rebinds to the new handle and keeps diffing (the emptied catalog surfaces as Deletes, the rebuild as Adds). An unopened cache db simply emits nothing until it opens or ctx ends, matching `ClusterDataKinds`' empty posture); `clusterDataEventsWatch(id, cacheID)` → `ClusterDataEventsWatch(clusterID, cacheID)` (**the dashboard events table's real-time source** — one ClusterCache's cached Kubernetes Events (the synced `events.k8s.io`/core Event rows, *not* kstack's own `Event`/`clusterEvents` control-plane timeline) as a Kubernetes-style delta watch: the newest window (`store.Events`' default limit, 500) as an `Added` burst, then `Added`/`Modified`/`Deleted` per event keyed by `uid`, each frame carrying its `cacheID` provenance like the kind watch. It shares one generic engine with `ClusterDataKindsWatch` — `cacheDeltaWatch[T]`, which owns the WatchDB cache-lifecycle rebind + coalescing-debounce loop; the two differ only in which store broker they follow, what they read, and the key. Events use a **separate** store broker (`EventsSubscribe`/`EventsNotify`, distinct from the object-write `ObjectsSubscribe`/`ObjectsNotify`) so an event burst wakes only this watch, never the kind-catalog re-read — the whole reason event writes don't ping the object-write broker. Because the read is a bounded window, an event aging out of it as newer ones arrive surfaces as `Deleted`; acceptable for a "latest events" table, and filtering will make it cleaner. Debounced by `dataEventsDebounce` (500ms, coarser than kinds since events are the highest-volume stream). **Open Kubernetes semantics, deliberately not the control-plane `Event`'s closed shape:** `ClusterDataEvent.type` is a plain `String!` (not the `EventType` enum) — k8s doesn't constrain `Event.type`, so an omitted/custom value passes through verbatim instead of producing an out-of-schema enum value; and `firstSeen`/`lastSeen` are **nullable** `Time` via field resolvers (`nilIfZeroTime`) — the domain keeps value `time.Time` (comparable, required by `cacheDeltaWatch`'s diff), so the resolver maps the zero time (a source Event with no timestamp) to null rather than serializing `0001-01-01`); `clusterDataObjectsWatch(id, cacheID, apiVersion, resource)` → `ClusterDataObjectsWatch(...)` (**the dashboard's per-kind object tables** — a Kubernetes-style delta watch of one kind's cached objects, keyed like the kind/events watches **plus** the target kind: an `Added` burst on subscribe, then `Added`/`Modified`/`Deleted` per object keyed by `uid`, each frame carrying its `cacheID` provenance. `ClusterDataObject` carries **only its typed universal identity for now** (`uid`/`apiVersion`/`kind`/`namespace`/`name`/`creationTimestamp` — enough for a Name/Namespace/Age table); `creationTimestamp` is a **nullable** `Time` field resolver (`nilIfZeroTime`, shared with the event timestamps and hoisted to `graph/util.go` so gqlgen doesn't relocate it). The **nested object body** — and the kind-specific columns derived from it — is a deliberate follow-up (see the "ClusterDataObject — native nested body" item in `TODO.md`: ship the full native object as a JSON scalar rather than server-computed table cells). It mirrors `ClusterDataEventsWatch` — a `cacheDeltaWatch` over the **object-write** broker (`ObjectsSubscribe`, the same broker the kind catalog follows) re-reading `store.Objects(apiVersion, resource)` on each debounced ping (`dataObjectsDebounce`, 250ms), projecting each row to a `ClusterDataObject` keyed by `uid`. The store translates the plural `resource` to its `kind` via a `kind_catalog` subquery (the `objects` table is keyed by `kind`) and orders by `(namespace, name)`. Because only the object's **immutable identity** is projected today, a diff never fires `Modified` (uid/apiVersion/kind/namespace/name/creationTimestamp don't change under a stable uid) — an in-place edit surfaces nothing until the nested body ships; rows update on `Added`/`Deleted`. Empty posture matches the kind/events watches (no open cache → no frames, closes on ctx). `clusterEvents`/`clusterEventsWatch` → `ClusterEvents`/`ClusterEventsWatch` (the generic per-cluster event timeline, decoupled from the list watch) and the ClusterCache-kind parallel `clusterCacheEvents`/`clusterCacheEventsWatch` → `ClusterCacheEvents`/`ClusterCacheEventsWatch` (the per-cache sync-event timeline, decoupled from `clusterCachesWatch`); `clusterScheduleWatch` → `ClusterScheduleWatch` (the generic reconcile-schedule gauge / next-attempt countdown, also decoupled from the list); `clusterEnabledSet` → `SetEnabled`; `clusterSyncEnabledSet` → `SetSyncEnabled`; `clusterConnectionRetry` → `RetryConnection` (returns immediately; the outcome lands on conditions and reaches the webview through the cluster watch); `clusterCacheClear` → `ClearCache` (delete cache files + restart the engine to rebuild); `clusterDelete` → `Delete` (delete the `Cluster` so GC cascades to `ClusterCache`; if the kube-context still exists the importer re-creates it — same `kubeconfig/{context}` slug, but a fresh `ClusterID`/ObjectID, since it is a new record). The resolver field is named `ClusterSvc` (not `Clusters`) to avoid shadowing the generated `queryResolver.Clusters` method. `graph/model` holds only the gqlgen-generated `models_gen.go` plus a permanent stub `models.go` (just the package clause) that keeps the package non-empty across regen. The frontend joins the two delta streams in `src/lib/clusters.tsx`: `ClustersProvider` reduces `clustersWatch` and `clusterCachesWatch` into id-keyed maps (via urql's `useSubscription` accumulator, Added/Modified upsert, Deleted removes) and derives each row's `activeCache` client-side (the cache whose `serverUid` matches the cluster's `status.server.uid`), so `useClusters()` still exposes a Kubernetes-shaped `Cluster` with `spec`/`status`/`activeCache`. `cluster-sync-panel.tsx` renders that as a grouped Active/Orphaned table keyed on `status.source.kubeconfig?.isPresent`, with a "pending" row state derived from `status.server.uid == null`, an enable/disable toggle (`clusterEnabledSet`), and a sync play/pause (`clusterSyncEnabledSet`); the kube-context picker (`kube-config.tsx`) shows only `spec.enabled` + present records. Both status columns are **expandable disclosures** sharing one `EventRunList` (a newest-first, upsert-by-id run list): the **connection** label opens a `ConnectionDetail` (uptime, next-check countdown, "Recent attempts" from `clusterEventsWatch(category:"connection")` + `clusterScheduleWatch`), and the **sync** label — a disclosure only when the row has an `activeCache` — opens a `SyncDetail` showing a live **freshness line** (`activeCache.status.lastSyncedAt` as "last update received Ns ago"), an amber **"Possibly stale"** banner when the `Synced` condition reason is `Stale` (engine-derived — the client never infers staleness from `lastSyncedAt` age), and the "Recent sync events" transition log from `clusterCacheEventsWatch(id: activeCache.id, category:"sync")` (reason codes mapped to friendly labels — `SyncComplete`→"Initial sync complete", `ResyncStart`→"Starting re-sync", `SyncStale`→"Watch stalled", etc.). The sync column itself reads `Stale` (amber) off that condition reason. Each per-row subscription mounts only while its detail is open, so idle clusters cost nothing.

The data dir (`--data-dir` / env `KSTACK_DATA_DIR`) is **required** — `app.New` errors when it's empty; the Tauri host wires its `app_local_data_dir()`, tests supply `t.TempDir()`. `<data-dir>/app.db` is **owned by `internal/appdb`**, which opens it, holds its one migration sequence, and hands the `*sql.DB` to feature packages (a SQLite file has a single `schema_migrations` sequence, so its schema can't be co-owned; add a new app-level table as a numbered migration in `appdb/migrations/`, not as a second embed against the same file).

## Auth / identity (`internal/auth`) — the local-first lower layer

User accounts backed by kstack-cloud's Hydra OAuth server (`https://oauth.kstack.sh/`). The whole flow is **sidecar-owned**: the sidecar opens the system browser (auth-code + PKCE, ephemeral loopback redirect), runs the loopback listener, exchanges + verifies the code, **and persists the refresh token in the OS keyring itself** (via an internal `keyringStore` over `zalando/go-keyring` — loopback OAuth already pins the browser to this machine, so there's no host round-trip and **no gRPC credentials channel**). This is **local-first**: a user stays signed in offline — identity is read back from a locally-stored ID token, and a present refresh token is what marks "signed in." It's deliberately **independent of the cloud settings feature**: the settings-sync subsystem (`internal/cloud`) depends on `auth` (for an `oauth2.TokenSource` and the latest-value session `State` stream), **not the reverse**. Like `cluster`/`cloud`, it's fronted by one composition owner and **degrades** when neither a keychain service name nor a credentials store is configured (signed-out, login errors, logout is a no-op, `TokenSource()` nil). The composition root (`internal/app`) configures auth by name, not by wiring (`main.go` passes `OAuthIssuerURL`/`OAuthClientID` — from `KSTACK_OAUTH_ISSUER`/`KSTACK_OAUTH_CLIENT_ID` — plus the keychain service name to `app.Config`, which hands them to `auth.New` as `Config.IssuerURL`/`ClientID`/`KeychainService`. `auth.New` then builds its **own** dependencies: it derives Hydra's standard endpoint paths from the issuer via `newHydraOAuthConfig` (a caller-side helper in `auth.go`; the `auth/oauth` sub-package stays Hydra-agnostic, taking resolved endpoint URLs), and builds its own `keyringStore` over the service name — so only the issuer, client id, and keychain name are configured, no constructed store/config is passed in. `Config` carries **only production knobs** (`IssuerURL`/`ClientID`/`Scopes`/`KeychainService`) — nothing on it lets a caller bypass the real OAuth flow, and `New(Config)` takes no other arguments. The test seams are **unexported functional options** applied by an unexported `newWithOptions(cfg, opts...)` builder that `New` wraps (`withOAuthConfig` → httptest endpoints, `withCredentialsStore` → in-memory store, `withOAuthFlow`/`withLoopback`/`withBrowserOpener` → fakes); they resolve at construction (they pick the store/oauth client the grant is built over) and are reachable only from `auth`'s own (white-box) tests. Auth degrades to signed-out when neither a keychain name nor a `withCredentialsStore` option is given.) It threads the `auth.Service` into the `graph.Resolver` as one `Auth` field — always non-nil; the service itself degrades (signed-out, erroring login) when unconfigured — backing the `authState` query, `authLoginStart`/`authLogout` mutations, and `authStateWatch` subscription (built/consumed by the webview's `src/lib/auth.tsx`).

**Mostly flat, one carved-out sub-package.** The root `package auth` is deliberately flat (no `session`/`credentials` sub-packages — those files share a dense web of value types and would only have to export private state-machine internals to live apart). It's organized **by domain into four files**: `auth.go` (the service facade — the public `Service` interface, the `State`/`TokenSet` value types, the `Token`/`Identity` aliases, `Config` + the test options, and the composition owner; named to match the `cluster.go`/`cloud.go` convention), `grant.go` (the **grant aggregate** plus everything it owns — the credential state machine, its `CredentialsStore`/`RefreshFunc` ports + `ErrSignedOut` defined consumer-side, and the `grantTokenSource` `oauth2.TokenSource` adapter), `login.go` (the **interactive login flow** — the unexported `loginFlow` that runs loopback → browser → exchange → verify, the PKCE verifier/state generation + browser opener that feed it, the flow's seam interfaces `OAuthFlow`/`Loopback`/`LoopbackFunc` and the `loginStarter`/`pendingLogin` types the service holds the login step behind, **and the 127.0.0.1 `loopbackServer` redirect listener** that implements the flow's own `Loopback` seam — `(*loginFlow).start` runs the **synchronous setup** (loopback bind + browser open) and returns a `pendingLogin` for the slow async tail), and `keyring.go` (the OS-keyring credential persistence — the unexported `keyringStore`, the lone concrete `CredentialsStore` impl, kept apart from the aggregate since it carries its own `zalando/go-keyring` dependency).

The **one** piece carved out is `internal/auth/oauth` (`package oauth`) — the OAuth2/OIDC **protocol layer**, the subsystem's one genuine deep module (PKCE S256, JWKS verification via go-oidc, RFC 7009 revocation, token exchange/refresh) behind a small `Client` surface. It is a **leaf**: `auth` builds an `oauth.Client` (via `oauth.NewClient(oauth.Config)`) and drives it, so `oauth` must not import `auth`. Because `oauth.Client` *produces* the `Token` and `Identity` value types, those types **live in `oauth`** (avoiding the import cycle that keeping them in root would force), and `auth.go` re-exports them as true type aliases (`type Token = oauth.Token`, `type Identity = oauth.Identity`) so the rest of `auth` and external consumers (`graph`, `cloud`) keep naming them `auth.Token`/`auth.Identity` with no conversion and no sub-package import. `oauth.ParseIdentityUnverified` (display-only claim decode, used by the grant on cache restore) is the one other exported helper `auth` calls across the boundary.

The grant aggregate, the loopback listener, the login flow, and the keyring store remain **unexported** (`grant`/`loopbackServer`/`loginFlow`/`keyringStore`); the root's exported surface is the `Service` interface, its `New(Config)` constructor (with an unexported `newWithOptions(cfg, opts...)` builder that white-box tests use to inject `option` seams), the seam interfaces (`OAuthFlow`/`Loopback`/`LoopbackFunc`), the `Token`/`Identity` aliases, and the persistence types. External consumers (`graph`, `cloud`) that need a stand-in fake the `Service` interface directly rather than constructing a real service with seams.

- **`Service`** is an **interface** (`auth.New(Config) (Service, error)`), passed around to consumers like the cloud client. It owns **no long-lived goroutines, so there's no `Start`/`Close`** (restore happens in `newGrant`; revocation is a per-`Logout` fire-and-forget, and `StartLogin`'s async tail is likewise bounded fire-and-forget — see below). Methods: `Current(ctx) (State, error)` (the current `State` — `Authenticated` + `Identity` + `TokenSet`, no forced refresh), `StartLogin(ctx)` (runs the `loginFlow`'s **synchronous setup** — loopback bind + browser open — under the caller's ctx and **returns its error synchronously** so the `login` mutation can surface a setup failure to the UI; the slow tail — wait for redirect → exchange → `Verify` → `grant.set(tok, identity)`, which persists before publishing the signed-in `State` — then runs in a **bounded, detached fire-and-forget goroutine** (`loginTimeout`, not tied to shutdown — like `Logout`'s revoke), its completion observed via `Subscribe`/`authStateWatch`; a tail failure is logged and stays signed-out. The flow's two phases are tested directly in `login_test.go`, while a service-level test fakes the whole login step via the `withLoginStarter` option — so the per-part flow seams don't leak onto the service's build path), `Logout(ctx)` (captures the refresh token, `grant.clear()`s local-first — publishes the signed-out `State` — then `Revoke`s fire-and-forget on its own bounded context; if the keychain write fails it returns the error and stays signed in), `TokenSource(ctx) oauth2.TokenSource` (a `grantTokenSource` adapter capturing `ctx` for the lazy refresh exchange; **nil when degraded**), and `Subscribe() (<-chan State, func())` (a **latest-value** session-state stream — current-on-subscribe, then each change — plus cancel).

**The grant aggregate models the OAuth grant.** The unexported `grant` aggregate owns the **token set as the source of truth** plus the cached identity; `State.Authenticated` and `State.Identity` are **derived** (signed-in ⇔ a refresh token is present), never stored alongside, so credential state and the published `State` can't drift. It owns the token (cache + **lazy refresh**, mutex serializing a burst into a single refresh, persist-before-cache) and a `gochan/watch` hub publishing the **current session `State`** (latest-value, current-on-subscribe; seeded with the restored State at construction). A sign-in/out republishes a flipped `Authenticated`; a routine refresh republishes the same `Authenticated` bit with a renewed `Tokens` projection — so a consumer that keys off the sign-in bit sees no transition on refresh, without any event-type tagging. `newGrant(store, refresh, opts)` restores from the store (decode identity via `parseIdentityUnverified` — display-only; the cloud re-verifies the access token per request). `validToken`/`current`/`set`/`clear`/`state`/`subscribe` are the internal ports. **Refresh decision:** the cache/refresh/dedup is hand-rolled (we keep per-call `ctx` into refresh, which a long-lived `oauth2.ReuseTokenSource` would bake in at construction); only the refresh *HTTP exchange* is delegated to `golang.org/x/oauth2` inside the oauth client's `Refresh`.

**Token-source shape & leak posture.** Downstream consumers get an **`oauth2.TokenSource`** (the cloud api client builds one per request from the request `ctx` via `Service.TokenSource`, so the bounded token-fetch timeout governs each refresh). This is the idiomatic shape but **does expose the refresh token** on the returned `*oauth2.Token` — the api client simply reads `AccessToken` and never inspects the rest. The resolver still maps only the tokenless projection (`State.Authenticated` + `State.Identity` → `AuthState { authenticated, identity }`); `State.Tokens` (a `TokenSet`) rides along for in-process callers but is dropped by the GraphQL projection.

**Hydra OIDC mechanics** (the `auth/oauth` sub-package, plus the loopback listener in `login.go`): PKCE (`generateVerifier` in `login.go` / `s256Challenge` in `oauth`), `Client.AuthCodeURL`, a 127.0.0.1 `loopbackServer` redirect listener (in `login.go`, behind the exported `Loopback` seam), `Client.Exchange`/`Refresh` (via `golang.org/x/oauth2`), `Client.Revoke` (RFC 7009 token revocation — public client, posts `token`+`client_id` to `oauth.Config.RevocationURL`; revoking the refresh token also kills the grant's access tokens), and `Client.Verify` (ID-token signature/iss/aud/exp via `github.com/coreos/go-oidc/v3` against Hydra's JWKS) → `Identity{UserID,Email,Name}` (claim `sub` → `UserID`). **Identity comes from the verified ID token**, so no extra profile round-trip.

## Cloud settings sync (`internal/cloud`) — depends on `auth`

Cloud-synced settings (later AI-model routing) backed by kstack-cloud's API. Settings are **local-first**: an edit applies to a local JSON file immediately and is queued for the cloud, surviving offline/restart. The subsystem **depends on `internal/auth`** — it authenticates the api client from `authSvc.TokenSource`, and **wakes its sync engine by observing `authSvc.Subscribe()` session `State`** (`auth` knows nothing about the engine). It **degrades** when unconfigured (no cloud URL / data dir ⇒ no settings sync). The composition root (`internal/app`) wires CloudURL (`KSTACK_CLOUD_URL`) and hands the `auth.Service` to `cloud.New(dataDir, cloudURL, authSvc)`.

- `internal/cloud` (root package `cloud`) — **composition + lifecycle owner**, mirroring `cluster.Service`. `cloud.New(dataDir, cloudURL string, authSvc auth.Service, pokeSvc *poke.Service)` wires prefs + queue + engine, building the api upstream from `authSvc.TokenSource` (degraded — no engine — without a data dir, or without a cloud URL + a non-nil token source); `pokeSvc` is the shared resync broadcaster handed to the engine (nil disables external wake signals). `Start(ctx) (stop func(context.Context) error, error)` runs the settings-sync engine (idempotent — a second `Start` returns a no-op stop so it can't leak an engine goroutine) **plus a goroutine that observes the auth session `State` and pokes the engine only when `Authenticated` flips** (sign-in → authenticate + sync now; sign-out → cancel the in-flight authenticated watch). The stream is latest-value (current-on-subscribe), so the goroutine seeds its baseline from the first `State` without poking, and a routine token refresh — which leaves `Authenticated` unchanged — never wakes the engine. Tracking the single `Authenticated` bit (not the whole `State`) is what makes refresh a non-event. `ctx` scopes initialization only; the returned `stop` cancels the engine **and** the poke goroutine and blocks until both unwind, honoring its own drain-deadline context (there's no `Close` — the stop func replaces it). Exposes `Prefs()` (the settings store, nil when degraded). The required production inputs are positional constructor args (`dataDir`, `cloudURL`, `authSvc`, `pokeSvc`), not a config struct; the test seam (a fake sync upstream instead of the api client) is an **unexported functional option** — `withUpstream`, applied by an unexported `newWithOptions(dataDir, cloudURL, authSvc, pokeSvc, opts...)` builder that `New` wraps and reachable only from `cloud`'s own (white-box) tests, mirroring the `auth` subsystem's option pattern.

Sub-packages (leaf-first):

- `internal/cloud/syncstore` — generic `Envelope[T]{Data, Version, LastSyncedAt, LastEventAt}` + `Store[T]` over `internal/atomicjson` (crash-safe JSON; serialized writers). The reconcile-state file primitive.
- `internal/cloud/prefs` — the `Settings` type (**pointer fields + omitempty** so absent ≠ cleared, for the cloud's deep-merge), `Merge(base, patch)` (the local-first reconcile primitive), `Clone` (deep copy), and `Store` (persist + a `gochan/watch` hub that publishes current-on-subscribe, with an equality guard so an unchanged `Set` neither writes disk nor publishes). Because `Settings` holds pointers, the `Store` (Set/Get) and the `mutationqueue` (Enqueue/Pending) **deep-copy at their boundaries** so a caller mutating a string it passed in (or one it got back) can't desync in-memory state from the persisted JSON or queued payload.
- `internal/cloud/mutationqueue` — durable FIFO of pending local patches (atomicjson-backed, monotonic non-random ids). `Enqueue`/`Pending`/`Ack`; survives restart so offline edits still reach the cloud.
- `internal/cloud/api` — minimal GraphQL-over-HTTP cloud client (POST + SSE `WatchSettings`), authenticating every request from a per-request `oauth2.TokenSource` built from a `func(context.Context) oauth2.TokenSource` factory (`auth.Service.TokenSource`), reading its `AccessToken` — not a per-call token threaded through.
- `internal/cloud/prefsync` — the always-on reconcile `Engine` + `Upstream` interface (`Snapshot`/`Watch`/`Update`). `Watch` returns the settings channel **plus a buffered terminal-error channel** (nil = clean end / ctx cancel; non-nil = a read/transport failure **or** a GraphQL subscription error frame, which ends the stream rather than being silently skipped) so the engine distinguishes an errored close (record `LastError`, keep escalating backoff) from a healthy one — a nil error channel is treated as a clean end. Supervised connection with exponential backoff + poke. Production builds with `New(up, store, queue, notifier)` (defaults only); the deterministic `Now`/`Sleep`/`Jitter`/backoff seams are **unexported functional options** (`withNow`/`withSleep`/`withJitter`/`withBackoff`) applied by an unexported `newWithOptions(..., opts ...option)` builder that `New` wraps — reachable only from the package's white-box tests, mirroring the `auth`/`cloud` option pattern (so prefsync's tests are `package prefsync`, not `_test`). Wake/resync signals arrive via the `*poke.Service` passed to `New` (the shared broadcaster) — a wired-in dependency alongside `up`/`store`/`queue`, *not* a tunable option; nil disables external wake signals (tests, degraded runs). It's the concrete type, not an interface: `prefsync` already imports `poke` (the signals are `poke.Signal`), so an interface would decouple nothing — `poke` stays a leaf because it never imports `prefsync`, interface or not. `Set` is **local-first** (write store + enqueue + poke); on Live it **drains the queue** via `Upstream.Update` and acks; incoming snapshots/events have **still-pending patches re-layered on top** (`prefs.Merge`) so a stale cloud snapshot can't clobber an unacked local edit.

## Resync broadcaster (`internal/poke`)

`internal/poke` is a **cross-subsystem, leaf package** — no imports from other `internal/` packages. It owns two jobs:

1. **Wall-clock gap detector**: runs a ticker and compares the elapsed wall-clock time against the expected interval (default 15s tick, 2× gap factor). A jump larger than the threshold means the process was frozen (machine sleep, SIGSTOP, VM pause) — it fires a `Poke(SourceWallClock)`. This is the backstop that needs no OS event and works headless.
2. **Fan-out broadcaster**: every poke (from the detector or a direct `Poke(SourceHost)` call) is broadcast to all current subscribers via a `github.com/amorey/gochan/broadcast` hub. The `SourceHost` entry point is driven by the host gRPC `PokeService.Poke` handler (`grpc/poke_server.go`) — the host calls it on OS resume / network-on. (The Rust host trigger that actually calls the RPC is a separate `src-tauri/` change.)

**API**: `New()` → `*Service` (no arguments — production tunes nothing); `Start(ctx) (stop func(context.Context) error, error)` (the composition-root lifecycle entry, mirroring `cluster.Service`/`cloud.Service` — `Start` runs the detector in a goroutine and returns a `stop` func that cancels and waits, closing the hub, bounded by its own drain-deadline context) or the lower-level `Run(ctx)` it wraps (blocks, used directly by tests); `Poke(src)` (never blocks, safe from any goroutine); `Subscribe()` (returns `(<-chan Signal, func())`). `internal/app` owns the one `*poke.Service`'s lifecycle and hands it to `cluster.New`, `cloud.New`, and `grpcserver.NewServer`. The integrations sharing the one broadcaster: the settings engine receives signals via the `*poke.Service` it's given in `prefsync.New`; the host gRPC `PokeService` produces `SourceHost` pokes; and **both cluster controllers subscribe to the bus directly** (each in its beehive `Start`, fed the `*poke.Service` via `cluster.New`). On a poke the `ClusterCoreController` re-probes every eligible cluster's connection immediately, and the `ClusterCacheController` restarts its live sync engines in place — they re-dial and resume cheaply from their persisted resourceVersions. This is a **fan-out, not a cascade**: a poke is an ephemeral "re-establish now" event delivered to both consumers in parallel; it is deliberately *not* routed through a durable spec counter or through connection-status conditions (a clean resume produces no condition transition, so a cascade would silently fail to restart the now-stale watches). Conditions remain the *output* the webview reads, never the poke transport.

Test seams: the gap-detector tuning (`tick`/`gapFactor`) and the clock/ticker (`now`/`newTicker`) are **unexported functional options** (`withTick`/`withGapFactor`/`withNow`/`withTicker`) applied by an unexported `newWithOptions(opts ...option)` builder that `New` wraps — reachable only from poke's own white-box tests, mirroring the `auth`/`cloud`/`prefsync` option pattern. Production never tunes them (the gap detector's defaults are fixed and the gRPC `PokeService` only calls `Poke`, never reconfigures the detector), so `New` exposes no knobs; the external consumers that hold a `*poke.Service` in tests just call `New()` and drive `Poke` directly.

## gRPC + GraphQL over one socket (h2c)

gRPC needs HTTP/2; GraphQL stays HTTP/1.1. `internal/app` wraps the GraphQL/control mux in `h2c.NewHandler` whose dispatcher routes requests matching `grpcserver.IsGRPCRequest` to the `*grpc.Server` and everything else to the mux. The predicate lives in `grpc/` because it *is* the definition of a gRPC request (HTTP/2 *and* `application/grpc`); the composition root owns the dispatch + h2c wiring (the decision that these two surfaces share one socket). Each concern stays with its owner without a separate multiplexer package — `grpc/` owns "what is a gRPC request", `app` owns the topology. HTTP/1.1 GraphQL POST + SSE are untouched (they keep `ProtoMajor==1` and a Flusher-backed writer). An idle `AuthStateWatch` stream is kept alive under the server's 60s `IdleTimeout` by a gRPC keepalive ping. The webview uses GraphQL; the host (tray) uses gRPC (auth-state watch + login/logout, resync poke). The cluster surface is GraphQL-only (`clusters`/`clustersWatch` + `clusterCachesWatch` + cluster mutations).

**Shutdown** is driven through the `App` surface from `main.go`. `srv.RegisterOnShutdown(app.NotifyShutdown)` fires the moment `srv.Shutdown` begins, then:

1. **`app.NotifyShutdown()`** fans out to both sub-servers: `grpcServer.NotifyShutdown()` cancels the serving context (every `Watch` handler returns `nil` → grpc writes its OK trailers → each client sees a clean `io.EOF`), and `graphqlServer.NotifyShutdown()` closes a `shutdownCh` that cancels each active SSE subscription's request context (gqlgen flushes its terminal `event: complete`).
2. **`srv.Shutdown(ctx)`** stops accepting and waits for the non-hijacked GraphQL requests to finish — the SSE streams, now cancelled, flush and return.
3. **`app.DrainWithContext(ctx)`** waits on *both* sub-servers' `WaitGroup`s. This is the essential wait for the **hijacked h2c gRPC streams** that `srv.Shutdown` does not track; for GraphQL it's belt-and-suspenders.
4. **the `stop` func from `app.Start`** drains the services — `clusterSvcStop` → `cloudSvcStop` → `pokeSvcStop` (poke's hub closes last, after the cluster controllers that subscribe to it have drained) — then **`app.Close()`** stops the gRPC transports (`grpcServer.Stop()`) and `clusterSvc.Close()` (which owns the whole cluster control-plane teardown order: stop writers → stop beehive's controllers + engines → shut the per-cluster cache → close the beehive store). main() calls `stop(stopCtx)` before `Close`.

Why it's built this way (the non-obvious parts): grpc's own `GracefulStop` **panics** on the `ServeHTTP`/h2c path, so the stream must end on its own serving context instead, and `Stop` only runs in step 4 after the streams have drained. The GraphQL SSE drain is **per-request** (`graph.Server.ServeHTTP` wires each SSE request's context to `shutdownCh`), deliberately **not** via `http.Server.BaseContext`: a `BaseContext` cancel would tear down the shared h2c connection carrying gRPC mid-stream. Because nothing touches `BaseContext`, the two transports are independent — `NotifyShutdown` signals both at once and there is no required gRPC-before-GraphQL ordering. (The h2c dispatcher also routes gRPC away *before* the GraphQL server's `ServeHTTP`, so a long-lived gRPC connection is never counted in the GraphQL `WaitGroup`.)

## Patterns

- **Resolver deps are always non-nil**: the composition root (`internal/app`) wires every `Resolver` field, and resolvers call their deps without nil guards — degraded behavior (e.g. no cloud account) lives inside the services themselves (`auth.New` degrades internally; the data dir is simply required). Tests construct the `Resolver` with fakes (e.g. `newFakeAuth`) rather than relying on nil tolerance.
- **Pub/sub**: `github.com/amorey/gochan` hubs fan snapshots to subscribers — `watch` for latest-value "current state" streams (the kubeconfig watcher and the auth session-`State` stream, both delivering the current snapshot on subscribe — a consumer needs no separate "read current" call to seed itself), `broadcast` for fan-out streams whose subscribers supply their own initial snapshot (the `poke` resync broadcaster). Watchers use fsnotify + a debounce, then publish the new snapshot.
- **Subscription resolvers**: return a channel that **emits the current snapshot first, then deltas**. Hub-backed sources forward through `mapStream` (`graph/util.go` — the source is current-on-subscribe, so its first value IS the snapshot; see `authStateWatch`). `clustersWatch`/`clusterCachesWatch` follow the same rule the Kubernetes way: beehive's `WatchList` replays current state as `Added` changes (the snapshot) then streams `Added`/`Modified`/`Deleted`, so the resolver just `mapStream`s each value change to a pointer. Honor `ctx.Done()`.

## Tests & checks

- testify + `net/http/httptest`. Resolver-level GraphQL tests stand up `graph.NewServer(&graph.Resolver{...})` and `POST /graphql` (in `graph/`); h2c/control/lifecycle tests stand up `app.New(...)` (in `internal/app/`). Filesystem via `t.TempDir()` / `os.MkdirTemp`.
- **White-box tests by default** — a package's tests live in the same `package foo` (not `package foo_test`), so they can exercise unexported helpers directly with no export-tax. This mirrors the flat-package philosophy elsewhere in the tree (e.g. `internal/auth`): boundaries inside a package are kept by discipline + file ownership, not by the compiler, and the test layer follows the same rule. **Escape hatch:** reach for an external `package foo_test` only when a test's *purpose* is to pin the public contract and you want the compiler to *guarantee* it touches only the exported surface — then say so in a comment. Don't mix the two styles within one package without that reason.
- **Avoid magic sleeps.** Don't `time.Sleep` to wait for async work (fsnotify reloads, hub publishes) — block on the actual event with `<-sub.Chan()` guarded by a `select { case … : case <-time.After(deadline): t.Fatal(…) }` timeout, as the watcher tests do. A `time.After` deadline is fine; a fixed sleep is flaky and slow.
- `make test-go` (`cd sidecar && go test ./...`).
- `make lint-go` (gofmt) and `make vet-go` (`go vet`). Run `gofmt -w` before committing.

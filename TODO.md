The `objects.updated_at` column (ingest wall-clock, restamped on every upsert) still exists. To bring `lastUpdatedAt` back **without reintroducing a scan**, extend the trigger-maintained `kind_counts` aggregate to also track a per-kind `MAX(updated_at)` (bump it in the same `objects` triggers), surface it through `KindCatalog`/`ClusterDataKind`, and expose it per kind on the dashboard nav (a "last updated Ns ago" per-kind hint) rather than resurrecting the whole `resources[]` rollup. Caveat to preserve: it's ingest time, not the k8s `metadata` timestamp — a full re-list restamps it even when objects didn't change upstream.

- **Cluster-schema namespace scheme — the deferred hoist.** The naming scheme is otherwise complete: type prefixes announce **where the data lives** — `Cluster*` (bare) = the beehive **Cluster** kind (registry record + status, including connection/probe observations); `ClusterCache*` = the beehive **ClusterCache** kind plus that cache's on-disk stats; `ClusterData*` = the per-cluster **data cache file** contents; unprefixed = a type that spans more than one kind (`Condition`, `Event`, `Schedule`, `ChangeType`, RBAC `ResourceRule`/`NonResourceRule`). The renames are **done** (`ClusterKind` → `ClusterDataKind`, `ClusterCondition` → `Condition`). **What remains (deliberately deferred):** `Condition`/`Event`/`Schedule` are still bound to `internal/cluster` Go types because `cluster` is their only consumer today. **Trigger to hoist:** the first non-cluster kind/subsystem that needs conditions/events/schedules — at that point move all three into a shared leaf package (e.g. `internal/apimeta`/`internal/k8smeta`), leaving `cluster` its `ConditionType` constants (`Connected`/`Healthy`/`Synced`). Hoisting earlier would be a one-importer abstraction.

- **CRD printer columns — render a CRD's `additionalPrinterColumns` client-side.** The per-kind column registry (`src/components/widgets/object-columns.tsx`, keyed by `gvrKey`) now carries hand-written accessors for built-ins, and every unregistered kind falls back to the universal Namespace/Name/Age columns — so **CRDs currently show no kind-specific columns at all**, even though they declare exactly what they want shown. **Approach (settled in the native-body design):** the server ships the column **descriptors** only — `{name, jsonPath, type, priority}`, static per kind, cheap, **no** per-object cell values — and the frontend evaluates the jsonPath client-side against each object's `rawJSON`. So the sidecar still computes no cell values (the whole point of shipping the native body) yet CRD columns work.
  - **Where the descriptors come from:** a CRD's `spec.versions[].additionalPrinterColumns`. The cache's `kind_catalog` already has a `schema_json` column (currently NULL) — the natural home; the sync engine's discovery pass would populate it for `isCRD` kinds, and `ClusterDataKind` would surface the parsed descriptors (they're per-kind and low-churn, so they ride the kinds watch, not the objects watch).
  - **Frontend:** `columnsForKind` becomes a two-tier lookup — hand-written registry entry first, else descriptor-derived columns, else universal-only. Needs a **minimal jsonPath evaluator**: Kubernetes only permits a restricted subset (`.spec.replicas`, `.status.conditions[0].type`), so a ~30-line reader beats a dependency; decide explicitly rather than pulling in a general JSONPath lib.
  - **Respect `priority`:** kubectl hides `priority > 0` columns unless `-o wide`. Filter to `priority === 0` initially; a "wide" toggle on the table can surface the rest later.
  - **Related gap (built-ins):** the registry only covers **Pod** and **Deployment** today. Obvious next: StatefulSet, ReplicaSet, Node, Service, Job, CronJob, PVC. Note **DaemonSet cannot reuse the Deployment/workload accessors** — it has no `spec.replicas`; its Ready is `status.numberReady/status.desiredNumberScheduled`.

- **Payload-carrying object-write deltas — retire the re-read.** *(Blocked on `amorey/gobus/conflate` shipping publicly with a `Receiver.Chan()`.)* Today the object-write bus is a **contentless keyed ping** (`notifyBroker` + the kind-routing just added): a per-kind `ClusterDataObjectsWatch` wakes on its kind's writes, then re-reads the whole `store.Objects(apiVersion, resource)` snapshot and diffs it against a service-layer `prev` to derive Added/Modified/Deleted. That's correct but O(kind size) per ping — and now that the native body rides the projection, each ping also decompresses **every** row and the diff retains every uncompressed body (see the resourceVersion-diff item below). Replace the ping with **payload-carrying deltas** over a `conflate` hub on `ClusterDB`, keyed by `(apiVersion, resource, uid)`, `V = ObjectDelta{type, gvk, resource, uid, resourceVersion, body}`. The consumer folds deltas instead of re-reading, so work drops to O(changed objects) and the body arrives on the delta rather than being re-read + re-diffed. (MODIFY already works — the body in the compared projection made in-place edits observable — so this is now a cost/scaling change, not a capability one.)
  - **Key by resource, not Kind (carry the P2 fix forward):** the compound key's kind-scope component must be the **plural `resource`**, not the Kind — the same reason the object-write notify routing landed on resource. A CRD deleted and recreated with the same `(apiVersion, resource)` but a new Kind keeps the resource stable while the Kind changes, so a `(kind, uid)` key would strand a per-kind objects watch against the dead Kind (missing the replacement driver's deltas), exactly the staleness the resource-keyed `notifyBroker` fix removed. So `ObjectDelta` carries its `resource` (from the driver's GVR) as the routing identity, and the per-kind consumer's `ReceiverFunc` filters on the `(apiVersion, resource)` prefix; `gvk`/`uid` stay in the payload for display + the map key. (The read side already translates `resource → kind` via `kind_catalog`, so the resource is the natural external identity throughout.)
  - **Why deltas must carry the body (the DELETE argument):** a keyed *ping* can't express a targeted delete — the consumer wakes, the row's already gone from the DB, and it can't tell an intentional delete from a stale ping without falling back to a full re-read + diff. Only a delta that carries `{uid, lastState}` at publish time works. The writer already has it: `ApplyChange(watch.Deleted, u)` holds `u`; the metadata-diff resync path (uid-only) does a read-before-delete in the same txn.
  - **Merge (type-aware annihilation) — the sharp edge:** conflate's `Merge(prev, next)` folds successive writes per uid. Annihilate (`keep=false`) **only** an undelivered `ADD` + `DELETE` pair (create+delete the consumer never saw). A `DELETE` following a delivered `ADD`/`MODIFY` (i.e. pending is a `MODIFY`) **must be kept** and delivered, or the consumer holds a ghost row forever. `ADD`+`MODIFY` → `ADD` with latest body; overlap resolves by keeping the higher `resourceVersion` (monotonic Merge).
  - **Snapshot↔delta fence (the hard part):** create the receiver **before** the SQL snapshot read (conflate guarantees delivery of every `Send` that happens-after registration), emit the snapshot, then fold the buffered deltas onto it. Overlap (a write in both the snapshot and the buffer) is idempotent under the monotonic Merge. **Keep a periodic full re-read as a reconcile backstop** (the read-side analogue of the driver's `resyncPeriod`) so a dropped/mis-built delta self-heals rather than silently corrupting the client view forever — preserves the engine's watch-for-latency / poll-for-correctness posture.
  - **No debounce.** `dataObjectsDebounce` exists only to throttle the expensive full re-read; with deltas there is no re-read, and conflate already coalesces per uid. The consumer loop becomes wake → drain-pending → fold/emit → park; coalescing is **backpressure-driven** (a slow consumer conflates more, a fast one emits promptly — self-tuning, no guessed window, lower latency than a fixed debounce). If wire *frame count* becomes a concern, add a **batch-drain** to conflate (emit the drained set as one frame) — still no timer. Retire `dataObjectsDebounce`.
  - **Keyless heartbeat stays a separate `gochan/watch`, NOT a conflate wildcard key.** Decided against a `WithWildcardKey` sentinel: it pollutes `conflate`'s `V`, keyspace, and Merge with a payload-less sentinel and *still* double-sends per write, buying nothing over composing `watch`. Put a contentless activity tap (`gochan/watch`) beside the conflate hub on `ClusterDB`; the per-commit writer helper does `deltas.Send(delta)` + `activity.Bump()`. Consumers of the tap: the engine **freshness tracker** ("any write → stamp liveness") and the **kind-catalog watch** (leave it on its cheap O(kinds) `kind_counts` re-read, woken by the tap — don't rebuild the trigger-maintained aggregate by folding deltas). The **discovery catalog-rewrite** bumps the tap; the **orphan prune** sends *targeted* `DELETE` deltas for the uids it removes (it already enumerates stale uids), so the current "keyless-wakes-keyed" broadcast semantics is engineered out entirely.
  - **conflate API asks (feed back to `gobus`):** `Receiver.Chan() <-chan V` (close-on-close; internal pump keeps ≤1 value in flight so coalescing survives a slow reader — `<-chan V` can't carry `ErrClosed`, so we select on `ctx` ourselves); a **documented happens-after-registration ordering guarantee** (the snapshot fence depends on it — it's already true in the code, just needs to be contract); and a worked type-aware-annihilation `Merge` example in the docs. Optional: a batch drain and exported pending/receiver metrics.
  - **Supersedes:** the interim keyed `notifyBroker` (object-write side) is replaced by the conflate hub; the events broker can stay a contentless `watch`-style tap (one consumer). Also subsumes the resourceVersion-diff item below (deltas carry the change witness, so nothing is re-compared).

- **Carry the failure *reason* for stuck kinds (fully-actionable surfacing).** A kind that exhausts its resync error budget now surfaces by name via `EngineStale`/`StaleKinds` → the cache controller's `SyncStale` event ("Not receiving updates for X — cache may be behind"), but the message doesn't say *why* (forbidden RBAC vs. un-paginatable-within-token-lifetime `errListRestartBudget` vs. a wedged/idle-timed-out request), which is what makes it actionable ("fix RBAC" vs. "cluster too large / raise `--min-request-timeout`"). To do it: capture the driver's last resync error on `markStuck` (`kindDriver.lastResyncErr`), thread a per-kind reason from `staleLaggards` (today it returns bare kind names) into a richer `StaleKinds`/a new `EngineStatus` field, and render it in `staleMessage`. Also consider a distinct reason from the wedged-watch case (a stuck kind that *never synced* isn't literally a "stalled watch") — today both share `ReasonSyncStale`.

- **Events ordering — timestampless events have no stable order.** `store.Events` (backing `ClusterDataEventsWatch`) orders by bare `last_seen DESC`, which rides the `events_last_seen` index. But a source Event with no timestamp stores `last_seen = NULL` (deliberate — `nullableInt64`), and under `DESC` those NULLs sort last **with no tiebreak**, so timestampless events land at the bottom in undefined order even though their write order is recoverable: the table has `updated_at` (ingest wall-clock, restamped on every upsert) and a stable `rowid` (insert order). The schema even anticipates this — `nullableInt64`'s NULL-on-zero exists so a `COALESCE(last_seen, updated_at)` fallback can fire. Fix when it matters: order by `COALESCE(last_seen, updated_at) DESC` so ingest time stands in for a missing event time. Two catches to weigh: (1) it **mixes clocks** (cluster `last_seen` vs. local `updated_at`), so a just-ingested timestampless event can rank above a real older one — defensible for a "latest events" view but a real semantic; (2) the `COALESCE(...)` expression **can't use `events_last_seen`**, turning the read into a full scan + top-N sort, so at high event volume add an **expression index** (`CREATE INDEX events_recency ON events(COALESCE(last_seen, updated_at) DESC)`, a store migration) to keep it index-backed. Deferred because timestampless events are rare (most Events carry `lastTimestamp`/`eventTime`); revisit if the events table shows meaningful ordering churn.

- **Diff objects on `resourceVersion`, not the whole body (`cacheDeltaWatch` should take an equality hook).** `cacheDeltaWatch[T comparable]` decides "changed" by whole-value `!=`, so shipping the body inside `ClusterDataObject` made *byte-identical re-serialization of the entire object* the change witness. Three costs: (1) `store.Objects` `DecompressRaw`s **every** row on **every** debounced ping (a single pod write in a 5k-pod cluster inflates 5k blobs, ~all discarded as unchanged); (2) the watch's `prev`/`next` maps retain every object's *uncompressed* body for the life of the subscription, rebuilt per ping — memory proportional to cluster size, not churn; (3) the invariant "raw_json is byte-stable across reads for an unchanged object" is now load-bearing but enforced nowhere — any write-path normalization change (a re-marshal, a different strip) would turn every object of every kind into a spurious `Modified` burst. The `objects` table already has `resource_version` (`migrations/0001_init.sql:64`) — the canonical O(1) change witness — but `ObjectRow` doesn't select it. **Fix:** swap `[T comparable]` for `[T any]` + a `changed func(old, new T) bool` (or `version func(T) string`); kinds/events keep whole-value equality, objects compare `resourceVersion`. Then `RawJSON` no longer needs to be a comparable string, and the body can be decompressed **lazily in `mkChange`** (only for rows actually emitted) — or the diff can run on the *compressed* blob, since `CompressRaw` is deterministic. Partially subsumed by the payload-carrying-deltas item above (which retires the re-read entirely), but worth doing first if that one stays blocked.

- **Revisit the per-timestamp field resolvers — a zero-aware `Time` scalar could retire them.** Three fields resolve through hand-written resolvers whose only job is mapping the zero `time.Time` (an absent timestamp) to `null` instead of serializing `0001-01-01`: `ClusterDataEvent.firstSeen`/`lastSeen` and `ClusterDataObject.creationTimestamp` (all via `nilIfZeroTime` in `graph/util.go`, wired as `resolver: true` in `gqlgen.yml`). The domain deliberately keeps **value** `time.Time` (not `*time.Time`) because these types flow through `cacheDeltaWatch`'s `old != v` diff, which requires the struct stay `comparable` — so the null-mapping can't just be a nullable pointer field. But the same trick we used for the body — a **custom scalar that does the transform at marshal time** — applies here: bind the GraphQL `Time` scalar (or a new `Timestamp`) to a small comparable wrapper over `time.Time` whose `MarshalGQL` emits `null` for the zero value, then all three fields **autobind** and the three resolvers + `nilIfZeroTime` delete. (Same reasoning as dropping the `rawJSON` resolver: push the representation concern into the scalar, keep the field declarative.) Catch to weigh: `Time` is currently bound to plain `string` in gqlgen and marshaled by gqlgen's built-ins across the *whole* schema (not just these three fields), so this means either introducing a **separate** scalar for the nullable-zero case or migrating every `Time` field onto the wrapper — check nothing else relies on the string binding before committing. Low priority; purely an internal simplification with no wire change.

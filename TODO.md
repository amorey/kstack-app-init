- **Payload-carrying object-write deltas — retire the re-read.** *(Blocked on `amorey/gobus/conflate` shipping publicly with a `Receiver.Chan()`.)* Today the object-write bus is a **contentless keyed ping** (`notifyBroker` + the kind-routing just added): a per-kind `ClusterDataObjectsWatch` wakes on its kind's writes, then re-reads the whole `store.Objects(apiVersion, resource)` snapshot and diffs it against a service-layer `prev` to derive Added/Modified/Deleted. That's correct but O(kind size) per ping — and now that the native body rides the projection, each ping also decompresses **every** row and the diff retains every uncompressed body (see the resourceVersion-diff item below). Replace the ping with **payload-carrying deltas** over a `conflate` hub on `ClusterDB`, keyed by `(apiVersion, resource, uid)`, `V = ObjectDelta{type, gvk, resource, uid, resourceVersion, body}`. The consumer folds deltas instead of re-reading, so work drops to O(changed objects) and the body arrives on the delta rather than being re-read + re-diffed. (MODIFY already works — the body in the compared projection made in-place edits observable — so this is now a cost/scaling change, not a capability one.)
  - **Key by resource, not Kind (carry the P2 fix forward):** the compound key's kind-scope component must be the **plural `resource`**, not the Kind — the same reason the object-write notify routing landed on resource. A CRD deleted and recreated with the same `(apiVersion, resource)` but a new Kind keeps the resource stable while the Kind changes, so a `(kind, uid)` key would strand a per-kind objects watch against the dead Kind (missing the replacement driver's deltas), exactly the staleness the resource-keyed `notifyBroker` fix removed. So `ObjectDelta` carries its `resource` (from the driver's GVR) as the routing identity, and the per-kind consumer's `ReceiverFunc` filters on the `(apiVersion, resource)` prefix; `gvk`/`uid` stay in the payload for display + the map key. (The read side already translates `resource → kind` via `kind_catalog`, so the resource is the natural external identity throughout.)
  - **Why deltas must carry the body (the DELETE argument):** a keyed *ping* can't express a targeted delete — the consumer wakes, the row's already gone from the DB, and it can't tell an intentional delete from a stale ping without falling back to a full re-read + diff. Only a delta that carries `{uid, lastState}` at publish time works. The writer already has it: `ApplyChange(watch.Deleted, u)` holds `u`. The relist's prune does not — it is a mark-and-sweep `DELETE` that never materializes the uids it removes (deliberately: see the eventsync/objectsync prune notes), so it would need a read-before-delete in the sweep transaction to emit targeted deltas. Weigh that against the sweep's whole point before committing; a cheaper option is to leave the relist path emitting the keyless activity tap and let the consumer's periodic reconcile re-read cover it.
  - **Merge (type-aware annihilation) — the sharp edge:** conflate's `Merge(prev, next)` folds successive writes per uid. Annihilate (`keep=false`) **only** an undelivered `ADD` + `DELETE` pair (create+delete the consumer never saw). A `DELETE` following a delivered `ADD`/`MODIFY` (i.e. pending is a `MODIFY`) **must be kept** and delivered, or the consumer holds a ghost row forever. `ADD`+`MODIFY` → `ADD` with latest body; overlap resolves by keeping the higher `resourceVersion` (monotonic Merge).
  - **Snapshot↔delta fence (the hard part):** create the receiver **before** the SQL snapshot read (conflate guarantees delivery of every `Send` that happens-after registration), emit the snapshot, then fold the buffered deltas onto it. Overlap (a write in both the snapshot and the buffer) is idempotent under the monotonic Merge. **Keep a periodic full re-read as a reconcile backstop** (the read-side analogue of the driver's `resyncPeriod`) so a dropped/mis-built delta self-heals rather than silently corrupting the client view forever — preserves the engine's watch-for-latency / poll-for-correctness posture.
  - **No debounce.** `dataObjectsDebounce` exists only to throttle the expensive full re-read; with deltas there is no re-read, and conflate already coalesces per uid. The consumer loop becomes wake → drain-pending → fold/emit → park; coalescing is **backpressure-driven** (a slow consumer conflates more, a fast one emits promptly — self-tuning, no guessed window, lower latency than a fixed debounce). If wire *frame count* becomes a concern, add a **batch-drain** to conflate (emit the drained set as one frame) — still no timer. Retire `dataObjectsDebounce`.
  - **Keyless heartbeat stays a separate `gochan/watch`, NOT a conflate wildcard key.** Decided against a `WithWildcardKey` sentinel: it pollutes `conflate`'s `V`, keyspace, and Merge with a payload-less sentinel and *still* double-sends per write, buying nothing over composing `watch`. Put a contentless activity tap (`gochan/watch`) beside the conflate hub on `ClusterDB`; the per-commit writer helper does `deltas.Send(delta)` + `activity.Bump()`. Consumers of the tap: the engine **freshness tracker** ("any write → stamp liveness") and the **kind-catalog watch** (leave it on its cheap O(kinds) `kind_counts` re-read, woken by the tap — don't rebuild the trigger-maintained aggregate by folding deltas). The **discovery catalog-rewrite** bumps the tap; the **orphan prune** sends *targeted* `DELETE` deltas for the uids it removes (it already enumerates stale uids), so the current "keyless-wakes-keyed" broadcast semantics is engineered out entirely.
  - **conflate API asks (feed back to `gobus`):** `Receiver.Chan() <-chan V` (close-on-close; internal pump keeps ≤1 value in flight so coalescing survives a slow reader — `<-chan V` can't carry `ErrClosed`, so we select on `ctx` ourselves); a **documented happens-after-registration ordering guarantee** (the snapshot fence depends on it — it's already true in the code, just needs to be contract); and a worked type-aware-annihilation `Merge` example in the docs. Optional: a batch drain and exported pending/receiver metrics.
  - **Supersedes:** the interim keyed `notifyBroker` (object-write side) is replaced by the conflate hub; the events broker can stay a contentless `watch`-style tap (one consumer). Also subsumes the resourceVersion-diff item below (deltas carry the change witness, so nothing is re-compared).

- **Carry the failure *reason* for stuck kinds (fully-actionable surfacing).** A kind that exhausts its resync error budget now surfaces by name via `EngineStale`/`StaleKinds` → the cache controller's `SyncStale` event ("Not receiving updates for X — cache may be behind"), but the message doesn't say *why* (forbidden RBAC vs. un-paginatable-within-token-lifetime `errListRestartBudget` vs. a wedged/idle-timed-out request), which is what makes it actionable ("fix RBAC" vs. "cluster too large / raise `--min-request-timeout`"). To do it: capture the driver's last resync error on `markStuck` (`kindDriver.lastResyncErr`), thread a per-kind reason from `staleLaggards` (today it returns bare kind names) into a richer `StaleKinds`/a new `EngineStatus` field, and render it in `staleMessage`. Also consider a distinct reason from the wedged-watch case (a stuck kind that *never synced* isn't literally a "stalled watch") — today both share `ReasonSyncStale`.

- **Events ordering — timestampless events have no stable order.** `store.Events` (backing `ClusterDataEventsWatch`) orders by bare `last_seen DESC`, which rides the `events_last_seen` index. But a source Event with no timestamp stores `last_seen = NULL` (deliberate — `nullableInt64`), and under `DESC` those NULLs sort last **with no tiebreak**, so timestampless events land at the bottom in undefined order even though their write order is recoverable: the table has `updated_at` (ingest wall-clock, restamped on every upsert) and a stable `rowid` (insert order). The schema even anticipates this — `nullableInt64`'s NULL-on-zero exists so a `COALESCE(last_seen, updated_at)` fallback can fire. Fix when it matters: order by `COALESCE(last_seen, updated_at) DESC` so ingest time stands in for a missing event time. Two catches to weigh: (1) it **mixes clocks** (cluster `last_seen` vs. local `updated_at`), so a just-ingested timestampless event can rank above a real older one — defensible for a "latest events" view but a real semantic; (2) the `COALESCE(...)` expression **can't use `events_last_seen`**, turning the read into a full scan + top-N sort, so at high event volume add an **expression index** (`CREATE INDEX events_recency ON events(COALESCE(last_seen, updated_at) DESC)`, a store migration) to keep it index-backed. Deferred because timestampless events are rare (most Events carry `lastTimestamp`/`eventTime`); revisit if the events table shows meaningful ordering churn.

- **Diff objects on `resourceVersion`, not the whole body (`cacheDeltaWatch` should take an equality hook).** `cacheDeltaWatch[T comparable]` decides "changed" by whole-value `!=`, so shipping the body inside `ClusterDataObject` made *byte-identical re-serialization of the entire object* the change witness. Three costs: (1) `store.Objects` `DecompressRaw`s **every** row on **every** debounced ping (a single pod write in a 5k-pod cluster inflates 5k blobs, ~all discarded as unchanged); (2) the watch's `prev`/`next` maps retain every object's *uncompressed* body for the life of the subscription, rebuilt per ping — memory proportional to cluster size, not churn; (3) the invariant "raw_json is byte-stable across reads for an unchanged object" is now load-bearing but enforced nowhere — any write-path normalization change (a re-marshal, a different strip) would turn every object of every kind into a spurious `Modified` burst. The `objects` table already has `resource_version` (`migrations/0001_init.sql:64`) — the canonical O(1) change witness — but `ObjectRow` doesn't select it. **Fix:** swap `[T comparable]` for `[T any]` + a `changed func(old, new T) bool` (or `version func(T) string`); kinds/events keep whole-value equality, objects compare `resourceVersion`. Then `RawJSON` no longer needs to be a comparable string, and the body can be decompressed **lazily in `mkChange`** (only for rows actually emitted) — or the diff can run on the *compressed* blob, since `CompressRaw` is deterministic. Partially subsumed by the payload-carrying-deltas item above (which retires the re-read entirely), but worth doing first if that one stays blocked.

- **Revisit the per-timestamp field resolvers — a zero-aware `Time` scalar could retire them.** Three fields resolve through hand-written resolvers whose only job is mapping the zero `time.Time` (an absent timestamp) to `null` instead of serializing `0001-01-01`: `ClusterDataEvent.firstSeen`/`lastSeen` and `ClusterDataObject.creationTimestamp` (all via `nilIfZeroTime` in `graph/util.go`, wired as `resolver: true` in `gqlgen.yml`). The domain deliberately keeps **value** `time.Time` (not `*time.Time`) because these types flow through `cacheDeltaWatch`'s `old != v` diff, which requires the struct stay `comparable` — so the null-mapping can't just be a nullable pointer field. But the same trick we used for the body — a **custom scalar that does the transform at marshal time** — applies here: bind the GraphQL `Time` scalar (or a new `Timestamp`) to a small comparable wrapper over `time.Time` whose `MarshalGQL` emits `null` for the zero value, then all three fields **autobind** and the three resolvers + `nilIfZeroTime` delete. (Same reasoning as dropping the `rawJSON` resolver: push the representation concern into the scalar, keep the field declarative.) Catch to weigh: `Time` is currently bound to plain `string` in gqlgen and marshaled by gqlgen's built-ins across the *whole* schema (not just these three fields), so this means either introducing a **separate** scalar for the nullable-zero case or migrating every `Time` field onto the wrapper — check nothing else relies on the string binding before committing. Low priority; purely an internal simplification with no wire change.

- **`cache_idle_timeout_test.go` decides pass/fail on real wall-clock gaps.** The ported transport suite drives real timers at small durations — `TestIdleTimeoutAllowsSlowProgressingBody` sends 8 chunks 20ms apart against a 50ms idle window and asserts the body completes, and the stall/before-headers tests wait out real windows. The assertion is exactly right (a *progressing* body must survive a total duration longer than the window; only a true stall may be cancelled), but the margins are thin enough that a loaded CI box or a GC pause can starve a 20ms gap past 50ms and fail a correct implementation. It also contradicts the tree's no-magic-sleeps rule, which the rest of the sidecar's tests follow. **Why it's still here:** it came over verbatim from the deleted `cache/engine`, where it presumably passed, and rewriting it means giving `idleWatchdog` an injectable clock/timer seam (the driver's `withGraceTimer`/`withEstablishTimer` pattern is the in-tree precedent) so the test can advance virtual time instead of waiting. **Fix:** add the seam, drive the watchdog deterministically, and keep one real-timer test as a smoke check if the end-to-end `RoundTrip` path is worth covering live. See the audit item under Testing — this is the concrete instance that motivated it.

- **SQL optimization audit of the cluster cache store — port what beehive already settled.** The cache schema (`internal/cluster/cache/store/migrations/0001_init.sql`) and its pool were written for correctness first and have never been reviewed for storage/read cost, while `amorey/beehive` — same author, same modernc driver, same single-writer shape — has an ADR trail for exactly these questions (`docs/adr/` in the module). Do it as one pass with a measurement per change (a cold sync of a large cluster + file size + `EXPLAIN QUERY PLAN` on the hot reads), not as a batch of plausible pragmas.
  1. **Vacuum.** We already run `auto_vacuum=INCREMENTAL` and drain it from the janitor (`janitor.go` `sweep`, gated on `freelist_count`, capped at `vacuumPagesPerSweep`), so the mechanism exists — what's unreviewed is the *policy*: beehive drains only once the freelist passes a **floor** (→ its `2026-07-29-auto-vacuum-incremental.md`), we drain whenever it's non-zero, so a cluster with steady churn pays a vacuum on every janitor tick on the single writer. Also unify *where* the mode is set: beehive puts `auto_vacuum(incremental)` on the DSN in `sqlitemigrate.OpenPool` (applied while the file is still empty, free); ours is absent from `internal/sqlitemigrate/sqlitemigrate.go` and instead fixed up in `store.go` (~798) with a `PRAGMA` + full `VACUUM` rewrite after the pool is already open. Same end state, one costs a file rewrite on first open.
  2. **`WITHOUT ROWID`.** Every table in `0001_init.sql` is a plain rowid table, including several whose primary key *is* the row: `owner_refs (child_uid, owner_uid)`, `labels (uid, key)` (+`value`), `kind_counts (api_version, kind)`, `kind_catalog (api_version, kind)`, `cluster_meta (key)`. Each stores its key twice — once in the table, once in the automatic PK index — and their secondary indexes (`owner_refs_owner`, `labels_kv`) currently need a table seek to recover the other key column, which is precisely the pair of costs beehive's `edges` change removed with one keyword (→ its `2026-07-26-edges-without-rowid.md`; note there that `WITHOUT ROWID` makes `owner_refs_owner` implicitly covering as `(owner_uid, child_uid)`). Judge per table, not wholesale — the rule of thumb is narrow rows and no large blob; `objects` and `events` are the clear *non*-candidates (wide rows with a compressed `raw_json`).
  3. **The rest of beehive's storage decisions.** Read its ADR index and take what transfers: the object write-log / cursor shapes, the event **retention ring per timeline** (ours prunes by TTL sweep), and the DSN set in general — we match beehive on WAL/`busy_timeout`/`synchronous=NORMAL`/`foreign_keys`/`immediate` txlock but diverge on `auto_vacuum` as above, so confirm the divergence is the only one. Worth checking as part of the same pass: whether the four `objects` indexes are all earning their write cost (`objects_kind_ns_name`, `objects_kind_host`, the partial `objects_kind_ready`, `objects_ns_kind` — every one is maintained on every upsert, and the relist item above notes we rewrite every row per resync), and whether a periodic `PRAGMA optimize` belongs on the janitor tick.

### Deferred from the `/simplify` pass over the cache rewrite (commit `d572f0b`)

Findings a cleanup pass surfaced and deliberately did **not** apply — each is real, each was too wide or too behavior-changing for a quality pass. (The pass itself landed the shared `store.ResumeCookie`/`EnsureKindCatalog`, the eventsync mark-and-sweep prune, pooled zlib codecs, the dirty-scoped sync-health fold, `ptrStream`, and the `unhealthyResources` wire change.)

- **`sanitize` deep-copies every object body before projecting it.** `objectsync/store.go`'s `sanitize` calls `u.DeepCopy()` for every watch delta and every relist item — a full recursive copy of the unstructured map, comparable in cost to the `json.Marshal` that immediately follows, so roughly doubling per-object CPU on the write path. The stated reason ("the driver may still be reading it") looks over-cautious in practice: the tap goroutine has already forwarded the event before the apply loop receives it, and the driver only reads `GetResourceVersion()` afterward. **Why deferred:** the copy is the only thing standing between the write path and a shared-mutable-body bug, and the argument that no concurrent reader exists is exactly the kind of claim that quietly stops being true. If taken up, either strip/redact in place on the driver-owned body, or copy **only** for `isSecret` (the one case that rewrites values a caller could otherwise observe) — and pin the no-concurrent-reader invariant with a test or a comment at the driver's tap.

- **Three `objects` indexes are maintained on every write and read by nothing.** `migrations/0001_init.sql` creates `objects_kind_host`, `objects_ns_kind`, and `objects_kind_ready`; the cache rewrite is what made them dead (the schema comment now says the `host`/`status_summary`/`ready_count` columns are **not** written). So `objects_kind_host` carries one all-NULL entry per object, `objects_ns_kind` has no reader (`Objects` uses `objects_kind_ns_name`, `Kinds` doesn't touch `objects`), and `objects_kind_ready` is partial-empty — an extra b-tree insert/delete per object write and per relist row, plus file size, for zero reads. **Fix:** drop `objects_kind_host` and `objects_ns_kind` in a follow-up migration and re-add each alongside the writer that fills its columns. **Why deferred:** needs its own numbered migration, and the columns land with the materialized-column work.

- **The per-kind 30s liveness poll re-walks an immutable owner chain and rewrites an existing edge.** A running worker's reconcile returns `RequeueAfter: workerRecheckInterval` (30s), and each pass does `resolveChain` (3 `GetOwner` queries), `AddDependency` (a write transaction), and a condition/observed-generation write. At ~150 kinds per cache that's ~450 beehive reads + ~150 write transactions per cache per 30s, all to notice a connection-fingerprint change that almost never happens. **Fix:** have the `connections.Manager` publish fingerprint changes (it already holds the value at `Get`) and requeue only the affected clusters' children; or, less invasively, cache the resolved chain per object (owner edges are written at creation and never rewritten) and skip `AddDependency` once known present. **Why deferred:** changes when a credential rotation is noticed — a behavior change, not a cleanup.

- **`cacheDeltaWatch`/`cacheGaugeWatch`/`cacheWatchLoop` are a leaf deep module living inside `service.go`.** ~230 lines that know nothing about beehive, the domain types, or GraphQL — they take a `*store.Manager`, a cache id, a subscribe func and a read func — sitting in the 2,100-line boundary file, which makes `service.go` look like it owns SQLite-watch mechanics. They are also the one piece here with real concurrency subtlety (WatchDB rebind, debounce arm/disarm, closed-broker handling) and would benefit from focused tests of their own. **Fix:** move to `internal/cluster/cache/cachewatch` (or onto `store`, which already owns `WatchDB` and the brokers), leaving `service.go` the three thin per-watch adapters. Mechanical, no logic change — but a wide diff.

- **`objectsync.Kind` is the package-wide kind-identity vocabulary, including on the Events path.** `newGVRWorkerFunc`, `newLiveGVRWorker`, `newSyncStore`, `syncEntry.kind` and `isEventsKind` all speak `objectsync.Kind`, and `newSyncStore` hands an `objectsync.Kind` to `eventsync.NewStore`, which discards it — so `isEventsKind(kind objectsync.Kind)` reads as "is this objectsync kind not an objectsync kind". The shared identity type lives inside one of the two specializations. **Fix:** move `Kind` (and `GVR()`) up into `kubesync`, where `Source` and `Store` already live; `objectsync` keeps only its catalog-column helpers (`scope()`, `group()`, `isCRD()`). ### Deferred from the second `/simplify` pass over the cache system (applied as `9f91f8e`)

A four-angle cleanup pass (reuse / simplification / efficiency / altitude) over the whole
cache system. What landed: the duplicate Event-identity constants, the dead
`eventsync/source.go`, `forgetKindRows` as the one owner of the Events reap exemption,
`liveCondition` for the two hand-built conditions, `Kind.group()`→`apiGroup`, the shared

`DisclosureLabel` extraction, the orphan sweep's reused child list, the one-statement
status-history guard, and dropping the unread `conditions` selection. Deferred below.

- **The two `replaceSession` types are one mark-and-sweep relist protocol written twice.** `objectsync/store.go` and `eventsync/store.go` each carry ~90 near-identical lines: the `mark: now()+1` boundary, the clear-the-cookie-on-first-write latch, the `now := max(now(), mark)` page stamp, the per-page transaction + notify, and the Commit (sweep-below-mark → persist cookie → notify) — with the three long rationale comments pasted into both and already drifting in wording. **Cost:** these are the subtlest correctness invariants in the system ("a cookie means a COMPLETED pass", millisecond-resolution marks) and a fix to one is silently not a fix to the other. **Fix:** hoist one session into `cache/store`, beside `ResumeCookie` and `EnsureKindCatalog` (extracted for exactly this reason), parameterised by the four things that differ — the row projection, the insert, the sweep statement, and the notify. **Why deferred:** it is a rewrite of both write paths, and deserves its own change with its own verification rather than riding along in a cleanup commit. Highest-value item in this list; two of the four reviewers ranked it first.

- **Ten hand-rolled write-transaction envelopes across the two write stores.** `BeginTx` / `if err` / `defer tx.Rollback() //nolint:errcheck` (the same nolint comment ten times) / 1–5 lines of real work / `Commit` / notify, at `objectsync/store.go` ~133, ~158, ~429, ~502, ~571, ~611 and `eventsync/store.go` ~144, ~174, ~251, ~293. **Cost:** a 5:2 ceremony-to-content ratio hides the one interesting statement in each method, and the rollback/commit/notify ordering is re-asserted by hand every time (`Forget` already differs on whether the notify precedes or follows an error). **Fix:** one `func (c *ClusterDB) InTx(ctx, func(store.Execer) error) error` on the shared handle.

- **The three object deleters re-walk `cascadeTables` with only the predicate differing.** `deleteOne` (`WHERE uid=?`), `sweep` (`uid IN (SELECT …)`) and `DeleteByUIDs`' chunk loop (`uid IN (?,?,…)`). **Cost:** the `cascadeTables` comment itself records that `owner_refs.owner_uid` was once dropped from all three deleters independently; the table list was centralised, the three loops around it were not, so the same class of omission can recur in the predicate. **Fix:** one private `deleteObjectsWhere(ctx, ex, where string, args ...any)` emitting the cascade deletes as `uid IN (SELECT uid FROM objects WHERE <where>)` then the `objects` delete; the three callers become one line each.

- **Three copies of "mutex-guarded, lazily-created, never-reclaimed keyed registry".** `workerSet.lifecycleLock`, `ClusterCoreController.reconcileLock` and `cacheClientPolicies.get` share a body and each carries its own paragraph re-explaining the reclamation policy. **Fix:** one generic `keyedRegistry[K comparable, V any]` in `helpers.go` with `getOrCreate(k, func() V)`. Note this overlaps the stats-map item above, which records the catch: the sync controller's stats map is deliberately guarded by the *external* `writeMu`, so any generic must accept a caller's mutex rather than owning one. Worth doing as one change with that item, or not at all.

- **`sanitize` deep-copies a whole object body to delete two fields.** `objectsync/store.go` ~681 calls `u.DeepCopy()` so it can remove `metadata.managedFields` and the kubectl last-applied annotation. **Cost:** one full recursive clone per object, on every watch delta *and* every relist page item, across ~100–150 kind workers — a cold sync of a 20k-object cluster is 20k whole-object copies for two deletions. **Fix:** shallow-copy only what is mutated — the top-level map and its `metadata` sub-map (plus `data` for a Secret) — leaving every other subtree shared. Equivalent, and O(top-level keys) instead of O(object size). **Measure first:** worth confirming against a real cold sync before restructuring the write path.

- **A relist rewrites every row in full even when nothing changed.** `insertRow` re-compresses `raw_json`, upserts all 15 columns and `DELETE`+re-`INSERT`s both edge tables per object per resync period (30m, every kind), when the mark-and-sweep only needs `updated_at` bumped. **Cost:** on a quiet 20k-object cluster, 20k needless zlib compressions and 60k+ statements every resync, on the single writer connection all ~150 workers queue behind. **Fix:** cheap path first inside the same transaction — `UPDATE objects SET updated_at=? WHERE uid=? AND resource_version=?`; if it affected a row the object is unchanged, so skip the projection, the compress and both edge rewrites, and fall through to the full path only on `RowsAffected()==0`.

- **`events.raw_json` is written but never read.** Every event body is `json.Marshal`ed and zlib-compressed into a column no read path selects — `store.Events()` reads the flattened columns only, and there is no other reader in the tree. **Cost:** a marshal + a compress + the stored bytes per event, on the highest-volume collection in the system, forever, plus the file growth and the vacuum work it creates. **Decide, don't just delete:** it is plausibly there for a future event-detail view. Either stop populating it, or record that it is deliberate and what will read it.

- **The metadata-diff resync fetches sequentially and commits per object.** `kubesync/driver.go` ~682: up to `diffThreshold` (200) serialized `src.Get` round trips per kind per resync — ~4s at 20ms RTT with the LIST semaphore slot held throughout — each `ApplyDiff` opening its own transaction and firing its own notify, which re-arms the (expensive) objects re-read 200 times. **Fix:** fan the GETs over a small bounded pool (4–8, drawing on the same per-cache rate limiter — they are independent reads), and apply in batches inside one transaction with a single notify, mirroring the existing `DeleteByUIDs` batching (`ApplyDiffBatch` on `MetadataDiffStore`).

- **The sync-health fold flushes per watch frame.** Each flush copies the controller's whole stats map (under `writeMu`, contended by exactly the condition writers that are busy then) and re-folds the dirty caches. **Cost:** at cold start each of a cache's ~150 kinds emits several frames, so it is O(K²) per cache per cold start. **Fix:** on a frame, mark dirty and arm a short timer (100–250ms) instead of flushing inline; flush on the timer and on the existing 10s tick. The output is a latest-value gauge, so coalescing loses nothing.

- **`readCacheStats` knows which catalog rows are backed by the objects table.** It scans `store.Kinds()` and skips the Events row by kind identity, because events live in their own table — a fact about the cache's physical schema, expressed in the domain service. **Fix:** either have `store.KindRow` carry the property (a `Tabular`/`InObjects` flag set by `EnsureKindCatalog`, so the service filters on a property rather than an identity), or move the rollup into `store` as a `Stats(ctx)` read and have the service forward. `store` owns reads and the `kind_catalog`/`kind_counts` join; it is where a third table would land.

- **`gvrSyncAnchorFilter` is ~150 lines compensating for beehive's watch shape.** A memoized ruled-out-anchor set plus a bounded undecided-frame buffer, all to turn a fleet-wide per-kind `WatchList` into a cache-scoped one; every reasoning step in it is about beehive, not about clusters, and it runs per subscriber on every sync record of every cache in the fleet. **Fix:** beehive is first-party — add an owner-scoped `WatchList` (filtered at the store, where the owner edge is already indexed). The service call then collapses to `watchListStream` like its three siblings and the memo, the buffer and `maxUndecidedSyncFrames` all disappear. **Blocked on:** a change to the beehive dependency, outside this repo.

- **The kubeconfig importer polls where an event exists.** `ReconcileClusterSet` retries the last snapshot every 2s while a departing `Cluster` still holds a context's name. **Cost:** a second liveness mechanism whose interval is tuned to a guess about drain latency, in a component that is otherwise purely level-triggered off kubeconfig snapshots. **Fix:** wake off the signal itself — the importer already holds `coreClient`, so subscribe to the Cluster kind's `WatchList` and re-run on the frame that frees the name. That also removes the guess, and could replace the per-reconcile `List` that builds `tracked`. **Weigh:** the poll is simple and self-limiting; the watch is another long-lived subscription in a component that currently owns none.

- **A hard `Deleted` on the discovery watch carries no `cacheID`, so every client needs a reverse index.** The frame's owner edge is gone by then, so `cacheID` is `"0"` and the webview resolves it by scanning its whole map for a matching record id — a client-side workaround for something the stream could state. The sidecar already solved the identical problem for sync records, on the server (`gvrSyncAnchorFilter` forwards a hard delete on its id alone). **Fix:** have `Discovery().Watch` remember the `id → cacheID` mapping it has already seen and stamp it onto the `Deleted` frame, so every consumer keys one way.

- **`kubesync.resync` still mixes strategy with mechanics.** ~130 lines that take the LIST-phase limiter slot, make the four-way strategy choice (non-diff store / cold cache / no metadata endpoint / delta past `diffThreshold` — each its own bail-out to `fullList`), and *are* the diff algorithm. The duplicated epilogue was factored into `recordPass` by this pass; the interleaving remains. **Fix:** keep the limiter and the participation/warmth checks in `resync` and dispatch to `d.diffResync(ctx, md)`, which returns a sentinel `errFallBackToList` for its own bail-outs — so the decision a maintainer opens this function to understand is readable without the mechanics.

## Testing

- **Audit the tree for wall-clock-dependent tests (magic sleeps and thin real-timer margins).** Both `CLAUDE.md` files state the rule — "don't wait on wall-clock delays to let async work settle" — and the tree is *mostly* compliant, so this is a small, bounded sweep rather than a campaign. What a survey turns up today:
  - **Rust is the model, not a target.** `src-tauri/.../sidecar/ipc.rs`'s retry test uses `#[tokio::test(start_paused = true)]` and lets tokio auto-advance virtual time between parked timers, with a comment saying so. Whatever the Go/TS fixes look like, this is the shape to match.
  - **Frontend is clean.** No `setTimeout`-based waits in any `*.test.ts[x]`; the suites use `vi.useFakeTimers()` + `advanceTimersByTimeAsync`, `waitFor`, or the `flush()` helper, per the rule.
  - **Go has exactly one literal sleep**: `internal/cluster/service_test.go:~1219`, `time.Sleep(100ms) // longer than the debounce window`, asserting a NEGATIVE — that an unrelated resource's keyed write does *not* wake a watch. That's the hard case: `require.Eventually` proves something happened, but proving something didn't needs either a deterministic clock on the debounce or a positive signal to synchronize on (e.g. ping the *matching* resource afterward and assert the read count when THAT lands, so the negative is checked at a known point rather than after a guessed wait).
  - **The real category is thin real-timer margins, not `time.Sleep`** — tests that never call Sleep but still fail on a slow machine because they race short real durations. `cache_idle_timeout_test.go` is the known instance (its own item above). The ~90 `time.After(...)` uses in sidecar tests are almost all *deadlines* guarding a channel receive, which the rule explicitly permits; the audit should separate those from any that are load-bearing waits.
  - **Output:** either fixes, or a short note recording which timing-sensitive tests are deliberate and why, so the next reader doesn't re-litigate them. Worth doing while the memory is fresh — a `-count=20` soak of `./internal/cluster/...` on a loaded machine is the cheapest way to find the rest (that is how the `TestClusterDataKindsWatchWakesOnKeyedWrite` race was identified).
